# 通用标准规范工程 Loop

**源 SOP**：《通用标准规范撰写与 Loop 自迭代优化元提示体 V3》。这是把源 SOP **封装为可复用 Skill**，不是将 DuckDB SQL 教程 SOP 升级为通用技能。源全文位于 `assets/original-sop-v3.md`，详细规则按原文顺序无内容改写地拆在 `references/` 中。

## 目标

把输入要求转成对象清楚、条件可判断、动作可执行、结果可验收、边界可解释、依据可追溯、版本可回退的标准。**不以润色、模板填充、SQL 语法覆盖、专业概念堆叠代替标准制定。**

固定核心闭环：识别标准类型 → 领域映射 → 组织轴 → 事实与依据 → 规范本体 → 主表 → 原子标准与逻辑规则 → 测试 → 依据时效 → Baseline V0 → Loop 0–9 → 最小修正 → 回归 → 发布判断。

## 入口契约

1. 从用户材料提取：主题、使用目标、规范对象、读者/责任角色、场景、已确认要求、已有分类、案例、依据、交付载体、约束和特殊规则。未知保持未知，不能补造法规、阈值、时间、负责人或当前版本。
2. 按原文先识别**主标准类型与辅助类型**：分类、判定、操作、准入、能力、技术使用、质量、风险治理、数据、流程或混合。必须识别领域后才能选择术语、主组织轴和结构。
3. 把输入分成**事实、规则判断、动作、未知**；详细账本进一步分为已确认事实、明确要求、推导、设计决策、示例、冲突、缺失、待裁决。示例不自动成为规则，推导不得写成官方要求。
4. 主体默认**一张主表、一个主要组织轴**。每条规范原子化并有标准 ID、适用条件、排除条件、具体动作、验收证据、依据与维护角色。使用 MUST / SHOULD / MUST NOT / GATE / MAY；不能用“确保稳定”等口号代替可检验规则。
5. 复杂条件按原文的中文 Lisp 表达：中间只用 `AND`、`OR`、`NOT`，叶子只写独立事实条件；**判断条件与动作分开**。需要渐进/能力升级时，按原文的前置条件、输入产出、反模式、验收、停留与升级 Gate；无依赖的能力不可伪造线性阶段。
6. 为关键标准设计正向、反向、边界、排除、冲突、反事实、回归测试。核验官方/权威来源的当前有效性、版本和适用范围；未实际检索/测试不可宣称已验收。
7. 保存初稿 **Baseline V0**，按 **Loop 0–9** 审查领域、时效、完整性、原子性、冲突、反事实、可执行性、溯源、复杂度、回归。发现问题先定根因，**只做最小必要修正**；复验失败就回退，不叠补丁。
8. 用原文 12 维、各 0–2 分评分；P0/P1 优先。按原文发布 Gate 得出**可发布 / 有条件发布 / 不可发布**，不可把缺少测试或过时依据判成通过。
9. 满足停止条件即停，**最多 10 轮**，不为了凑次数循环；无法闭合则交付安全可用范围、阻断原因、待裁决角色和恢复条件。

## 执行纪律

- 用户要求“制定规范”时必须产出实际条目、规则、测试和证据，不能只给方法说明或空模板；信息不足则保留明确标注的待裁决项并继续不依赖它的步骤。
- 用户要求“仅审查 / 不修改”时，只给已验证的问题、位置、失败样本和修复建议，**不得修改原 SOP 或发布**。
- 不擅自改动用户既有标准、仓库或远程数据。发布/写入需用户授权，源 SOP 的“发布判断”不等于执行外部发布操作。
- 标准正文以**直接说明**为主，不把读者带入“先回答题目”的教学考试；必要的测试另存。
- 完整交付按原文的 18 项顺序；若用户要求一张大表，则只让一张主表承载主体，其他清单为辅助。
- 无真实测试、无当前来源证据时分别标记**未执行 / 待核验**；静态规则检查不能替代实际业务验收。

## 维护和测试

在修改此 Skill 前保存原文件与行为基线；先测失败、边界和原通过样本，再最小修改并回归。评估用例见 `evals/evals.json`。`scripts/validate_skill.py` 只检查包结构、分段覆盖与关键触发，不证明 Claude 实际触发或领域真实执行通过。
