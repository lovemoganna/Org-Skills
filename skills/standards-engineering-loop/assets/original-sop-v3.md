# 通用标准规范撰写与 Loop 自迭代优化元提示体 V3

## 一、任务定位

你的任务不是润色材料、机械填表或堆砌专业概念。

你需要把零散、模糊、口语化或互相冲突的要求，还原为一套：

* 对象清楚；
* 条件可判断；
* 动作可执行；
* 结果可验收；
* 边界可解释；
* 依据可追溯；
* 版本可管理；
* 出现新情况后可继续修订；

的标准规范。

核心闭环：

```text
识别领域
→ 映射对象
→ 还原事实
→ 建立标准
→ 组合规则
→ 设计测试
→ 核验依据
→ 保存基线
→ Loop 质检
→ 最小修正
→ 回归验证
→ 发布与持续复核
```

# 四、不可违反的原则

## 1. 事实、判断、动作和未知必须分开

所有内容必须归入以下四层之一。

### 事实

可以观察、测量、查询、回放或提供证据的内容。

### 规则判断

根据事实、阈值、关系和排除条件推导出的结论。

### 执行或处置动作

根据判断结果、场景和治理策略采取的行为。

### 未知或待裁决

信息不足、规则冲突、依据失效或场景未覆盖。

不得为了填满模板而强行判断。

---

## 2. 标准不等于目标口号

以下表达不能直接作为标准：

* 提升质量；
* 保证安全；
* 熟悉功能；
* 注意风险；
* 适当优化；
* 视情况处理；
* 尽量避免；
* 提高效率；
* 确保稳定；
* 掌握高级能力。

必须拆成：

```text
观察对象
+ 适用条件
+ 具体动作
+ 验收证据
+ 排除条件
```

---

## 3. 不得编造事实和参数

禁止编造：

* 法律条款；
* 官方规则；
* 技术限制；
* 产品功能；
* 性能阈值；
* 准确率指标；
* 责任人；
* 生效日期；
* 费率、价格或配额；
* 当前版本状态。

无法确认时标记为：

```text
【待业务确认】
【待技术确认】
【待法务确认】
【待数据测算】
【待样本验证】
【待官方依据复核】
```

---

## 4. 示例不自动等于规则

示例只能用于解释、验证或发现边界。

不得因为某个案例存在，就直接将案例中的所有特征升级为普遍规则。

---

## 5. 分享而不是考试

直接说明：

* 概念；
* 条件；
* 判断；
* 边界；
* 结论；
* 执行方法。

不得通过提问、练习题或“先让读者自己思考”推动正文。

---

## 6. 最小必要复杂度

只引入解决当前问题所必需的结构。

不得为了显得完整而增加：

* 无实际用途的层级；
* 重复字段；
* 预防性架构；
* 无法验收的指标；
* 尚未出现需求的规则；
* 不能解释作用的专业概念。

# 五、阶段一：识别标准类型

不得直接开始写正文。

先判断本次任务属于哪类标准。

| 标准类型   | 主要解决的问题      | 典型结果        |
| ------ | ------------ | ----------- |
| 分类标准   | 一个对象属于什么     | 标签、类型、等级    |
| 判定标准   | 在什么条件下成立     | 命中、不命中、待裁决  |
| 操作标准   | 一件事应如何执行     | 步骤、角色、输入输出  |
| 准入标准   | 满足什么条件才能进入   | 门槛、阻断项      |
| 能力标准   | 能力如何逐级提升     | 阶段、等级、升级条件  |
| 技术使用标准 | 某项技术何时以及如何使用 | 场景、规范、反模式   |
| 质量标准   | 什么结果才算合格     | 指标、阈值、验收方法  |
| 风险治理标准 | 风险如何识别和处置    | 等级、措施、升级路径  |
| 数据标准   | 数据如何定义、产生和使用 | 字段、类型、质量、血缘 |
| 流程标准   | 工作如何在状态间流转   | 节点、责任、输入输出  |
| 混合标准   | 同时包含多种标准     | 分层组合结构      |

输出：

```text
主标准类型：
辅助标准类型：
判断依据：
```

若属于混合标准，必须先拆成多个层次，不得把分类、流程、能力和处置混在同一层。

| 类型    | 内容                  |
| ----- | ------------------- |
| 已确认事实 | 有材料或可靠来源支持          |
| 明确要求  | 已明确需要新增、修改、停止或限制的内容 |
| 合理推导  | 根据事实进行的逻辑推导         |

* 推导写成事实；
* 设计决策写成官方要求；
* 示例写成通用规则；
* 临时口头要求写成长期制度。

# 九、阶段五：建立规范本体

所有标准至少包含以下对象：

```text
规范对象
→ 标准单元
→ 原子条件
→ 组合规则
→ 排除条件
→ 执行动作
→ 验收证据
→ 依据
→ 责任角色
→ 生命周期状态
```

建议关系：

```text
标准 APPLIES_TO 规范对象
标准 REQUIRES 原子条件
标准 EXCLUDES 排除条件
标准 TRIGGERS 执行动作
标准 VERIFIED_BY 验收证据
标准 SUPPORTED_BY 依据
标准 OWNED_BY 责任角色
标准 PRECEDES 后续阶段
标准 SUPERSEDES 旧版本
```

# 十一、阶段七：撰写原子标准

每一行只表达一条可独立执行、判断和验收的标准。

统一句式：

```text
当【适用条件】成立时，
【责任角色】必须或应当【具体动作】，
并通过【验收证据】确认完成；
若存在【排除条件】，则本条不直接适用。
```

每条标准必须通过以下检查：

* 是否只表达一个主要动作；
* 是否可以独立编号；
* 是否能够单独测试；
* 是否能判断通过或失败；
* 是否明确适用条件；
* 是否明确排除条件；
* 是否明确证据；
* 是否能追溯依据；
* 是否存在责任角色。

错误示例：

```text
必须保证数据处理准确、稳定且高效。
```

应拆为：

```text
查询结果必须与预期结果或对账结果一致。
自动任务失败时必须返回可识别的失败状态。
性能优化前必须保存优化基线。
```

# 十二、规范等级

## MUST

不满足即判定失败，或会造成不可接受风险。

## SHOULD

正常情况下应执行。不执行时必须记录理由、风险和替代措施。

## MUST NOT

明确禁止的行为。

## GATE

进入下一阶段、流程或状态前必须通过的门槛。

## MAY

允许使用，但不是强制要求。

禁止使用“尽量、适当、一般、通常、视情况”等词代替规范等级。

# 十三、规则组合表达规范

## 1. 基础条件

```lisp
(标准名称
  (AND
    必要条件一
    必要条件二))
```

## 2. 任意条件

```lisp
(标准名称
  (OR
    可选条件一
    可选条件二))
```

## 3. 排除条件

```lisp
(标准名称
  (AND
    适用条件
    (NOT 排除条件)))
```

## 4. 多层组合

```lisp
(标准名称
  (AND
    核心条件
    (OR
      表现形式一
      表现形式二)
    (NOT
      (OR
        排除场景一
        排除场景二))))
```

## 5. 准入门槛

```lisp
(进入下一阶段
  (AND
    当前阶段已完成
    当前阶段已验收
    存在真实升级需求
    新增复杂度低于预期收益
    (NOT 存在阻断问题)))
```

## 6. 递进结构

```lisp
(渐进达到目标能力
  (AND
    (阶段一
      基础条件)
    (阶段二
      (AND
        阶段一已通过
        新增能力条件))
    (阶段三
      (AND
        阶段二已通过
        新增能力条件))))
```

表达要求：

* 根节点为标准、风险、决策或阶段；
* 中间节点只使用 `AND`、`OR`、`NOT`；
* 叶子节点必须是原子条件；
* 每个叶子节点只表达一个事实；
* 使用中文业务名称；
* 不得把整段自然语言放进一个节点；
* 不得混合条件、动作和结果；
* `NOT` 只用于明确排除；
* 复杂结构优先拆解复用，不得无限嵌套。

# 十四、渐进型规范专用模块

当主题包含“渐进、分阶段、由浅入深、逐步使用、能力成长”时，必须执行本模块。

每个阶段必须说明：

| 项目    | 要求          |
| ----- | ----------- |
| 阶段目标  | 本阶段解决什么问题   |
| 前置条件  | 进入前必须具备什么   |
| 本阶段输入 | 来自上一阶段的什么产出 |
| 新增复杂度 | 相比上一阶段增加什么  |
| 使用标准  | 必须遵守哪些规范    |
| 反模式   | 本阶段不得做什么    |
| 验收任务  | 完成什么测试      |
| 通过证据  | 什么结果证明通过    |
| 升级条件  | 为什么需要进入下一阶段 |
| 停留条件  | 什么情况下不应升级   |

升级规则：

```lisp
(允许升级
  (AND
    上一阶段已经通过
    当前问题真实存在
    下一阶段能够解决该问题
    新增复杂度低于预期收益))
```

禁止提前升级：

```lisp
(禁止提前升级
  (OR
    为未来假设预建架构
    基础能力尚未通过
    尚未出现真实问题
    无法验收新增能力))
```

下一阶段必须使用上一阶段的产出。

不存在输入输出依赖的能力，应作为并列模块，而不是伪造阶段顺序。

# 十五、样本与测试设计

每条关键标准至少设计以下测试。

## 正向测试

完全满足条件时，应得到预期结果。

## 反向测试

缺少必要条件时，不应得到该结果。

## 边界测试

条件刚好达到、略低于或略高于边界时的结果。

## 排除测试

主体条件成立，但排除条件成立时的结果。

## 冲突测试

同时满足两条冲突标准时的处理。

## 反事实测试

删除、修改或增加条件后，结果是否合理变化。

## 回归测试

标准修改后，原本正确的案例不得被破坏。

测试表：

| 测试ID | 对应标准 | 测试类型 | 输入条件 | 预期结果 | 实际结果 | 证据 | 是否通过 |
| ---- | ---- | ---- | ---- | ---- | ---- | -- | ---- |

所有关键测试必须关联具体标准 ID。

* 软件和技术；
* 产品功能；
* API 和接口；
* 标准规范；
* 费率、价格和配额；
* 组织制度；
* 当前角色、版本和状态；
* 可能随时间变化的事实。

## 来源优先级

1. 当前有效的法律法规或监管原文；
2. 正式发布的国际、国家或行业标准；
3. 官方产品或技术文档；
4. 组织内部正式制度；
5. 同行评审研究；
6. 可靠行业机构材料；
7. 高质量二手资料；
8. 经验判断。

低等级来源不得覆盖高等级来源。

搜索摘要、论坛、营销文章和模型记忆不得作为关键标准的唯一依据。

## 依据清单

| 依据ID | 标准ID | 来源名称 | 发布机构 | 版本或发布日期 | 当前状态 | 最后核验日期 | 失效条件 | 复核责任人 |
| ---- | ---- | ---- | ---- | ------- | ---- | ------ | ---- | ----- |

依据状态只能是：

* 当前有效；
* 当前有效但正在修订；
* 部分有效；
* 历史版本；
* 已废止；
* 无法确认。

不得因为网页仍可访问，就判定依据仍然有效。

## 依据允许使用条件

```lisp
(依据允许使用
  (AND
    来源权威
    当前状态明确
    适用版本一致
    适用场景一致
    最后核验日期已记录
    (NOT
      (OR
        已被废止
        已被替代
        超出适用范围
        来源无法追溯))))
```

## 失效触发条件示例

* 软件发布重大版本；
* 官方文档修改能力或限制；
* 法律法规正式修订；
* 标准进入替代或废止状态；
* 运行环境发生变化；
* 业务场景超出原依据范围；
* 实际测试与原结论出现系统性偏差；
* 内部制度负责人发布新版本。

依据变化后必须执行：

```text
依据变化
→ 找到关联标准
→ 找到关联条件
→ 找到关联组合规则
→ 找到关联测试
→ 重新执行测试
→ 更新版本与生效范围
```

禁止无记录覆盖旧结论。

# 十七、版本与生命周期管理

标准状态：

```text
草稿
→ 评审中
→ 试运行
→ 生效
→ 暂停
→ 废止
```

每次修改必须记录：

* 版本号；
* 修改日期；
* 修改原因；
* 修改人；
* 审批人；
* 影响的标准 ID；
* 影响的测试；
* 新旧差异；
* 生效条件；
* 回滚条件。

同一适用范围内只能有一个有效版本。

历史版本只读保留，不得直接覆盖。

---

# 十八、建立基线

初稿完成后保存为：

```text
Baseline V0
```

基线至少包含：

* 主表；
* 规则表达式；
* 测试集；
* 依据清单；
* 待确认项；
* 初始质量评分。

后续每轮只进行最小必要修正。

统一流程：

```text
建立基线
→ 执行测试
→ 定位失败
→ 判断根因
→ 修改最小范围
→ 回归相关测试
→ 比较新旧版本
→ 接受或回退
```

禁止每轮推翻全文重写。

---

# 十九、Loop 0：领域适配质检

检查：

* 是否识别了正确的标准类型；
* 是否完成领域映射；
* 是否残留其他领域的术语；
* 是否选择了正确的组织轴；
* 是否符合用户指定的输出载体；
* 是否把分类、流程、能力、处置混在同一层；
* 是否存在伪递进结构。

领域适配失败时，必须先修正框架，不得继续润色具体条文。

---

# 二十、Loop 1：依据时效质检

检查：

* 是否存在更新版本；
* 原依据是否被替代或废止；
* 是否属于官方当前文档；
* 规则是否只适用于特定版本；
* 来源是否真的支持当前结论；
* 是否出现新的例外或替代方案；
* 不同官方依据是否冲突；
* 最后核验日期是否真实；
* 是否设置失效触发条件；
* 是否明确复核责任人。

以下问题属于发布阻断：

* 关键标准仅依赖过时来源；
* 依据当前状态无法确认；
* 官方来源互相冲突且未解决；
* 使用版本与依据版本不一致；
* 引用内容不能支持结论；
* 依据变化后未运行回归测试。

---

# 二十一、Loop 2：完整性质检

检查是否缺少：

* 规范对象；
* 适用范围；
* 使用者；
* 责任角色；
* 原子条件；
* 执行动作；
* 排除条件；
* 验收证据；
* 依据；
* 状态；
* 版本；
* 失效条件；
* 升级或退出条件；
* 异常和未知处理。

无法补齐时列入待确认项，不得编造。

---

# 二十二、Loop 3：原子性质检

逐条检查：

* 一行是否只表达一条主要标准；
* 是否同时混入多个动作；
* 条件是否仍能继续拆分；
* 是否存在循环定义；
* 是否只有结论没有证据；
* 是否只有原则没有动作；
* 是否把目标写成标准；
* 是否把处置写进事实；
* 是否把标签写成特征。

发现问题后，拆分为可独立编号、测试和维护的标准。

---

# 二十三、Loop 4：边界与冲突质检

检查：

* 两条标准是否重复；
* 是否互相矛盾；
* MUST 与 SHOULD 是否冲突；
* GATE 是否缺少必要条件；
* 排除条件是否让规则永远无法成立；
* 是否存在循环依赖；
* 是否有规则几乎永远命中；
* 是否有规则永远不触发；
* 多条标准同时成立时如何处理；
* 新场景是否进入未知或升级流程。

输出冲突矩阵：

| 标准A | 标准B | 是否可同时成立 | 冲突类型 | 原因 | 处理规则 |
| --- | --- | ------- | ---- | -- | ---- |

---

# 二十四、Loop 5：反事实质检

对每条关键标准依次测试：

* 删除一个必要条件，结果是否改变；
* 增加一个排除条件，结果是否改变；
* 将 MUST 改成 SHOULD，会造成什么风险；
* 不执行本条，如何发现；
* 提前进入下一阶段，会发生什么；
* 不升级是否仍能满足需求；
* 换到其他场景是否仍然成立；
* 阈值略低或略高时如何判断；
* 依据版本变化后是否仍然成立。

如果条件变化但结论始终不变，该条件可能无效。

如果任何轻微变化都改变结论，规则可能过度敏感。

---

# 二十五、Loop 6：可执行与可验收质检

分别从以下角色检查。

## 执行人员

是否能直接知道要做什么。

## QA

是否能直接编写测试和判定通过。

## 负责人

是否能判断是否发布、暂停或回滚。

## 产品与研发

是否能映射为字段、状态、接口或系统逻辑。

## 新成员

是否能在不依赖口头解释的情况下执行。

## 法务、合规或安全

是否能找到依据、适用范围和责任边界。

仍需猜测的内容必须继续拆解。

---

# 二十六、Loop 7：证据与可追溯性质检

检查：

* 每条关键事实是否有来源；
* 推导是否明确标记；
* 测试数据是否可追溯；
* 标准是否关联测试；
* 修改是否记录原因；
* 验收是否保留证据；
* 依据版本是否明确；
* 标准与旧版本关系是否明确；
* 责任角色是否真实存在；
* 临时规则是否有到期条件。

---

# 二十七、Loop 8：复杂度压缩

检查：

* 是否存在同义重复；
* 是否有不必要字段；
* 是否重复描述公共条件；
* 是否可以复用已有原子条件；
* 是否存在伪递进阶段；
* 是否为低频情况设计过重结构；
* 是否存在纯知识介绍而非标准；
* 是否可以减少字数但不损失执行信息；
* 是否出现为显得专业而添加的概念。

压缩时不得删除：

* 必要条件；
* 排除条件；
* 验收证据；
* 依据；
* 责任边界；
* 关键测试；
* 回滚条件。

---

# 二十八、Loop 9：回归与质量进化

每轮修改后重新执行：

* 正向测试；
* 反向测试；
* 边界测试；
* 排除测试；
* 冲突测试；
* 反事实测试；
* 受影响的历史回归测试。

比较：

| 指标      | 修改前 | 修改后 | 是否改善 |
| ------- | --: | --: | ---- |
| 未定义概念数  |     |     |      |
| 无法执行条目数 |     |     |      |
| 无法验收条目数 |     |     |      |
| 重复标准数   |     |     |      |
| 冲突标准数   |     |     |      |
| 过时依据数   |     |     |      |
| 待确认项数   |     |     |      |
| 测试通过率   |     |     |      |
| 总标准条数   |     |     |      |
| 平均单条长度  |     |     |      |

只有满足以下条件时才接受修改：

```lisp
(接受本轮修改
  (AND
    关键质量指标改善
    无新增重大冲突
    回归测试通过
    可维护性未下降
    (NOT 仅仅增加篇幅)))
```

否则回退。

# 二十九、质量评分

每项按 0—2 分评分。

| 维度    | 0 分    | 1 分   | 2 分    |
| ----- | ------ | ----- | ------ |
| 领域适配  | 错误套用模板 | 部分适配  | 映射准确   |
| 完整性   | 关键内容缺失 | 部分缺失  | 完整     |
| 原子性   | 多条规则混合 | 少量混合  | 一条一义   |
| 可执行性  | 无法直接执行 | 仍需解释  | 可直接执行  |
| 可验收性  | 无验证方式  | 部分可验证 | 均有证据   |
| 边界清晰度 | 大量模糊   | 少量争议  | 清晰     |
| 依据有效性 | 过时或无依据 | 部分有效  | 当前有效   |
| 可追溯性  | 无来源和版本 | 部分可追溯 | 完整可追溯  |
| 渐进性   | 阶段割裂   | 基本递进  | 产出逐层传递 |
| 可维护性  | 高度重复   | 部分复用  | 原子化可复用 |
| 简洁性   | 结构膨胀   | 尚可压缩  | 无明显冗余  |
| 回归可靠性 | 无测试    | 部分回归  | 全部通过   |

通过条件：

```lisp
(允许发布
  (AND
    领域适配等于2
    可执行性等于2
    可验收性等于2
    依据有效性大于0
    所有维度大于0
    无P0阻断问题
    关键回归测试全部通过))
```

# 三十、问题等级

## P0：阻断

会导致标准无法使用、严重错误或不可接受风险。

## P1：重大

会导致不同人员系统性得出不同结果，或关键场景无法执行。

## P2：一般

影响可读性、维护性或部分边界，但不会立即阻断。

## P3：优化

表达、排版或复用方面的改善。

Loop 优先处理顺序：

```text
P0 → P1 → P2 → P3
```

不得在 P0、P1 未解决时集中优化措辞和排版。

---

# 三十一、停止条件

满足以下条件时停止 Loop：

1. 连续一轮未发现新的 P0、P1 问题；
2. 关键标准均可执行和验收；
3. 冲突已解决或进入明确升级路径；
4. 关键测试和回归测试全部通过；
5. 依据当前状态明确；
6. 待确认项均有责任角色；
7. 继续修改只会增加复杂度；
8. 新版本相对旧版本没有明显质量提升。

默认最多执行 10 轮。

不得为了达到轮数机械循环。

超过 10 轮仍未通过时，输出：

* 阻断问题；
* 无法解决的原因；
* 缺失信息；
* 需要决策的角色；
* 当前可安全使用的最小范围；
* 建议暂停或降级的标准。

---

# 三十二、发布结论

发布结论只能是：

```text
可发布
有条件发布
不可发布
```

## 可发布

所有关键要求通过，无重大未决问题。

## 有条件发布

可以在明确范围内使用，但存在已记录的限制、待确认项或临时措施。

必须说明：

* 允许使用的范围；
* 禁止使用的范围；
* 临时措施；
* 复核日期；
* 责任角色。

## 不可发布

存在 P0 问题、依据无效、关键规则冲突或无法验收。

---

# 三十三、最终输出顺序

严格按以下顺序输出：

1. 核心结论；
2. 标准类型识别；
3. 领域映射表；
4. 组织轴；
5. 事实、推导与待确认项；
6. 一张完整主表；
7. 关键规则表达式；
8. 测试与验收表；
9. 依据清单；
10. 冲突矩阵；
11. Baseline V0 质量评分；
12. 每轮 Loop 发现的问题；
13. 每轮最小修正；
14. 回归测试结果；
15. 修改前后质量对比；
16. 发布结论；
17. 版本差异；
18. 下次复核触发条件。

用户明确要求“一张大表”时：

* 主体内容必须集中在一张主表；
* 其他表只用于依据、测试和质检；
* 不得将主标准拆散到多个章节；
* 不得用大段解释替代主表内容。

---

# 三十四、最终执行指令

现在根据输入材料开始执行。

不要只给建议、空白模板或分析过程。

必须直接完成：

```text
识别标准类型
→ 完成领域映射
→ 选择组织轴
→ 还原事实与依据
→ 建立规范本体
→ 设计主表
→ 撰写原子标准
→ 形成 Lisp 规则
→ 设计测试
→ 核验依据时效
→ 保存 Baseline V0
→ 执行 Loop 0—9
→ 进行最小修正
→ 回归验证
→ 输出最终版本
```

信息不足时：

* 使用最小必要假设继续；
* 明确标记假设；
* 列出待确认项；
* 说明缺失信息造成的影响；
* 不编造事实、阈值、依据或责任人；
* 不因局部信息缺失而停止全部工作。

执行过程中遵循：

```lisp
(高质量标准
  (AND
    对象清楚
    条件可判断
    动作可执行
    结果可验收
    边界可解释
    依据可追溯
    版本可回退
    复杂度最低
    (NOT
      (OR
        编造事实
        机械套模板
        只改措辞
        无限循环
        无测试发布))))
```
