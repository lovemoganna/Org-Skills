# 九、阶段五：建立规范本体

所有标准至少包含以下对象：

```text
规范对象
→ 标准单元
→ 原子条件
→ 组合规则
→ 排除条件
→ 执行动作
→ 验收证据
→ 依据
→ 责任角色
→ 生命周期状态
```

建议关系：

```text
标准 APPLIES_TO 规范对象
标准 REQUIRES 原子条件
标准 EXCLUDES 排除条件
标准 TRIGGERS 执行动作
标准 VERIFIED_BY 验收证据
标准 SUPPORTED_BY 依据
标准 OWNED_BY 责任角色
标准 PRECEDES 后续阶段
标准 SUPERSEDES 旧版本
```

# 十、阶段六：设计一张主表

默认以一张主表作为核心交付物。

其他说明、测试表和冲突矩阵只能作为辅助，不得反客为主。

## 通用主表字段

| 字段       | 说明                            |
| -------- | ----------------------------- |
| ID       | 唯一编号                          |
| 分类或阶段    | 所属位置                          |
| 规范等级     | MUST、SHOULD、MUST NOT、GATE、MAY |
| 标准名称     | 一句话概括                         |
| 标准内容     | 应当做什么                         |
| 适用条件     | 何时适用                          |
| 排除或不适用条件 | 何时不成立                         |
| 执行方式     | 如何落实                          |
| 验收证据     | 如何证明完成                        |
| 规则表达式    | 结构化条件                         |
| 依据来源     | 规则依据                          |
| 依据版本     | 适用的具体版本                       |
| 依据状态     | 有效、修订中、历史、废止等                 |
| 最后核验日期   | 最近检查日期                        |
| 失效触发条件   | 什么变化会触发复核                     |
| 责任角色     | 谁负责执行或维护                      |
| 标准状态     | 草稿、试行、生效、暂停、废止                |
| 备注       | 例外、风险或待确认项                    |

可根据领域修改字段名称，但不得删除以下核心链路：

```text
标准是什么
→ 何时适用
→ 何时不适用
→ 如何执行
→ 如何验收
→ 依据是什么
→ 谁负责维护
```

# 十一、阶段七：撰写原子标准

每一行只表达一条可独立执行、判断和验收的标准。

统一句式：

```text
当【适用条件】成立时，
【责任角色】必须或应当【具体动作】，
并通过【验收证据】确认完成；
若存在【排除条件】，则本条不直接适用。
```

每条标准必须通过以下检查：

* 是否只表达一个主要动作；
* 是否可以独立编号；
* 是否能够单独测试；
* 是否能判断通过或失败；
* 是否明确适用条件；
* 是否明确排除条件；
* 是否明确证据；
* 是否能追溯依据；
* 是否存在责任角色。

错误示例：

```text
必须保证数据处理准确、稳定且高效。
```

应拆为：

```text
查询结果必须与预期结果或对账结果一致。
自动任务失败时必须返回可识别的失败状态。
性能优化前必须保存优化基线。
```

# 十二、规范等级

## MUST

不满足即判定失败，或会造成不可接受风险。

## SHOULD

正常情况下应执行。不执行时必须记录理由、风险和替代措施。

## MUST NOT

明确禁止的行为。

## GATE

进入下一阶段、流程或状态前必须通过的门槛。

## MAY

允许使用，但不是强制要求。

禁止使用“尽量、适当、一般、通常、视情况”等词代替规范等级。

# 十三、规则组合表达规范

## 1. 基础条件

```lisp
(标准名称
  (AND
    必要条件一
    必要条件二))
```

## 2. 任意条件

```lisp
(标准名称
  (OR
    可选条件一
    可选条件二))
```

## 3. 排除条件

```lisp
(标准名称
  (AND
    适用条件
    (NOT 排除条件)))
```

## 4. 多层组合

```lisp
(标准名称
  (AND
    核心条件
    (OR
      表现形式一
      表现形式二)
    (NOT
      (OR
        排除场景一
        排除场景二))))
```

## 5. 准入门槛

```lisp
(进入下一阶段
  (AND
    当前阶段已完成
    当前阶段已验收
    存在真实升级需求
    新增复杂度低于预期收益
    (NOT 存在阻断问题)))
```

## 6. 递进结构

```lisp
(渐进达到目标能力
  (AND
    (阶段一
      基础条件)
    (阶段二
      (AND
        阶段一已通过
        新增能力条件))
    (阶段三
      (AND
        阶段二已通过
        新增能力条件))))
```

表达要求：

* 根节点为标准、风险、决策或阶段；
* 中间节点只使用 `AND`、`OR`、`NOT`；
* 叶子节点必须是原子条件；
* 每个叶子节点只表达一个事实；
* 使用中文业务名称；
* 不得把整段自然语言放进一个节点；
* 不得混合条件、动作和结果；
* `NOT` 只用于明确排除；
* 复杂结构优先拆解复用，不得无限嵌套。

# 十四、渐进型规范专用模块

当主题包含“渐进、分阶段、由浅入深、逐步使用、能力成长”时，必须执行本模块。

每个阶段必须说明：

| 项目    | 要求          |
| ----- | ----------- |
| 阶段目标  | 本阶段解决什么问题   |
| 前置条件  | 进入前必须具备什么   |
| 本阶段输入 | 来自上一阶段的什么产出 |
| 新增复杂度 | 相比上一阶段增加什么  |
| 使用标准  | 必须遵守哪些规范    |
| 反模式   | 本阶段不得做什么    |
| 验收任务  | 完成什么测试      |
| 通过证据  | 什么结果证明通过    |
| 升级条件  | 为什么需要进入下一阶段 |
| 停留条件  | 什么情况下不应升级   |

升级规则：

```lisp
(允许升级
  (AND
    上一阶段已经通过
    当前问题真实存在
    下一阶段能够解决该问题
    新增复杂度低于预期收益))
```

禁止提前升级：

```lisp
(禁止提前升级
  (OR
    为未来假设预建架构
    基础能力尚未通过
    尚未出现真实问题
    无法验收新增能力))
```

下一阶段必须使用上一阶段的产出。

不存在输入输出依赖的能力，应作为并列模块，而不是伪造阶段顺序。
