# 十五、样本与测试设计

每条关键标准至少设计以下测试。

## 正向测试

完全满足条件时，应得到预期结果。

## 反向测试

缺少必要条件时，不应得到该结果。

## 边界测试

条件刚好达到、略低于或略高于边界时的结果。

## 排除测试

主体条件成立，但排除条件成立时的结果。

## 冲突测试

同时满足两条冲突标准时的处理。

## 反事实测试

删除、修改或增加条件后，结果是否合理变化。

## 回归测试

标准修改后，原本正确的案例不得被破坏。

测试表：

| 测试ID | 对应标准 | 测试类型 | 输入条件 | 预期结果 | 实际结果 | 证据 | 是否通过 |
| ---- | ---- | ---- | ---- | ---- | ---- | -- | ---- |

所有关键测试必须关联具体标准 ID。

# 十六、依据时效与有效性管理

涉及以下内容时，必须检索当前官方或权威资料：

* 法律法规；
* 监管要求；
* 软件和技术；
* 产品功能；
* API 和接口；
* 标准规范；
* 费率、价格和配额；
* 组织制度；
* 当前角色、版本和状态；
* 可能随时间变化的事实。

## 来源优先级

1. 当前有效的法律法规或监管原文；
2. 正式发布的国际、国家或行业标准；
3. 官方产品或技术文档；
4. 组织内部正式制度；
5. 同行评审研究；
6. 可靠行业机构材料；
7. 高质量二手资料；
8. 经验判断。

低等级来源不得覆盖高等级来源。

搜索摘要、论坛、营销文章和模型记忆不得作为关键标准的唯一依据。

## 依据清单

| 依据ID | 标准ID | 来源名称 | 发布机构 | 版本或发布日期 | 当前状态 | 最后核验日期 | 失效条件 | 复核责任人 |
| ---- | ---- | ---- | ---- | ------- | ---- | ------ | ---- | ----- |

依据状态只能是：

* 当前有效；
* 当前有效但正在修订；
* 部分有效；
* 历史版本；
* 已废止；
* 无法确认。

不得因为网页仍可访问，就判定依据仍然有效。

## 依据允许使用条件

```lisp
(依据允许使用
  (AND
    来源权威
    当前状态明确
    适用版本一致
    适用场景一致
    最后核验日期已记录
    (NOT
      (OR
        已被废止
        已被替代
        超出适用范围
        来源无法追溯))))
```

## 失效触发条件示例

* 软件发布重大版本；
* 官方文档修改能力或限制；
* 法律法规正式修订；
* 标准进入替代或废止状态；
* 运行环境发生变化；
* 业务场景超出原依据范围；
* 实际测试与原结论出现系统性偏差；
* 内部制度负责人发布新版本。

依据变化后必须执行：

```text
依据变化
→ 找到关联标准
→ 找到关联条件
→ 找到关联组合规则
→ 找到关联测试
→ 重新执行测试
→ 更新版本与生效范围
```

禁止无记录覆盖旧结论。

# 十七、版本与生命周期管理

标准状态：

```text
草稿
→ 评审中
→ 试运行
→ 生效
→ 暂停
→ 废止
```

每次修改必须记录：

* 版本号；
* 修改日期；
* 修改原因；
* 修改人；
* 审批人；
* 影响的标准 ID；
* 影响的测试；
* 新旧差异；
* 生效条件；
* 回滚条件。

同一适用范围内只能有一个有效版本。

历史版本只读保留，不得直接覆盖。

# 十八、建立基线

初稿完成后保存为：

```text
Baseline V0
```

基线至少包含：

* 主表；
* 规则表达式；
* 测试集；
* 依据清单；
* 待确认项；
* 初始质量评分。

后续每轮只进行最小必要修正。

统一流程：

```text
建立基线
→ 执行测试
→ 定位失败
→ 判断根因
→ 修改最小范围
→ 回归相关测试
→ 比较新旧版本
→ 接受或回退
```

禁止每轮推翻全文重写。
