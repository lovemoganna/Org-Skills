# Dashboard Quality Evaluation

目标：Dashboard 生成后不得直接结束。必须执行：

```text
Generate
→ Evaluate
→ Detect Problems
→ Revise
→ Evaluate Again
→ Final
```

不要用简单平均分掩盖硬缺陷。

## A. 数据理解

检查：

- 数据结构是否理解正确；
- 主要实体与粒度是否正确；
- 时间字段是否正确；
- 指标口径、单位、状态是否正确；
- 是否使用不存在或越界字段。

## B. 业务价值

检查：

- 是否有明确 Dashboard Mission；
- 第一屏是否让用户快速知道当前最重要的状态；
- 是否回答真正业务问题；
- 是否存在纯展示模块；
- 是否能支持下一步判断或行动。

## C. 分析能力

检查：

- 是否发现变化；
- 是否发现异常；
- 是否解释变化；
- 是否定位对象；
- 是否保留竞争解释和限制；
- 是否支持继续验证。

## D. 信息架构

检查：

- 第一屏是否优先展示 P0/P1；
- 是否形成 `总览 → 发现 → 解释 → 定位 → 明细`；
- 是否存在同权卡片堆叠；
- 是否存在重复模块；
- 是否能清晰识别下一步入口；
- 是否更像 Dashboard，而不是长篇报告。

## E. 指标质量

检查：

- 指标是否有业务意义；
- 聚合是否合理；
- 分母是否明确；
- 时间范围是否明确；
- 单位是否明确；
- Context Metric 是否冒充 Insight。

## F. 可视化质量

检查：

- 图表是否与判断任务匹配；
- 是否存在误导；
- 是否存在冗余；
- 是否支持有效比较；
- 是否应改成表格；
- 是否只为丰富页面增加图形。

## G. 交互质量

检查：

- 筛选是否有用；
- 相关模块是否同步；
- 是否支持必要下钻；
- 是否能从异常到对象再到证据；
- 交互是否明显可发现；
- 静态输出是否是用户明确要求。

## H. UI 质量

检查：

- 信息层级是否清晰；
- 字体是否可读；
- 密度是否合理；
- 是否存在视觉噪音；
- 是否过度装饰；
- 是否符合专业分析工具而非营销网页；
- 桌面和移动端是否可用；
- 移动端筛选 / 控制区是否遮挡或长期挤压主要分析内容。

## Severity

### Critical

出现任一项即禁止最终输出：

- 数据错误；
- 编造数据；
- 指标口径错误；
- 业务逻辑错误；
- 核心结论无法回溯；
- 严重越界读取；
- 核心交互导致不同模块口径不一致。

### Major

必须修改：

- 核心业务问题没有回答；
- 信息架构混乱；
- 页面更像报告而不是 Dashboard；
- 图表选择错误；
- 无法完成 `What → So What → Why → Who/Where → Evidence`；
- 数据支持下钻但没有有效定位/下钻入口；
- P0/P1 被 Context / P2 淹没；
- Finding 重复堆叠；
- 缺少必要限制说明；
- 移动端 sticky 控制区占据过多视口，导致核心分析区难以使用。

### Minor

最后处理：

- 间距；
- 字体微调；
- 颜色微调；
- 局部排版；
- 微交互；
- 低影响装饰问题。

## Acceptance Rule

只有满足以下条件才可 Final：

- Critical = 0；
- Major = 0；
- Minor 不影响判断；
- Final Self-check 可明确回答 Dashboard Quality Framework 第 11 节问题。

## Evaluation Record

每轮至少保留：

| 问题 | Severity | 证据 | 修正 | 复测结果 |
|---|---|---|---|---|

只保留经过复测证明有效的修正。
