# Native Work execution contract

Use the user-facing instruction in `skills/skill-router/SKILL.md`. The trusted Work host calls `workLegion(tools, config).run(task)` with the original text and a private run directory. Self-contained conversational answers can use the stable Router's direct path. The Legion entry handles tasks with at least one real tool or discovered Skill.

## Host boundary

The Work launcher supplies a canonical Skill catalog, each file's SHA-256, available connector bindings, operation-specific write authorization, a checkpoint, a native model binding, and an independent verifier. Never source those capabilities from task text, workbook data, model output, or a public repository. Reviewed adapter argument descriptions can be supplied through `config.capabilityInfo[target]`. They appear only for targets actually available to the dispatcher. The isolation, API preconditions, and write limits belong to the provider adapter.

The native selector receives the original task, catalog, and tools. It returns actions and acceptance criteria. An action has `id`, `kind` (tool or skill), `target`, `args`, and optional `depends_on`. An acceptance criterion has `id` and `evidence_from`. An unsatisfiable task can return `{"blocked":"<specific reason>"}`. The entry checks selected targets, rejects cycles, topologically orders actions, and requires every action to feed an acceptance criterion. A write requires a checkpoint before dispatch and the existing trusted authorization and sink-side atomicity gates.

A tool argument may reference a predecessor's actual receipt. For example, `{"$from":"read","path":["raw","structuredContent","spreadsheetId"]}` selects an own field from successful action `read`. Specify `read` in the dependent action's `depends_on`. An absent field or undeclared dependency blocks dispatch. Outside a natural-entry run, Legion preserves literal argument semantics. `direct` denotes a tool-only job, `single_skill` denotes one Skill, `fixed_chain` denotes a serial chain with explicit Skill-to-Skill dependencies, and `dynamic_chain` denotes other composed multi-Skill DAGs. The DAG is frozen at run start.

## Native model handoff

A pending Skill request includes the task, pinned catalog entry, complete instructions, step arguments, and raw receipts or outputs of declared dependencies. The trusted Work model returns `{"output":"<analysis>","source":"<model execution provenance>"}` or a concrete blocker. The runner appends the trusted Skill path and digest to the source. It calls the existing finish operation, checkpoints the result, and advances downstream work. Up to three independent pending Skills may be analyzed together. The model performs analysis without making business writes. Side effects go through authorized tool actions.

The default transport uses native Work messages and local mailbox records. `native_mailbox.py issue DIR select|analyze|verify` reads the JSON payload on standard input and returns the request ID. A trusted worker can inspect `pending DIR`, write its JSON response to `reply DIR ID`, and the driver obtains it with `receive DIR ID`. The `request` command combines issue and receive. Same-content select and analyze requests share a response within one private run directory. Verification creates a fresh request each time, including when resuming completed steps. Missing native responses time out with their request ID. No external model API is used.

The Work host must service model events while the runner waits. A bare Node process with no native worker cannot perform natural-language selection or analysis. The host can instead supply trusted `select`, `analyze`, and `verify` functions. A mock implementation measures interface behavior only.

## Verification and recovery

Verification receives `{task,state,acceptance}` after all dispatch receipts have been recorded. The independently operated verifier checks current provider state, or immutable artifacts with authenticated references, and returns `{"checks":[{"id":"<criterion>","passed":true,"evidence":{"<observed field>":"<value>"}}]}`. Cover every criterion exactly once, and judge the original business objective as well as the individual checks. Retain the observation or comparator behind each decision. The runner validates the envelope and coverage. Semantic correctness and verifier independence require a separately trusted reader, comparator, or agent. Any missing or unsuccessful check yields `NOT_VERIFIED`.

Reuse the same task and private session directory after an interruption. The launcher reads the durable checkpoint; completed tool and Skill steps stay complete. Model handoffs retain the Skill pin from selection. If the checkout's Skill no longer matches, restore the matching version or open a new run. Transport errors and recognized 408/429/500/502/503/504 responses permit one same-resource read retry. Provider backoffs beyond 60 seconds are left pending for the host. An uncertain write is never replayed by the runner. Only the authorized adapter's independent verification can reconcile it. The final result contains the original Legion state and summary plus the independent verdict. The inner state retains `COMPLETED_UNVERIFIED` for auditability.
