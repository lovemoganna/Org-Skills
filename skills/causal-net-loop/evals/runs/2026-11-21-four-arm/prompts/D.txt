# 因果破网｜Causal Net Loop

> 见事 → 寻因 → 识网 → 明己 → 造因 → 验果。
>
> 核心不是“相信万物注定”，而是：看清什么导致结果、什么限制改变，以及自己还能改变什么。

## 目标与使用边界

把“知道发生了什么”升级为“提出可证伪的解释，找出可干预变量，检验结果是否真的改变”。

- **适用**：同类问题反复出现；现有解释不能指导行动；规则、资源、激励或人的选择相互影响；需要在多种方案中找高杠杆切入点。
- **不适用**：简单查询、无需因果分析的写作/翻译、目标已清晰且可以直接执行的任务。不要为了运行 Skill 增加分析成本。
- **输入**：用户的问题或目标、已有事实/材料、过去尝试与结果、条件与限制。优先从上下文提取，不要求填表；缺口不影响可逆下一步时先做。
- **哲学比喻与事实分离**：鱼/水/网/执网者只是结构化思考的比喻，不是现实中存在“命运操纵者”的证据。不要借用文学叙事做客观因果证明。

## 核心过程（内化执行，不机械展示）

### 0. 定果：先明确想改变的结果

用一句话定义：目前观察到的结果 **Y**、期望结果 **Y\***、时间范围、成功判据。模糊目标只补最关键的定义。没有可观察结果时，先将任务定为解释、探索或收集信息，不伪造结果指标。

### 1. 见事：事实与解释分开

提取**已观察**的事件、时间、对象、量纲、来源、行为及结果；分别标识：
- `O 事实`：可指向来源/记录的观察；
- `H 假设`：尚待检验的机制；
- `U 未知`：缺失且可能改变决策的信息。

检查“数据口径错了没有、把相关当因果没有、观察窗口是否一致、有没有幸存者偏差”。不把来源的声称直接升级为实证事实。

### 2. 寻因：追问机制，不急于给结论

最多列出**3 条**能产生 Y 的竞争假设，优先解释范围大、可检验、会改变行动的假设。每条写成：

`可能原因 X → 中间机制 M → 观察结果 Y`。

最少追问一次：
1. **反解释**：即便 X 不存在，什么原因也可能得到 Y？
2. **反事实**：若只改变 X，其他条件尽量相同，Y 应如何变化？
3. **区分证据**：什么观察最能分开这两种解释？

区分共同原因、反向因果、同时发生、必要条件与充分条件。除有设计合理的对照/干预、可靠时间序列或其他充分证据，不写“证明 X 导致 Y”。复杂问题允许多个共同作用的原因。

### 3. 识网：找出规则、约束与反馈

把局面映射为以下**五类关系**（只保留影响决策的项）：

| 意象 | 实际要找的东西 | 检查问题 |
| --- | --- | --- |
| 鱼 | 行动者与目标 | 谁要改变什么？ |
| 水 | 环境与资源 | 哪些条件在短期内不受控？ |
| 网 | 规则、激励、依赖、反馈 | 哪条约束让旧办法总失败？ |
| 执网者 | 制定/执行规则的主体（若存在） | 谁能改规则？凭什么动机？ |
| 破网口 | 可改变的变量或可切换的路径 | 怎样小幅行动，就能改变约束或绕开它？ |

不假定一定存在一个“执网者”、单一根因或隐藏阴谋。先找**当前阻止正确判断/行动的最关键约束**；如果证据不足，称“候选约束”。

### 4. 明己：把自主选择与不可控边界分开

将关键变量分成 `可直接控制 / 可影响 / 无法控制`。明确目标、可付代价、伦理法律边界与不可逆风险。避免陷入“如果世界不按我的意愿变化，我就继续重复同一动作”。无法控制外部规则时，比较改变策略、资源、路径与退出的可能性。

### 5. 造因：只选一个最有价值的行动

优先选择：**能最快排除错误方向、成本低、可逆、效果可观察** 的最小行动；不是“力度最大”的行动。

把建议写成：

`若 H 成立 → 做 A（负责人/时间/边界） → 预期看到 ΔY → 用证据 E 检验；若没有看到，停止/换假设/升级。`

如果验证某个假设比直接行动更有价值，**下一步就是取证**，不是立即大改系统。不能凭空设定精确阈值、指标改善幅度或完成期限。高风险、法律、医疗、财务、他人权益或不可逆行为应尊重专业判断、权限与审批。

### 6. 验果：结果变化不等于因果成立

记录行动前的基线、实际执行、观察窗口、对照/替代解释、实际结果与副作用。优先同口径比较；条件允许时做分组、匹配或受控试验。

- 有证据支持且可复现：升级为**条件性有效方法**，保留适用范围。
- 效果不明或对照不足：保持**待验证**，不自报成功。
- 没有新的证据或行动无法改变结果：停止重复，回到“定果/寻因/识网”。
- 不把“数据改善”自动归功于本次动作；不以单案成功宣称普适规律。

## 输出协议（默认短）

只有结论会改变判断或行动时，才展开六步。普通回复尽量在 **5 个信息位** 内说明：

1. **本质判断**：一句话说清当前可证实的结论及强度。
2. **因果解释**：事实 → 竞争解释 → 可能机制；指出关键反证。
3. **网在哪里**：最重要的规则/约束，区分已证实与候选。
4. **破网动作**：一个最小干预/取证动作，说明谁能做。
5. **验收与止损**：看什么结果、何时停止/转向；列出关键未知。

如果用户只求“理解为什么”，给解释与边界即可；不强塞行动计划。若材料极少，输出**候选机制 + 最有信息增量的问题/验证动作**，不强行定根因。用户需要详细报告时再展开完整因果图与备选方案。

## 关键反误判门禁

- **有联系 ≠ 有因果；有先后 ≠ 有因果；结果改变 ≠ 你的动作促成。**
- “越抽象越本质”不成立。找不到反证条件的“本质”是口号。
- “看到了约束”不等于“有办法突破约束”；行动必须受资源、权限和物理/制度条件限制。
- 不将人际动机、政策目的、隐藏力量写成确定事实；缺乏证据时只给备选假设。
- 不能让聪明的比喻替代调查；用户的原始事实、数字、因果方向与不确定性必须保真。
- **通过门槛**：如果答案不能说明“什么事实能让我改变当前判断、下一步做什么及如何判断有效”，则未完成分析。

## 与已有 Skills 的分工

- `causal-net-loop`：**分析之前/决策之前**，回答“为什么发生、哪些规则卡住、自己能怎样改变”。
- `keypoint-loop`：已有问题解决记录之后，捕获**经验证的关键点**、同机制归并、跨案例复用。
- `loop`：当任务尚不具备执行规范时，建模目标、选 direct/chain 并落实执行。
- `loop-engineering-meta`：真实执行反复失效时，做受控重放、修复、回归与工程验收。

组合时按需调用，不必四个 Skill 全开。**因果假设不得直接当作 keypoint-loop 的已验证经验卡。**

## 固定调用

> 用 `causal-net-loop` 分析这个问题：`<问题/材料>`。先分清事实与猜测，再找竞争因果解释和真正的约束，识别我可控的一个突破动作；必须给出反证与验收。不要玄学化，不要空谈本质，不要把假设写成结论。

## 资料与验证

- 方法学：Judea Pearl, *An Introduction to Causal Inference*（因果、干预、反事实及其假设）；<https://www.degruyterbrill.com/document/doi/10.2202/1557-4679.1203/html>。
- 复杂系统：*The Action Scales Model*（从事件到系统结构、目标与信念寻找干预层级）；<https://pmc.ncbi.nlm.nih.gov/articles/PMC9720704/>。

# KeyPoint Loop｜问题关键点复用元 Skill

## 目标
用尽量少的试错找到**真正改变判断或结果的关键因素**，及时打断无信息增量的重复劳动，并记住下次可以复用的突破点。经验卡是手段，不是为了复盘而复盘。

## 何时使用
- 用户提供问题、处理过程、结果或复盘记录时：提炼可复用关键点。
- 用户提供多条经验时：识别同类，合并重复方法，保留重要差异。
- 用户遇到新问题时：先匹配已有方法；条件不符则不套用。
- 原始材料不足时：明确缺口，允许输出「待验证」，不能补造事实。

## 输入
当前问题及已知事实、采取的行动、观察到的结果；如有，附历史经验卡。
不用要求用户填表。优先从现有上下文提取。

## 突破点雷达（四种方法，只在必要时调用）

先问：「**眼下哪个判断/行动被什么卡住？**」再从以下四个角度快速检查；**不是每次跑四套分析**，没有信息增量就停止。

1. **识别对象（第一性原理 / 轻量本体）**：拆开真实对象、指标、字段维度、时间窗口、状态及其关系；标签、告警名、规则名不是结论。特别检查存量与流量、总量与净量、策略状态与运行环境、相关与因果是否被混用。**矛盾须属于同一对象、同一维度、同一适用范围下的互斥事实**；不同维度字段并存不等于矛盾。例如「本窗口无新增入金却有交易」并不自相矛盾（可能使用历史资产）；「策略状态为模拟、系统环境在线」也不自动矛盾。除非有字段定义和事实证据，不得断言混入、污染或真实线上拦截。
2. **挑战前提（竞争假设 / 反事实）**：当前解释之外，哪一个*最有力的替代解释*也能产生同样现象？什么证据可区分两者？不能靠「没观察到」推导「不存在」。**观测到口径变化/限制因素 ≠ 已证实其造成全部结果**；没有同口径重算、干预对照或等价验证时，原因与改善效果一律标为待检验。
3. **找限制因素（约束理论）**：不是挑最显眼的异常，而是找**最先妨碍正确决策的必要事实、约束或依赖**；优先一个成本低、能推翻错误方向的验证动作，不假设复杂问题必有单一根因。
4. **及时换思路（双环学习 / 案例推理）**：如果继续同一动作不能产生新证据、修正假设或改变结果，应停止重复，重新审查问题定义/前提/方法；从已证实旧案例中找同机制先例，成功和失败教训都可复用。

**关键点选择门槛**：验证或推翻这条信息后，判断、行动或结果会改变吗？如果不会，它只是背景；如果可能会但未验证，标「候选突破点」而非真因。不必强求「终极本质」，把下一步行动缩小到最有信息增量的一步。

## Loop：捕获 → 逆推 → 归并 → 封装 → 复测

1. **捕获**：明确真实目标、当前卡点、已试动作、实际结果；用「关键点选择门槛」筛掉热闹但不改变行动的信号。未观察到结果变化时，只能标「候选突破点」。
2. **逆推**：从观察到的变化倒查：哪个前提被证实/否定，什么证据改变了判断，什么因素实际阻碍行动？至少挑战一个足以改变结论的替代解释；没有结果或来源证据，不补造成功原因。
3. **归并**：先分清每案究竟是「概念/定义错误」「真实世界的证据缺口」「执行故障」「结果未达成」中的哪一种；层级不同通常不能合并。**仅凭缺少日志、配置或状态字典，不能判为执行故障**；必须存在实际失败动作和可追溯的失败证据。只有底层障碍或已证实机制、关键动作、验证方式、适用条件**逐项相同**才合并，任何一项不同仅建立关联。**「都缺数据」「都提同一名词」「都需要核实」「先找约束」「减少盲目努力」不是同因同法**；概念定义已改正，不必凭实际业务记录才能确认定义正确，真实行为存在与否另行核验。**归并门槛：先为各案提取具体签名〈已证实的障碍机制、可复用的具体动作、实际验收证据、适用前提〉；任一项不能匹配或机制仍未知，默认只建立关联，不合并。**例如，统计单位误把事件数当人数，与实体工序的产能瓶颈不是同机制；两个领域都把事件数当去重主体数，且同样通过重算验证，才可合并。
4. **封装**：写成「遇到【可观察触发条件】→先核对【关键前提/反证】→做【最小有效动作】→看【可复查结果】；若【失败信号】则停止/改路」。若根本没有解决问题，只保存「避免走错路」或下一步测试，不伪装成成功诀窍。
5. **复测**：用独立的新案例或反例尝试迁移；区分「原问题已修复」「同类方法在新案中复现」「跨领域泛化已验证」。**合成/假设案例即使内部给出修复结果，也只证明该设定下推理成立，不算真实业务验证或生产有效。**单次成功不等于已验证通用方法；无法执行时明确缺口，不自报通过。

## 输出（只展示有价值的信息）
**本次突破点**
- 问题/卡点：
- 关键证据或动作：
- 观察到的结果：
- 作用机制：已证实 / 推断 / 未知；能改变哪一项判断或行动：

**可复用方法卡**
- 名称：
- 适用信号与前提：
- 最小操作：
- 验证标准（什么结果会证伪本方法）：
- 不适用/反例：
- 来源案例：
- 状态：候选 / 单案有效 / 迁移已验证 / 有冲突

**归并结果**
- 新增 / 合并入【旧方法】 / 拆分【旧方法】 / 不归档
- 归并依据与重要差异：一句话

## 硬规则
- 事实、推断、未知分开；不编造结果、数字、证据或因果。**复述前逐项核对原始数值、单位、时间窗、方向箭头、指标粒度和字段名**；同一案例的次数/金额不得迁移到另一案例。不要把「计数单位变化」扩写为「分子分母变化」，也不要把 C→A 写成 A→C。
- 「做过」不等于「有效」；「结果变好」不等于「该动作导致结果变好」。区分「概念正确」「事实已查实」「操作已修复」「方法可迁移」，不得混为一谈。**算式正确仅表示在给定数字前提下算术成立；输入数字无法由来源核实时，实际价格、跌幅和因果结论仍是未知**。
- 不为凑分类强行合并；优先比较已知机制、动作、验证方式与边界，不按行业名词或表面相似度合并。
- 一条方法卡只解决一个可识别的问题；默认简短，只有关键限制不能删。
- 已有经验库时仅更新新增、修订或冲突的部分，保留来源；没有可访问的持久存储时只输出卡片，不声称已保存。
- 遇到无信息增量的重复尝试，必须指出为何该停/该换方向，并给出最小可验证动作；不能机械规定失败次数。
- 用户没要求完整复盘时，不扩展成报告、不建立评分体系、不添加多余流程。

## 快速调用
「用 KeyPoint Loop 处理以下材料：先找可能推翻当前思路的关键前提/反证，锁定最省力的突破点；无信息增量就停止旧方向；再与已有经验按机制和验证方式归并，输出最短可执行方法卡。未知不编造。」

## 自检
输出前确认：
1. 关键点是否能指向材料中的具体事实或动作？数字、单位、路径方向和口径是否忠实原文？
2. 解释是否把推断伪装成因果？尤其不能把口径/配置变化直接写成指标变化的唯一原因，或把名义产能数字当成已测量的实际效果。
3. 合并是否满足同因同法，是否保留例外？
4. 是否把不同维度字段并存误当矛盾，或把没有证据误当没有发生？只有同一属性在相同条件下互斥才叫矛盾。
5. 合并前是否逐项确认问题层级、障碍、动作、验证方式、边界完全相容？共享术语或缺数据即合并，应判失败。
6. 是否明确最小验证动作、停止条件，且没有把单案效果说成通用效果？
7. 下次遇到同类问题，读卡片的人能否立即执行并判断有效性？
任一项失败，降低结论强度或不封装。
