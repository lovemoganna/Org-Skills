# 笔记形态参考

先判断原文属于哪类,再决定骨架。骨架是起点,不是模板,混合型就混合。

## 提示词 / 模板合集

- 开头:"我现在的情况 → 用哪条"的入口表。
- 每条:适用情形、逐字提示词(代码块,填空处用 [ ])、记录过的效果、不适用情形。
- 同一提示的多个长度版本合并为一条,按"多版本的处理"规则保留。
- 反复重发的同一症状收成一个条目,记录"提了几次、措辞怎么变";没记结果的写成缺口。
- 被作者评价为差的提示保留为反例,附评价原话。

## 操作手册 / Runbook

- 开头:什么时候用、前置条件。
- 主体:步骤,每步写预期结果与出错时看哪里。
- 末尾:回滚、已知坑、验证方法。命令、路径、参数逐字保留。

## 排障记录

- 以"症状"为标题。每条:症状 → 已试过的 → 有效/无效 → 根因(确认过的与推测的分开)。
- 未解决的保持未解决,不补结论。

## 决策与复盘

- 当时的情境和约束、备选方案、选了什么、为什么、后果。
- 没写后果的,写成缺口,不替作者推演。

## 学习笔记 / 概念笔记

- 以"想弄懂什么问题"开头。写出概念之间的关系(谁依赖谁、谁和谁易混)。
- 作者自己的例子和类比必须保留。易混点单列。

## 专家文章 / 博客(仅用户明确要求)

- 先确定一个中心问题或中心判断。全文只服务这一条主线;原材料是证据,不是文章目录。
- 推荐的自然推进是:提出判断或问题 → 解释底层机制 → 用必要事实/案例支撑 → 写清边界或权衡 → 得到更高一层结论。这个顺序是叙事逻辑,不是固定章节模板。
- 技术主题优先解释系统机制、状态变化、依赖关系、反馈、权限、隔离、约束、权衡和失败条件。不要用更多术语代替更深分析。
- 来源身份只在事实归属和证据边界需要时出现。不要反复用“讲者提到 / 报告指出 / 原文表示”推动全文。
- 作者分析可以比来源更进一步,但必须由来源事实或可靠通用知识支撑。自行归纳的术语、框架或分类必须明确说明不是来源官方分类。
- 标题只做导航。优先使用短的对象、概念、机制或问题;解释、因果和完整结论放正文第一句。
- 表达遵循“深度来自思考,不来自表达复杂度”:短句、明确主语、主动语态、一句一个主要意思、术语一致;删除无信息增量的衔接和强调。
- 用户明确要求双语时:标题写成 `中文 | English`;每个中文完整段落后立即接等价英文,放在同一段内。中英文的事实、数字、判断、限定、证据边界和结论必须 1:1 对等。
- 用户没有要求双语时,不得为了“国际化”自行增加另一种语言。
- 长材料必须主动取舍。优先保留能证明中心判断的事实、机制、案例、反例和边界;快捷键、临时 UI、版本细节等与主论点无关时压缩为必要补充。

## 阅读 / 资料笔记

- 作者观点和摘录分开,引文不改一字。保留页码、链接、出处。
- 补"这条资料能回答我什么问题"。

## 项目 / 系统笔记

- 当前状态、关键决定、已知问题、下一步。路径、仓库、环境、依赖版本逐字保留。
- 过期信息不删,标注原文日期。

## 教程 / 实验记录(带可执行代码和执行结果)

- 开头:环境记录和证据状态。哪些块有执行结果,哪些只有预期值,哪些被标阻塞,分开说。
  标题和导语不得强于这份状态。
- 主体:按"我想做什么"组织,每个能力保留代码块和结果记录。
- 末尾:验证方法与矩阵;"症状 → 先看哪里"。
- 不同环境、日期的执行记录分别标注。出处原文没写就写"我没记"。
- 与教程本身无关的维护台账、工具链过程日志,拆出去。

## 系列笔记(多篇有分工、互相回链)

- 默认每篇各出一份下一版,保留分工,更新彼此链接(改成 CUSTOM_ID 链接)。
- 系列已有入口篇就沿用,在入口里放全系列的"我遇到什么 → 去哪篇";没有才新建索引。
- 每篇自己再放一份本篇范围内的"症状 → 先看哪里"。
- 绑定文件名的脚本、配置,在回复里点明需要同步。
- 合并是用户明确要求时才做。
