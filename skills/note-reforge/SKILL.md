# Note Reforge:把旧笔记炼成下一版

## 立场

原文是原料,不是模板。你替作者把这个主题重新想清楚,
再以作者本人的口吻写成一篇三个月后带着具体问题回来就能直接用的笔记。

验收只有一条:**三个月后作者带着问题回来,读新笔记能用上,而且明显比原文好。**

其余规则都是手段。

## 固定极简调用入口

当用户只输入 `用 note-reforge 炼成下一版：<文件 / 目录>` 时，视为完整调用，不要求用户重复粘贴 Skill、解释规则或确认默认流程。

- `<文件 / 目录>` 就是本次处理目标；单文件、多文件和目录如何处理，继续由本 Skill 当前规则判断。
- 调用口令只负责触发，不承载执行规则；以后本 Skill 升级时，调用方式保持不变。
- 通过插件或其他 bootstrap 触发时，入口必须先读取 `lovemoganna/Org-Skills` 默认分支当前的 `skills/note-reforge/SKILL.md`，再执行目标。
- 本文件是唯一 canonical Skill。入口不得用内置旧副本覆盖本文件，也不得在读取失败时静默回退到旧规则。
- 只有目标或 canonical Skill 实际不可访问时才说明阻塞；不得为了默认流程再次向用户确认。

## 指令优先级

1. 用户当次的明确指令,优先于本 Skill 的任何默认做法。
2. 用户没说的事,走默认做法,并在回复里用一句话说明选了哪个默认。
3. **不得声称用户给过他没给的指令。** 用户说"可以""继续"时,只对应他刚被问到的那件事,
   不要引申成别的授权。意图不清就按默认做,并在回复里说明,不要替用户编出一条指令来支撑自己的选择。

## 输入与输出

- 输入:一个或多个 `.org` / `.md` 文件,或一个目录。
- 原文只读,不修改、不覆盖、不移动。
- 输出:新文件。用户给了路径就用;没给就写在原文件同目录,
  文件名 `<原名>.next.<原扩展名>`(多篇合并用主题名)。
- 没有文件系统权限时:不假装已写入。每个文件先写目标文件名,再直接输出全文。
- 格式沿用原文。

### 回复只写两样

1. 文件路径(或"全文如上")。
2. **会影响使用的事项**,每条一句话:被打破或被更新的依赖、拆出去的段落、
   本来就失效的链接、必须由用户确认的缺口、选了哪个默认。

回复里不放自检表、对照表、"已解决"清单,不自评,不复述做了什么,不评价原文。
文件头、状态词、表格依据这些检查在交付前内部做完,不对外汇报。

## 合并、系列与拆分

- 回答同一问题、内容重叠的多篇:合并成一篇。主题不同的:分开。拿不准:分开。
- **有分工的系列不是"同主题重复"。** 信号:各篇职责不同;互相回链;
  有脚本或配置绑定文件边界;作者写了"入口 / 前置 / 延伸"之类的关系说明。
  默认做法:每篇各出一份下一版,保留分工,更新彼此链接。
  - 系列里已经有入口篇的,沿用它,把全系列的"我遇到什么 → 去哪篇"放进去;
    没有入口篇才新建索引文件。不要为了形式再造一个入口。
  - 用户明确要求合成一篇时,才合并;回复里点明被打破的依赖
    (哪些 `file:` 链接失效、哪个脚本绑定了旧文件名)。
- **文件内的异主题段落**(例如一篇教程里夹着"维护生成这篇教程的工具的台账"):
  拆成单独文件,主体只留一行指针,并在回复里提一句。
- **链接**:文件改名或合并后,所有指向它们的 `file:` 链接必须更新。
  `::*标题` 这类按标题文字匹配的链接,改成 `CUSTOM_ID` 链接
  (在目标标题下加 `:PROPERTIES: :CUSTOM_ID: xxx :END:`)。
  更新前先核对原链接本来是否有效(例如目标标题的文字是否真的存在);
  本来就失效的,修好并在回复里说一句。

## 文件头与体例

- Org 文件头(`#+title`、`#+subtitle`、`#+filetags`、`#+STARTUP`、`#+OPTIONS`、
  `#+DESCRIPTION`、`#+property`、`#+WIKI_ID` 等)逐项保留原值,包括大小写和写法。
  只允许改标题文字(改成面向问题的写法)。原文没有的项不要凭空添加。
- 一篇出一份的,文件头逐项照抄。合并多篇时,`#+filetags` 取并集,
  其余项保留主文件的,并在回复里提一句有冲突的项。
- 作者关于笔记体系的约定(链接策略、命名、回链规则、"不硬编码某某字段"之类)保留一句。
  合并或改名后失效的,在原处写明"不再适用",不要悄悄删。
- 交付前逐项对照原文文件头;没核对过,就不要声称"已保留"。

## 工作方法

### 一、读

通读,先不动笔。心里回答五件事,不写进输出:

1. **作者当时在对付什么麻烦?** 标题常是名词,驱动力是问题。
2. **哪些东西换人写不出来?** 踩坑、实测结果、项目名、路径、数据、参数、命令、URL、
   术语、作者对效果的原话评价。这些不可再生。
3. **同一个意思出现几次?** 反复出现说明作者在反复碰同一个问题,
   这本身是信息:收成一个判断,并保留"出现过几次、措辞怎么变"。
4. **哪里冲突,哪里有空洞,哪里是版本漂移?**
   冲突:相反的做法或偏好。空洞:提到了但没交代结果、前提、适用条件。
   版本漂移:同一事物在不同日期、环境、版本下数值不同,不是观点冲突。
5. **证据强弱。** 哪些结论有执行记录,哪些只是预期值或文档说法,哪些被作者标了阻塞或未验证。

### 二、想

- 设想作者三个月后会带着什么问题回来,写下 3~7 个具体问题
  ("同一个 bug 提了三次还没好怎么办"优于"调试方法")。
- **先判断原文已经有多好。**
  - 原文零散、按时间或心情堆放:围绕问题重新搭结构。
  - 原文本来就按问题组织、判断充分(例如已有入口、症状表、契约和回归):
    保留它的骨架和顺序,不为重组而重组。增量放在:入口与症状索引、证据状态、
    边界与失效条件、默认选择建议、被漏掉的排查假设。
- 按内容性质选形态,见 `references/shapes.md`。
- 最常被查、最能直接动手的放前面,背景和待确认放后面。

#### 控制膨胀

升级不等于扩写。

先判断原文的信息密度和用途:

- 原文已经短、清楚、可直接使用:优先保留体量,只增强判断、边界、检索和行动入口。
- 原文零散、重复、难查:才允许明显重组或扩展。
- 新增内容必须解决一个原文真实存在的使用问题;只是"可以讲得更完整"的内容不要加。
- 不为了体现加工深度而增加章节、分类、方法论或解释。
- 一个判断能用一句话解决,就不要扩成一节。
- 新版本明显变长时,必须能回答:新增的每一部分未来具体解决什么问题。答不出来就删。

默认原则:**最小必要升级。能通过压缩、重排和补一条判断解决,就不要扩写成完整方法论。**

#### 炼化内核:三魂七魄

这是**内部认知检查**,不是输出模板。不得为了套模型把新笔记写成“三魂”“七魄”十个章节、表格或标签。

**三魂决定有没有真正形成知识:**

1. **本体:** 这份材料真正处理什么问题?核心对象、变量、目标、约束是什么?
2. **机制:** 对象之间如何作用?哪些是依赖、因果、条件或传播关系?哪些只是同时出现的现象?
3. **判断:** 从事实和机制里能推出什么可迁移的选择规则?尽量写成“什么条件下 → 选什么 → 为什么”。

**七魄保证知识还能落地和被核验:**

- **事实:** 不可再生的原始材料必须保留。
- **证据:** 结论强度不得超过来源、实测或记录的强度。
- **结构:** 把对象、属性、关系、层级和条件连起来,不只做分类。
- **边界:** 写清成立前提、适用范围和失效条件。
- **冲突:** 先判断是事实冲突、环境差异、版本漂移还是目标不同,再决定并列或解释。
- **行动:** 把判断落到下一步动作;没有行动价值的背景不因“完整”而补。
- **检索:** 从未来会问的问题反推标题、入口和组织方式。

内部炼化顺序默认是:**事实 → 本体与关系 → 机制 → 判断 → 行动 → 反查证据与边界**。
缺任何一环都可以保留缺口,不得为了闭环而编造。

对本来就写得很好的教程、概念笔记或资料笔记,**不要把“保留原结构”误解成“只做同义改写”**。
优先寻找原文已经提供、但尚未被压成明确关系的知识增量,例如:
依赖关系、因果链、决策分界、失败条件、易混概念之间的区别。
如果提炼不出真实增量,就保持最小修改;不要用更多文字伪造升级感。

任何新增机制或判断都必须满足至少一条:
- 能直接回指原文事实或多个原文事实之间的关系;
- 属于可靠的通用专业知识,并按本 Skill 的规则标 `〔补〕`。

### 三、写

**口吻。** 用作者本人的第一人称写。禁止"原文说 / 原文没写 / 原文标注 / 笔记未记录"这类审读口吻。
作者没记结果,就写"我没记结果",且只在有必要时写一次。

**判断。** 每个方法说清:什么情况用、什么情况不用、为什么。
保持来源强度:作者"试过一次觉得不行"不能写成"应避免";一次尝试不是结论。

**敢给建议。** 作者自己的判断很少时,"青出于蓝"主要来自你补的东西:
怎么选、先做什么后做什么、冲突时的默认读法、排查假设、适用边界。
给出带理由的默认建议,不要整节退回"原文没写"。只写你能为之负责的内容。

**结构。** 需要重组时按问题、场景、决策组织。复杂笔记开头给"我遇到 X → 去哪节"的入口表,
再加"症状 → 先看哪里"。短而清楚的轻量笔记不强制增加入口表或额外章节。
章节之间有因果脉络,不是并排罗列。

**可操作。** 提示词、命令、步骤、模板、代码要能直接复制。
原文的提示词、命令、代码块、配置**逐字保留**并放进代码块;需要填空处用 `[方括号]`。

**边界。** 写明适用范围、前提、失效条件、风险。

**检索。** 标题和小节名用未来会想起的说法:症状、场景、报错、项目名、工具名。

**改成表格或清单时。** 每个格子都要能在原文找到依据:

- 原文没说的格子,整列不要或留空,不写"未记录"。
- "是 / 否"类的格子核对语义,不同维度分开列。
- 宁可用短句列表,也不要一张半空的表。

**状态不拔高。** 标题、副标题、导语、小节标题里的状态词
(实测 / 已验证 / 通过 / 已解决 / 稳定)不得强于正文里最弱的证据。
有些块有执行结果、有些只有预期值,就如实分开说。

**执行记录的出处不推断。** `#+RESULTS:`、日志、版本号,原文没写它来自哪个环境、哪一天,
就写"出处我没记",不要根据版本号或路径推断后写成事实。
环境或日期不同的记录分别标注,不合成一个结论。

### 四、收:交付前内部过一遍

1. 拿第二步的那几个问题"查"新笔记:30 秒内能找到答案并直接用吗?
2. 独有素材都在:代码、结果记录、命令、URL、路径、原话评价。
3. 文件头、体例约定逐项对照原文。
4. 链接全部可达:`file:` 指向新文件名,`CUSTOM_ID` 都存在。
5. 描述原文位置、顺序、次数、先后关系的句子,逐句回原文核对;核对不了就删或按推测标注。
6. 标题、副标题、导语里的状态词逐个回原文核对。
7. 每个新增表格逐格核对依据。
8. 标记清理:一个判断最多标一次。
9. 回复只剩路径和影响使用的事项。

## 保留什么

以下原样带入新笔记,位置可以重排,不可丢弃、不可概括:

- 亲历的案例、症状、失败记录、对效果的评价原话
- 数据、参数、版本、日期、路径、命令、配置、`#+RESULTS:` 里的执行记录
- 提示词、模板、代码块(逐字)
- URL、文件路径、工具/技能/命令名,以及应用特有的链接语法(原样)
- 作者的术语和命名
- 作者表达过的不确定、阻塞、未验证状态
- 文件头与体例约定

**多版本的处理。** 同一内容有长短几个版本时:

- 保留最完整的一版,逐字。
- 短版若与完整版差异多于共同点(少了一半以上的内容,或另有独有条目),直接逐字保留短版。
- 短版只是完整版的子集时,才用一两句列出它少了什么、多了什么,必须列全。
- 提示词整段只放一处,别处写"见某节"。

## 冲突与并列

冲突并列保留,各写各的出处和场景,不选边、不折中。
然后给出你的默认读法(标一次〔补〕),同时明说作者没给调和方式。
版本漂移不当作冲突:按环境和日期分别记录。

## 补充与编造的界线

可以补:通用专业知识、你有把握的判断、对空洞的追问、排查方向、默认选择建议。
不可以:编造作者的经验、实测结果、项目事实、数据、引用、链接;
把推测写成事实;替作者补出他没记录的结论。

**补代码和命令要更严。** 只在同时满足两条时才写成可复制的代码:
原文已经精确描述了它的行为;它不引用任何未定义的函数、变量或文件。
不满足就写成步骤描述。

**标记只有一种:〔补〕**,表示"这条是整理时加的,我没在项目里验证过"。

- 整个小节都是补充内容,在小节标题上标一次,正文不再逐句标。
- 作者原话里的不确定,直接转述,不加标记。
- 不设"AI 区",不全篇铺标记。
- 没结果的地方写进末尾"待确认",**只留会影响使用的缺口,最多 5 条**。

## 常见失败方式

- 写成摘要、润色版、文章、审读报告。
- 抹平冲突;把版本漂移当冲突。
- 经验升格为原则。
- 该给默认建议时退回"原文没写"。
- 新造框架名、分类法、成熟度模型。
- 丢素材:链接、路径、命令、项目名、文件头、体例约定、`#+filetags` 里的词。
- 标记满天飞。
- 描述原文位置/顺序时凭印象写。
- 状态拔高:标题写"实测",正文是"阻塞"。
- 推断执行记录的出处。
- 表格改义:一格塞多个维度,或编出"未记录"的格子。
- 把有分工的系列当重复内容压成一篇,或为已有入口的系列再造一个入口。
- 异主题段落留在主体里。
- 改名或合并后留着指向旧文件的链接。
- 补了跑不通的代码。
- 编造用户没给过的指令。
- 回复里附自检表。
- 膨胀:加不属于这个主题的内容;重复整段提示词;为了"重组"而打乱本来就好的结构。
- 把"升级"做成"扩写":原文已经短而清晰,却为了显得更完整新增大量章节、解释和方法论。
- 过度结构化:为了入口表、分类和标题而增加比原文本身更高的阅读成本。
- 高质量原文只被换标题、调顺序、同义改写,却没有形成新的关系、机制、判断或使用边界。
- 把“三魂七魄”直接渲染成十个输出章节,让内部思考框架反过来增加阅读成本。

## 格式细节

- Org:代码块用 `#+begin_src ... #+end_src`;块内以 `*` 开头的行用 `,*` 转义
  (原文已转义的保持原样);行内代码/路径用 `=...=`;表格对齐;
  层级不超过必要深度;站内跳转用 `CUSTOM_ID`。
- Markdown:围栏代码块标注语言;不用 HTML。
- 语言和语气沿用作者。不用 emoji、装饰分隔线、流程图、评分或检查清单。
- 敏感信息(密钥、令牌、密码)不带入新笔记,用 `[已省略:密钥]` 占位,并在回复里提醒一句。
- 原文有明显的粘贴残留或笔误时,保留其中有用的信息,用一句话说明,不要悄悄删。
