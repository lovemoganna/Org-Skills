## 同一问题的 A/B

问题：一次计划任务完整读取所有来源，但用户约定“无重要新增就不通知”。是否需要 Slack 回执？能否推进 bookmark？

A（失败）：在一处补充“无发送也可推进进度”，却保留上文“先 Slack 成功再提交进度”“两条确认链依次成立才完成本轮闭环”，以及只覆盖四种状态的表格。这使同一输入获得冲突指示。

B（条件成立）：保留官方“需要发布时必须取得 Slack 成功回执”；另列独立的无发布分支，要求先保存完整读取和不发送决策，然后仅推进成功来源 bookmark，不新增 ledger 已发布记录。流程、确认链、状态表、使用说明、验收段落不得互相矛盾。**最终发布版维持原有四分支表和历史标题不变，把静默情形放在表后单独说明**；不能再使用旧测试稿“五种分支”的标题。

## 对抗性反例

1. Slack 结果未知：仍是 `maybe posted`，不先假定失败并重发；不能将无发布分支用于替代不确定的真实发布。
2. 一个来源不可读：不推进该来源 bookmark，也不报告“无新增”；其余来源可按读取和发布契约处理。
3. 事件迟到且没有有限的重读窗口：不能因为时间戳加稳定 ID 就保证没有漏读；必须保留覆盖缺口。
4. 来源未来支持更严格的游标机制：优先采用真实来源保证，不能机械重叠读取所有事件。
5. 已发布原文件的身份字段、全部 `CUSTOM_ID`、原始代码块、出处、配图和路径逐字保留。

## 质量裁决

静态检查能证实不同章节关键文本已被同步更新以及资产完整；不能证明目标读者实际更容易独立执行。本用例仍需独立盲读或真实任务复现，才能升级为“内容效果已验证”。若只是换词而没有修复跨章节条件冲突，判失败。
