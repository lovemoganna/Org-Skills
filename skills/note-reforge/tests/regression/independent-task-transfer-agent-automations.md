## 对照流程

1. 将两个完整 Org 文件匿名为 A/B，隐藏 commit、改稿说明和哪版更新的信息；保持真实文件头和原始素材可辨认，不伪造或删证据。让未参与改稿的独立读者在**不知道答案版本**的条件下，仅凭每份成品答同一组问题。
2. 每题记录读者回答、原稿中的证据位置、证据缺口、下一步动作；**不看关键词、不计字数、不凭审稿者“感觉更好”打分**。
3. 揭盲后，由不参与改稿的评审按三维评分：事实保真（0=错误或造假、1=正确但漏重要限定、2=准确完整）；条件判断（0=错、1=可判断但缺边界、2=包含适用与失败条件）；操作执行（0=无法执行、1=需要补前提、2=能说明具体下一步和停止条件）。每一分附原文位置和判定理由。
4. 若新稿任何任务的关键事实退化、出现跨章节冲突或证据虚构，直接拒收；有至少一题明显改善且无退化才可判为有可复查的内容增益。没有独立答题者的署名与记录，标「待核验」，不能报「通过」。
5. 使用 `python skills/note-reforge/tests/evaluate_task_transfer.py <evaluation.json>` 检查证据记录是否完整、评分有无退化；该脚本不阅读文章、不判定事实、也不能核验审稿者是否真的独立。

## 五个真实业务问题与正确答案边界

1. **按约定静默**：所有来源已完整读取，本轮无重要事项且用户约定不通知。不得要求虚构 Slack 回执；先记完整读取与不发送决策，再推进已完整来源 bookmark，不新增已发布 ledger；如果用户要求每天发简报，则仍走发送成功回执。
2. **Slack 请求未知**：发送超时，不能认定未发后重试；记 `maybe posted`，核对频道消息；回执不明时暂不推进 ledger/bookmarks。
3. **静默+单源故障**：不能断言“无新增”；记录该源失败并保持其 bookmark，其他完整来源按独立条件处理。异常通知必须预先授权目标频道、触发、类别和频率；无授权不发送。
4. **迟到且不可补读**：timestamp + stable ID 并不能保证漏读为零。注明历史覆盖缺口，不把本轮 API 成功冒充完整性证明。
5. **偏好变更后的追溯**：需首先确认用户要求追溯与否；回放范围与保留期由偏好规定。候选至少含稳定 ID、来源、首次读取、过滤依据、偏好版本；复核最新状态并以 ledger 去重，不能臆造永远完整的历史。

## 明确禁止的虚假成功

- 不能把模型自评、脚本 9/9、平台成功上线等同于独立 A/B 效果验证。
- 不能把没有实际答题记录的模板算作「已测试」。
- 不能仅因为新版用了上方的准确字词就给高分；评分必须按读者是否实际做对判断和行动。
