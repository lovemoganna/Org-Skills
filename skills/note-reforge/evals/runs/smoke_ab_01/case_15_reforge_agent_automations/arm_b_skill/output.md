* 核心判断与架构本质
:PROPERTIES:
:CUSTOM_ID: 核心判断与架构本质
:END:
*定时触发不等于可靠自动化。* 真正困难的不是让 Agent 每天执行，而是在数据源故障、时间错位、任务重复、消息发送不确定和用户偏好变化时，依然不漏重要信息、不误报状态、不重复打扰。

这套方案的实质是*带持久状态和外部副作用的定时任务*：

- *源数据*决定“发生了什么”；每个来源有独立读取进度。
- *用户偏好*决定“哪些变化值得打扰”；Agent 每轮重新读取，但不能修改。
- *运行状态*决定“以前读到哪里、报过什么、当前是否发送成功”；Agent 可以维护。
- *发布渠道*产生真实外部副作用；只有收到明确成功回执，才能把发送记入状态。
- *权限与预算*限制即使 Agent 误判，也能造成多大影响。

因果关系很直接：/读取进度控制完整性，去重台账控制重复，发布确认控制一致性，发送前复核控制时效性，权限隔离控制事故半径。/ 它们不能互相替代。

| 现象 | 先查的状态 | 决策规则 |
|----------------------------------+-----------------------------------+------------------------------------------------|

* 五大核心业务场景与异常处置规则〔补〕

:CUSTOM_ID: 五大核心业务场景与异常处置规则
:END:

** 场景一：按约定静默处理（无重要事项且约定不发）
:PROPERTIES:
:CUSTOM_ID: 场景一-按约定静默处理
:END:
- *触发条件*：本轮增量读取完成，无实质重要事项达到简报阈值，且用户偏好约定“没有重要变化就不通知”。
- *状态判定*：此分支属于正常业务闭环，但由于没有向外部发布消息，因此不会产生 Slack 的发布回执（=ok: true= / =ts=）。
- *处置规则*：
  1. *禁止直接丢弃或视同未执行*：必须在 =runs/<date>.md= 中先持久化本轮完整读取范围、筛选结果以及不发送的明确决定。
  2. *推进完整读取来源进度*：仅对本轮已确认完整读取的来源推进 =bookmarks.json=；=ledger.md= 不新增已发布事项。
  3. *保留候选重评线索*：若未发送事项未来可能因偏好变化重新进入关注范围，还须保留可回放的候选记录，否则 bookmark 前移会使它们后续不再自动参与筛选。

** 场景二：发送超时与未知状态（Slack maybe posted 判定）
:PROPERTIES:
:CUSTOM_ID: 场景二-发送超时与未知状态
:END:
- *触发条件*：向 Slack 接口发出发送请求后，遭遇网络超时、连接断开或未收到明确包含 =ok: true= 与消息 =ts= 的成功响应。
- *状态判定*：外部消息与本地状态写入无法做到原子操作，发送请求发出后无法确定外部渠道是否已实际展示该消息。
- *处置规则*：
  1. *严禁直接盲目重试发送*：若直接重发，在消息已实际送达时将导致同一天发布多份重复简报，造成严重打扰。
  2. *记录可疑状态*：在运行状态中明确标记为 =maybe posted=，立即暂停提交 =ledger.md= 与各来源的 =bookmarks.json=。
  3. *下轮重跑前核对频道*：下次恢复执行时，必须先主动查询目标 Slack 频道的当日消息历史，核对当日标题与 =ts=。若确认消息已存在，补齐修复 run/ledger/bookmark 记录而不再次发送；若确认未发出，方可重新执行发布。

** 场景三：单源读取故障与多源隔离
:PROPERTIES:
:CUSTOM_ID: 场景三-单源读取故障与多源隔离
:END:
- *触发条件*：某个特定数据源（如 GitHub MCP 连接中断、凭据失效或服务 5xx）不可读，但其余数据源正常可用。
- *状态判定*：“读取不可用”绝不等于“数据源无新增”。
- *处置规则*：
  1. *严禁断言“全量无新增”*：绝对不能把单源故障当作无新增事项掩盖过去。
  2. *来源进度严格隔离*：保持失败数据源的 bookmark 绝对不变，留待故障恢复后从原断点继续补读；其余读取成功的来源正常推进各自的 bookmark。
  3. *外部发布声明缺口*：若对外发布简报，必须在简报内容中显式注明该故障来源不可读。
  4. *静默与告警授权约束*：若本轮按偏好不发送正常简报，也不能把来源故障认定为“无实质新增”。应保存失败运行记录；仅当用户预先明确授权了异常通知的触发条件、目标频道与频率限制，且本轮能成功读取该授权时，才按配置发送异常告警；未获明确授权或偏好读取失败时，严禁擅自发送告警，只能保留故障记录等待人工或系统恢复。

** 场景四：迟到数据与时间戳并发（游标与缺口标注）
:PROPERTIES:
:CUSTOM_ID: 场景四-迟到数据与时间戳并发
:END:
- *触发条件*：外部数据源中存在同一时间戳的多条并发事件，或存在因异步写入、网络延迟而落在当前已读时间戳水位之前的“迟到写入”事件。
- *状态判定*：单纯的时间戳 bookmark 仅记录观察位置，无法天然保证完整区间覆盖。
- *处置规则*：
  1. *游标优先*：优先使用能够保证严格顺序与重放补读范围的原生游标（Cursor / Sequence ID）。
  2. *时间戳加稳定 ID 重叠补读*：若数据源仅支持时间戳，应采用“时间戳 + 稳定 ID”机制，每次读取向历史重叠一段安全窗口进行补读，并在消费端利用 =ledger.md= 的稳定 ID 进行去重。
  3. *显式标注历史覆盖缺口*：*若事件可能无限期迟到或数据源历史不可补读，绝对不能宣称 bookmark 已覆盖全部历史事件*，必须在状态中明确保留并标注历史覆盖缺口。严禁将“当期 API 响应成功”冒充全量无遗漏的证明。

** 场景五：偏好变更与历史追溯边界
:PROPERTIES:
:CUSTOM_ID: 场景五-偏好变更与历史追溯边界
:END:
- *触发条件*：用户在 =preferences= 中新增了关注主题、调整了排除条件或变更了汇报粒度，并可能期望对历史数据生效。
- *状态判定*：偏好是外部维护的只读单一权威来源。Agent 不得使用自身历史笔记或旧 prompt 覆盖用户最新偏好；读取偏好失败时任务必须立即停止。
- *处置规则*：
  1. *明确授权边界*：首先由用户偏好明确“仅对今后生效”还是“允许追溯历史”。不要求追溯时，新偏好仅作用于后续的增量读取与通知。
  2. *受控回溯重评*：若要求追溯，必须在来源可重放的历史范围内补读，或依据本地已持久化的未发布候选记录进行重评。候选记录必须包含：稳定 ID、来源链接、首次读取时间、当时的筛选原因以及当时的偏好版本。
  3. *重评与防重*：偏好变更后，重新读取原始对象状态，按新偏好筛选，并严格比对 =ledger.md= 防重后再决定是否通知。
  4. *期限与缺口声明*：候选记录必须覆盖已授权的回溯期限，到期才能按约定清理；若数据源无历史回放能力、未约定确定期限或记录已被清理，*必须向用户明确注明无法保证追溯完整，严禁虚构追溯能力或编造默认保存天数*。

* 一次运行的八步执行闭环
:PROPERTIES:
:CUSTOM_ID: 一次运行的八步执行闭环
:END:
无人值守运行必须严格遵循以下执行时序，保证每个阶段证据齐备：

1. *读取偏好。* 从只读 =preferences= 获取来源白名单、排除主题、消息长度、目标频道和停止条件。读不到偏好就立即停止，绝不静默启用默认设置。
2. *恢复状态。* 从可写 =state= 读取各来源 bookmark、已报告事项 ledger 和上一轮运行记录。按用户配置的时区计算当前简报日期。
3. *分别增量读取。* 每个来源从自己的 bookmark 继续；记录来源成功、失败、最后实际读取的位置。来源不可用时不要移动该来源 bookmark，也不要写成“无新增”。
4. *筛选值得报告的变化。* 标准不是“抓到多少条”，而是“是否改变读者今天的行动或决策”。已经报告但仍未处理的事项，标出持续状态；已经关闭的事项不再机械重复。
5. *发送前复核。* 对每条准备发布的消息重新查询原始来源。已解决则删除，状态改变则更新，无法验证则不作确定性报告。链接取自来源提供的正式字段，不自行拼接。
6. *先防重，再发布。* 检查目标频道当天是否已有对应简报；在运行记录中先登记准备发送。真正发布后，只接受 Slack 成功标志及消息时间戳作为送达凭据。
7. *按执行结果提交状态。* 需要发送时，Slack 明确确认后才登记已报告事项及已完整读取来源的 bookmark；发布结果不明时记录 =maybe posted=，暂停提交并先核对频道，不盲目重发。按约定不发送时，采用独立的无发布运行记录，只推进已完整读取的来源；无发送不新增已报告事项。
8. *保留运行证据。* 每轮记录成功读取的来源、读取失败、因状态无法确认而放弃的事项、发布回执、预算停止原因。

*状态提交核心准则*：有发布时先核对事实，再取得 Slack 回执，最后提交进度；无发布时先保存可复核的不发送决策及完整读取记录，再提交对应来源的进度。发布结果不明时先恢复状态，不用重试掩盖不确定性。

* 状态更新的四种分支与静默补充〔补〕
:PROPERTIES:
:CUSTOM_ID: 状态更新的四种分支与静默补充
:END:
状态推进不能只记“成功/失败”：来源读取完成、消息被平台接受、内部状态写入是三件独立的事。

| 本轮实际情况 | 对外处理 | 可否推进状态 |
|---------------------------------------+--------------------------------------+-----------------------------------------------------|
| 来源读取完整、Slack 明确确认发布 | 写入已发布事项与运行回执 | 仅对确认读取完整的来源更新 bookmark，并更新 ledger |
| 部分来源不可读，其余来源可用且发布成功 | 正常报告可用来源，并注明不可读来源 | 成功来源可推进；失败来源 bookmark 不变 |
| Slack 返回超时或发送结果不明 | 标记 =maybe posted=，先查询频道 | 暂不推进 ledger 或 bookmarks，禁止盲目重发 |
| Slack 已发送，但记录写入中断 | 用频道消息的 =ts= 与当日标题核对 | 先修复 run/ledger/bookmark 记录，不再重复发布 |

*额外分支：按约定静默。* 本轮无重要事项且偏好要求不发送、所有拟推进来源均读取完整时，记录读取证据与不发送决定；仅推进完整来源的 bookmark，ledger 不新增已发布事项。这是上述四种发布相关状态之外的补充分支。

*无实质新增时的处理契约*：先看发布契约：官方例子要求每轮发布一份注明日期的简报，此时可以发布“无实质新增”，经 Slack 确认后再提交进度；若另行约定“没有重要变化就不通知”，则没有 Slack 回执。此时先持久化本轮完整读取范围、筛选结果及不发送决定，再推进相应来源 bookmark，ledger 不新增已发布事项。若未发送事项可能因偏好变化重新进入关注范围，还须保留可回放的候选记录。

* 两条确认链：先证明读全，再证明发出〔补〕
:PROPERTIES:
:CUSTOM_ID: 两条确认链先证明读全再证明发出
:END:
*读取确认*判断本轮是否覆盖了该来源的待读取区间。API 返回成功，不等于历史已读全。比如某来源只返回最新 50 条，断线太久可能产生分页缺口；未追溯到上次 bookmark 时，不能推进该来源进度，也不能报告“无新增”。需补齐分页或显式标记该来源不完整。

*发布确认*判断外部消息是否真正被 Slack 接受。=ok: true= 和消息 =ts= 是本例的发布回执，不等于接收者已阅读。若 Slack 已确认发送，但在写入 =ledger.md= 前进程中断，下次应先从目标频道核对当日简报，再修复记录，而不是再次发送。

*确认链约束关系*：
- *需要对外发布时*，读取与发布两条确认链都必须成立。
- *无发布且依约不通知时*，以完整读取证据及不发送决策作为提交依据，不要求虚构 Slack 回执。
- 无论走哪条分支，失败来源的 bookmark 绝对不能顺带推进；无法补读的历史缺口必须在记录中明确保留。

* 两种读取失败的本质区别
:PROPERTIES:
:CUSTOM_ID: 两种读取失败的本质区别
:END:
用户偏好不可读与数据源不可读必须严格区分处置：

- *用户偏好不可读时，任务必须立即停止*：此时无法确认关注范围、排除条件、篇幅限制和发布目的地，继续运行就可能违背用户的最新授权。
- *单个数据源不可读时，可以继续隔离处理*：继续整理其他可用来源，保持失败源的 bookmark 不变；若发布简报，必须在简报中显式注明该源不可用。

二者的判断依据不是“是否出现报错”，而是*缺失的信息是否决定本轮任务的授权边界*。偏好控制什么能报、报给谁；来源只提供可核查的事实。绝不要把它们统一粗暴处理成“读取失败后使用缓存”。

* 四个容易混淆的状态认知
:PROPERTIES:
:CUSTOM_ID: 四个容易混淆的状态认知
:END:

** 1. Bookmark 不是“上次运行时间”
:PROPERTIES:
:CUSTOM_ID: 1-bookmark-不是上次运行时间
:END:
=bookmarks.json= 表示*某个来源读到哪里*，不是 cron 最后何时触发。原文给的例子按来源记录时间位置，因此迟到的运行可以补读、提早的运行不会因为固定窗口而重复采集。不同来源必须分开独立管理。

** 2. Ledger 不是原始消息存档
:PROPERTIES:
:CUSTOM_ID: 2-ledger-不是原始消息存档
:END:
=ledger.md= 记录已经向读者报告的事项、稳定 ID、来源、报告日期与最后状态。它解决“是否报过”，不是替代实时来源。某事项即使已经在 ledger 里，也必须重新确认是否仍待处理。

** 3. Preferences 不是 Agent 自己积累的经验
:PROPERTIES:
:CUSTOM_ID: 3-preferences-不是-agent-自己积累的经验
:END:
原文把 =preferences= 配成 *read-only*，由用户维护；=state= 为 *read-write*，由 Agent 保存书签、台账、运行记录、提议与来源行为笔记。不能让 Agent 的自动总结覆盖用户偏好。每轮都要读新偏好，以免旧 prompt 继续执行已撤销的要求。

** 4. 发布请求不等于发布成功
:PROPERTIES:
:CUSTOM_ID: 4-发布请求不等于发布成功
:END:
向 Slack 发送请求后，可能遇到超时、连接中断或不明确的 API 反馈。外部消息与本地状态无法简单地看作一个原子动作。原文采取务实防护：查看当天消息、防重、核对 Slack 返回值、将不确定状态留给后续核查。

*〔补〕* 这并不是严格的“恰好发送一次”保证。标题查重与本地台账之间仍存在并发竞争、查询延迟等边界。若同一任务可能并发运行，先对同一日期的发布任务做互斥或引入服务端幂等机制；不要仅凭一条 prompt 声称已实现严格 exactly-once。

* 部署依赖与操作入口
:PROPERTIES:
:CUSTOM_ID: 部署依赖与操作入口
:END:
官方示例目录 =daily-brief/= 的职责划分：

| 文件 | 职责 |
|---------------------------------+------------------------------------------------|
| =agent.md= | 模型、工具权限、运行步骤和简报筛选规则 |
| =deployment.md= | cron、时区、环境、预算、首次输入消息、内存挂载 |
| =environment.yaml= | 网络访问允许列表 |
| =memory_store_preferences.yaml= | 用户维护的只读偏好存储 |
| =memory_store_state.yaml= | Agent 可写的运行状态存储 |
| =vault.yaml= | 外部凭据的保险库配置 |
| =claude-lock.json= | =ant apply= 创建资源后的 ID 记录 |
| =slack/manifest.yaml= | Slack bot 应用配置 |

前提是 Claude API 工作空间、可用的 =ant= CLI、Slack app、具有合适权限的 GitHub 凭据及对应服务访问。原文示例在 Anthropic 托管环境运行，不要求个人计算机持续在线。

以下保留官方操作入口；完整配置与脚本以官方仓库当前版本为准：

#+begin_src sh
claude update
#+end_src

#+begin_src text
/claude-api managed-agents-onboard https://claude.dev/blog/building-effective-agent-automations/
#+end_src

#+begin_src sh
ant apply vault.yaml
ant apply deployment.md
ant beta:deployments run --deployment-id <id>
#+end_src

=<id>= 从 =claude-lock.json= 获取。部署前还需注入凭据，并使用官方 =scripts/seed-preferences.sh= 写入真实偏好；*单独执行 =ant apply deployment.md= 不会自动创建偏好正文。* 凭据应留在 vault，不写入提示词、状态文件或 Git 仓库。

官方部署示例使用工作日 cron =32 7 * * 1-5=，时区 =America/New_York=。这只是示例配置，不是通用最佳时间；表达时间与日期格式时，调度时区和 Agent 解释时区必须一致。

* 权限隔离与成本防线
:PROPERTIES:
:CUSTOM_ID: 权限隔离与成本防线
:END:
GitHub MCP 工具通过沙箱外的代理取得 vault 凭据，GitHub token 只授予读取权限。Slack 的 shell 请求使用 =$SLACK_BOT_TOKEN= 占位符；平台在访问获准主机时注入真实凭据，而不是把密钥明文放入沙箱。

MCP 无人值守的 =always_allow= 只表示工具调用无须人工逐次批准，*不代表 GitHub 具备写权限*。Slack token 同时担读取与发布，因此只邀请 bot 进入必要频道。网络出口也只放行必需主机。来自消息、PR 的内容即使夹带操作指令，也不应获得新增权限。

*〔补〕* 把来自 Slack 消息、GitHub PR、网页和 Agent 历史笔记的内容统一视为不可信输入。它们可以成为报告证据，但不能改变系统指令、发送频道、源白名单、权限或预算。仅有“提示词里写不要听从攻击文本”不足以构成隔离。

原文建议先观察真实运行成本，再把单次预算初设为正常开销的 *3--5 倍*，随后收紧。原例 =amount: "500"= 的单位为美分，即每轮 *5 美元*，不是 500 美元。达到预算时，托管运行可能以 =budget_reached= 暂停，而不是按照常规错误退出。必须把“触发”“暂停”“已完成发布”分开核验，不能把“按时触发过”误判为“已完成简报”。

* 反向验证方案：怎么证明没有静默失效〔补〕
:PROPERTIES:
:CUSTOM_ID: 反向验证方案怎么证明没有静默失效
:END:
第一次上线之前，至少人为制造以下 14 个反例；这些是*建议的验收任务，不是已执行结果*：

1. *断开一个数据源。* 预期：继续报告其余来源；故障源显示“本轮不可读”；该源 bookmark 不变。
2. *人为延迟一轮。* 预期：下一轮从真实 bookmark 补读，不因固定 24 小时窗口漏项。
3. *对已发版本重跑。* 预期：检查 Slack 历史并阻止重复版本。
4. *模拟发送结果未知。* 预期：标 =maybe posted=；ledger 和 bookmark 不前移；需先查消息实际存在与否。
5. *抓取后关闭一条待办。* 预期：发布前复核发现状态已改变，不继续报告为“待处理”。
6. *更改偏好或让偏好读取失败。* 预期：新偏好下轮生效；读取失败时停止而非使用旧规则。
7. *压低预算到不足一轮。* 预期：记录预算停止原因，并把“运行不完整”与“没有变化”分开。
8. *模拟来源只返回最近 50 条。* 预期：发现分页未覆盖旧 bookmark，标记不完整，不前移进度。
9. *模拟 Slack 已发送、台账写入失败。* 预期：重跑先核对目标频道，补齐记录而不再次发布。
10. *模拟无重要新增且配置为不通知。* 预期：没有 Slack 消息，但保存可复核的完整读取和不发送记录；仅完整来源的 bookmark 可推进。
11. *制造同时间戳或迟到事件。* 预期：使用稳定游标或重叠补读与去重，不因时间戳相同而漏项。
12. *无重要新增但一个数据源不可读。* 预期：不把故障误写成无新增；记录故障并遵守已授权的异常通知规则，失败来源 bookmark 不变。
13. *偏好新增关注主题并要求追溯。* 预期：用已授权回溯范围内的来源历史或候选记录重新核查，先核对当前状态和 ledger 再决定是否通知；缺少历史时注明无法保证追溯完整。
14. *异常告警权限缺失或偏好读取失败。* 预期：记录故障但不擅自发送；有授权时才遵守指定频道、触发条件及频率限制，且确认实际发送。

实际验收需要交叉核对*外部 Slack 消息、内部 run 记录、ledger 和 bookmarks*。无发布分支应核实 run 中的完整读取与不发送决定，而不是要求一条本不存在的 Slack 消息；不能只问模型“任务是否成功”。

* 适用场景与边界评估
:PROPERTIES:
:CUSTOM_ID: 适用场景与边界评估
:END:
*适合*：每天/每周追踪 GitHub PR、团队协作消息、监管动态、漏洞或其他可提供增量标识的来源；有明确读者、筛选规则与单一发布出口的场景。

*不要直接套*：需要资金划转、用户限制、生产配置修改等高影响外部操作的自动化。此时发布权限模型不够，必须另加人工审批与专门的操作授权。对缺少稳定 ID、不可补读、分页会截断、来源随时删除历史的系统，bookmark 也不足以单独防漏。

*〔补〕* 若用于风险情报监测，建议把来源状态、证据状态、业务影响分开保存：来源读取成功只能说明“抓到材料”，不能说明“情报已确认”；有情报新增也不代表达到通知阈值。让过滤规则决定是否提醒，并保留未被发送事项的可追踪线索。

* 待确认事项
:PROPERTIES:
:CUSTOM_ID: 待确认事项
:END:
- 部署目标是否具备 Claude Managed Agents beta 权限、=ant= CLI 和所需 API 凭据。
- 目标来源是否提供可稳定追踪的 ID、增量读取机制和足够的历史分页能力。
- 同一个部署是否可能出现并发或重入；如会发生，需独立设计发布互斥机制。
- 是否授权异常通知及其目标频道、触发条件和频率限制；偏好变化是否要求追溯，以及候选记录应保留多久。
