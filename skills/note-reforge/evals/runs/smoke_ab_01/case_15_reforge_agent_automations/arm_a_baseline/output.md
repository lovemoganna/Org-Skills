* 先抓住关键判断
:PROPERTIES:
:CUSTOM_ID: 先抓住关键判断

*定时触发不等于可靠自动化。* 真正困难的不是让 Agent
每天执行，而是在数据源故障、时间错位、任务重复、消息发送不确定和用户偏好变化时，依然不漏重要信息、不误报状态、不重复打扰。

这套方案的实质是*带持久状态和外部副作用的定时任务*：

- *源数据*决定“发生了什么”；每个来源有独立读取进度。
- *用户偏好*决定“哪些变化值得打扰”；Agent 每轮重新读取，但不能修改。
- *运行状态*决定“以前读到哪里、报过什么、当前是否发送成功”；Agent 可以维护。
- *发布渠道*产生真实外部副作用；只有收到明确成功回执，才能把发送记入状态。
- *权限与预算*限制即使 Agent 误判，也能造成多大影响。

因果关系很直接：/读取进度控制完整性，去重台账控制重复，发布确认控制一致性，发送前复核控制时效性，权限隔离控制事故半径。/ 它们不能互相替代。

* 五大核心业务与异常场景深度处置

** 场景 1：超时未知与发送中断（发布确认链）
- *现象与风险*：向 Slack 发送发布请求后遇到超时、连接中断或返回模糊结果；或者 Slack 已经成功发送，但在向本地 =ledger.md= 和 =bookmarks.json= 写入状态前系统崩溃。
- *核心判定*：Slack 返回超时或发送结果不明时，必须标记为 =maybe posted=；*禁止盲目重试*！
- *处置动作*：
  1. 暂不推进 =ledger.md= 或 =bookmarks.json=，暂停本轮状态提交。
  2. 先主动查询目标频道的实际消息历史，用当日标题与消息时间戳 =ts= 交叉核对。
  3. 若核对发现消息已实际送达：提取 Slack 返回的 =ts= 凭据，先行修复补齐 =runs/<date>.md=、=ledger.md= 和 bookmarks 记录，不再重复发送。
  4. 若确认未发出：在排除网络或凭据故障后，按需重新安排发布。
- *机制底线*：发布请求不等于发布成功，=ok: true= 和消息 =ts= 才是发布回执；标题查重与本地台账之间仍存在并发竞争与查询延迟边界，若同一任务可能并发，须引入发布互斥机制或服务端幂等机制。

** 场景 2：单源读取故障与部分可用（读取确认链）
- *现象与风险*：某一数据源（如 GitHub MCP 凭据失效或服务超时）不可读，但其余数据源（如内部文档、RSS）正常。
- *核心判定*：*绝对不能断言“全量无新增”或“本轮无变化”*；“读不到”不等于“没有新增”。
- *处置动作*：
  1. 保持失败源的 bookmark 原进度不变，禁止向前移动该源 bookmark。
  2. 继续正常处理和筛选其余可用来源的数据。
  3. 最终发布简报时，必须显式注明该故障数据源本轮不可用。
  4. 状态提交时，仅对确认读取完整的来源更新 bookmark。
- *异常告警授权边界*：若本轮按偏好不发送正常简报，也不能把来源故障直接认定为“无实质新增”。必须保存包含故障信息的运行记录；只有用户预先在偏好中明确授权了异常通知的触发条件、目标频道、频率限制和允许的故障类别，且本轮能成功读取该授权时，才按配置发送异常告警（告警本身同样需查重并核验回执）；未经授权、偏好不可读或条件不符时，严禁擅自发送告警，只能保留可监控的故障记录等待恢复。

** 场景 3：迟到数据、分页截断与不可补读缺口（覆盖范围界定）
- *现象与风险*：API 接口返回成功，但由于单次只返回最新 50 条导致断线太久产生分页缺口；或者多个事件共享同一时间戳，或有事件因网络延迟迟到写入已读水位之前。
- *核心判定*：*API 返回成功不代表历史已读全！不可将当期 API 调用成功冒充全量完整性。*
- *处置动作*：
  1. 检查 API 分页是否完整追溯到上次记录的 bookmark。若未追溯到上次 bookmark，判定为存在分页缺口，严禁推进该来源 bookmark，严禁报告“无新增”。
  2. 水位推进机制：优先使用能保证顺序与补读范围的原生游标；若只能依赖时间戳 bookmark，必须采用“时间戳 + 稳定 ID”机制，进行重叠补读并按 ID 去重。
  3. 不可补读处理：若来源事件可能无限期迟到，或历史数据因截断、删除而无法补读，*严禁宣称 bookmark 已覆盖全部事件*，必须在运行记录中明确标注历史覆盖缺口。

** 场景 4：依约静默与无发布闭环（静默处理）
- *现象与风险*：本轮增量抓取完成并筛选后，发现没有达到汇报阈值的实质变化，且用户偏好约定“没有重要变化就不通知”。
- *核心判定*：无发布且依约不通知时，以完整读取证据及不发送决策作为状态提交依据，不要求虚构 Slack 回执。
- *处置动作*：
  1. 检查契约模式：若为官方基准示例契约（要求每轮必须有一份注明日期的简报），则向目标频道发送“无实质新增”简报，取得 Slack 回执后推进状态；若为“依约静默”契约，则进入静默流程。
  2. 静默流程必须先在本地运行记录持久化保存：本轮完整读取范围、筛选结果及“不发送决定”。
  3. 仅对确认完整读取的来源推进 bookmark；=ledger.md= 不新增已发布事项。
  4. 为避免未发送事项在未来偏好变更后永久丢失，须保留可回放的候选记录。

** 场景 5：偏好更新、追溯边界与候选事项重评（偏好追溯）
- *现象与风险*：用户更新了 =preferences=（例如新增关注主题、提高关注敏感度或排除某些标签）。
- *核心判定*：偏好作为单一权威来源，读取失败时整个任务必须立刻停止，严禁静默回退到默认设置或旧规则。对于新增关注范围，必须厘清追溯边界。
- *处置动作*：
  1. 明确追溯模式：由用户偏好显式声明“只对今后生效”还是“允许追溯”。
  2. 若不要求追溯：新偏好仅作用于生效之后的读取与通知，之前的数据不重评。
  3. 若要求追溯：必须在数据源可重放的历史范围内补读，或基于预先保存的未发布候选记录进行重评。候选记录必须包含：稳定 ID、来源链接、首次读取时间、当时的筛选原因及偏好版本。
  4. 重评执行：偏好变化后重新读取原始对象当前状态，按新偏好重新筛选，并核对 =ledger.md= 查重，符合条件方可发布。
  5. 边界约束：候选记录必须覆盖已授权的回溯期限，到期才能按约定清理；没有确定期限、来源不可回放或记录已清理时，严禁承诺追溯完整，不得编造默认保存天数。

* 一次运行究竟应该怎样闭环
:PROPERTIES:
:CUSTOM_ID: 一次运行究竟应该怎样闭环
:END:
下面的运行顺序根据官方机制整理，并列出必要的核查条件；不是本地部署记录，也不代表官方逐字实现所有补充规则。

1. *读取偏好。* 从只读 =preferences= 获取来源、排除主题、消息长度、目标频道和停止条件。读不到偏好就停止，不静默启用默认设置。
2. *恢复状态。* 从可写 =state= 读取各来源 bookmark、已报告事项 ledger 和上一轮运行记录。按用户时区计算当前简报日期。
3. *分别增量读取。* 每个来源从自己的 bookmark 继续；记录来源成功、失败、最后实际读取的位置。来源不可用时不要移动该来源 bookmark，也不要写成“无新增”。
4. *筛选值得报告的变化。* 标准不是“抓到多少条”，而是“是否改变读者今天的行动或决策”。已经报告但仍未处理的事项，标出持续状态；已经关闭的事项不再机械重复。
5. *发送前复核。* 对每条准备发布的消息重新查询原始来源。已解决则删除，状态改变则更新，无法验证则不作确定性报告。链接取自来源提供的正式字段，不自行拼接。
6. *先防重，再发布。* 检查目标频道当天是否已有对应简报；在运行记录中先登记准备发送。真正发布后，只接受 Slack 成功标志及消息时间戳作为送达凭据。
7. *按执行结果提交状态。* 需要发送时，Slack 明确确认后才登记已报告事项及已完整读取来源的 bookmark；发布结果不明时记录 =maybe posted=，暂停提交并先核对频道，不盲目重发。按约定不发送时，采用独立的无发布运行记录，只推进已完整读取的来源；无发送不新增已报告事项。
8. *保留运行证据。* 每轮记录成功读取的来源、读取失败、因状态无法确认而放弃的事项、发布回执、预算停止原因。

状态提交取决于是否产生外部发布：*有发布时先核对事实，再取得 Slack 回执，最后提交进度；无发布时先保存可复核的不发送决策及完整读取记录，再提交对应来源的进度。* 发布结果不明时先恢复状态，不用重试掩盖不确定性。

** 状态更新分支表
| 本轮实际情况 | 对外处理 | 可否推进状态 |
|--------------+----------+--------------|
| 来源读取完整、Slack 明确确认发布 | 写入已发布事项与运行回执 | 仅对确认读取完整的来源更新 bookmark，并更新 ledger |
| 部分来源不可读，其余来源可用且发布成功 | 正常报告可用来源，并注明不可读来源 | 成功来源可推进；失败来源 bookmark 不变 |
| Slack 返回超时或发送结果不明 | 标记 =maybe posted=，先查询频道 | 暂不推进 ledger 或 bookmarks，禁止盲目重发 |
| Slack 已发送，但记录写入中断 | 用频道消息的 =ts= 与当日标题核对 | 先修复 run/ledger/bookmark 记录，不再重复发布 |

*额外分支：按约定静默。* 本轮无重要事项且偏好要求不发送、所有拟推进来源均读取完整时，记录读取证据与不发送决定；仅推进完整来源的 bookmark，ledger 不新增已发布事项。这是上述四种发布相关状态之外的补充分支。

这里的状态推进不能只记“成功/失败”：来源读取完成、消息被平台接受、内部状态写入是三件独立的事。

** 两条独立确认链〔补〕
- *读取确认*：判断本轮是否覆盖了该来源的待读取区间。API 返回成功不等于历史已读全。断线太久产生的未追溯到 bookmark 的分页缺口，必须补齐分页或显式标记该来源不完整，不能推进进度。原生游标优于时间戳；无原生游标时需用稳定 ID 重叠补读并去重。若历史无法补读或事件无限期迟到，必须保留覆盖缺口，不能将 API 成功冒充无漏项证明。
- *发布确认*：判断外部消息是否真正被 Slack 接受。=ok: true= 和消息 =ts= 是发布回执，不等于接收者已阅读。发布结果不明时标 =maybe posted=，先查后补，严禁直接重试。
- *综合准则*：对外发布时双链均须成立；依约静默时以完整读取证据与不发送决定作为依据；任一分支下，失败来源的 bookmark 均不得顺带推进，历史缺口必须保留记录。

* 两种读取失败必须采用不同处置
:PROPERTIES:
:CUSTOM_ID: 两种读取失败必须采用不同处置
:END:
用户偏好不可读时，任务必须停止：此时无法确认关注范围、排除条件、篇幅限制和发布目的地，继续运行就可能违背用户的最新要求。单个信息源不可读时，可以继续整理其他可用来源，且保持失败源的 bookmark 不变；若发布简报，必须注明不可用。

*〔补〕* 若本轮按偏好不发送正常简报，也不能把来源故障认定为“无实质新增”。应保存失败运行记录；只有用户预先授权异常通知的触发条件、目标频道、频率限制和允许的故障类别，且本轮能读取该授权配置时，才按配置发送异常告警。告警本身也须去重并核对发送回执；授权不存在、读取失败或条件不符时，不得擅自发送，只能保留可监控的故障记录等待恢复。可用来源是否推进进度，仍须满足各自的读取完整性条件。

二者的判断依据不是“是否出现报错”，而是*缺失的信息是否决定本轮任务的授权边界*。偏好控制什么能报、报给谁；来源只提供可核查的事实。不要把它们统一处理成“读取失败后使用缓存”。

* 四个容易混淆的状态
:PROPERTIES:
:CUSTOM_ID: 四个容易混淆的状态
:END:

** 1. Bookmark 不是“上次运行时间”
:PROPERTIES:
:CUSTOM_ID: 1-bookmark-不是上次运行时间
:END:
=bookmarks.json= 表示*某个来源读到哪里*，不是 cron
最后何时触发。原文给的例子按来源记录时间位置，因此迟到的运行可以补读、提早的运行不会因为固定窗口而重复采集。不同来源必须分开管理。

** 2. Ledger 不是原始消息存档
:PROPERTIES:
:CUSTOM_ID: 2-ledger-不是原始消息存档
:END:
=ledger.md= 记录已经向读者报告的事项、稳定
ID、来源、报告日期与最后状态。它解决“是否报过”，不是替代实时来源。某事项即使已经在
ledger 里，也必须重新确认是否仍待处理。

** 3. Preferences 不是 Agent 自己积累的经验
:PROPERTIES:
:CUSTOM_ID: 3-preferences-不是-agent-自己积累的经验
:END:
原文把 =preferences= 配成 *read-only*，由用户维护；=state= 为
*read-write*，由 Agent
保存书签、台账、运行记录、提议与来源行为笔记。不能让 Agent
的自动总结覆盖用户偏好。每轮都要读新偏好，以免旧 prompt
继续执行已撤销的要求。

** 4. 发布请求不等于发布成功
:PROPERTIES:
:CUSTOM_ID: 4-发布请求不等于发布成功
:END:
向 Slack 发送请求后，可能遇到超时、连接中断或不明确的 API
反馈。外部消息与本地状态无法简单地看作一个原子动作。原文采取务实防护：查看当天消息、防重、核对
Slack 返回值、将不确定状态留给后续核查。

*〔补〕*
这并不是严格的“恰好发送一次”保证。标题查重与本地台账之间仍存在并发竞争、查询延迟等边界。若同一任务可能并发运行，先对同一日期的发布任务做互斥或引入服务端幂等机制；不要仅凭一条
prompt 声称已实现严格 exactly-once。

* 部署依赖与原有命令
:PROPERTIES:
:CUSTOM_ID: 部署依赖与原有命令
:END:
官方示例目录 =daily-brief/= 的职责划分：

| 文件                            | 职责                                           |
|---------------------------------+------------------------------------------------|
| =agent.md=                      | 模型、工具权限、运行步骤和简报筛选规则         |
| =deployment.md=                 | cron、时区、环境、预算、首次输入消息、内存挂载 |
| =environment.yaml=              | 网络访问允许列表                               |
| =memory_store_preferences.yaml= | 用户维护的只读偏好存储                         |
| =memory_store_state.yaml=       | Agent 可写的运行状态存储                       |
| =vault.yaml=                    | 外部凭据的保险库配置                           |
| =claude-lock.json=              | =ant apply= 创建资源后的 ID 记录               |
| =slack/manifest.yaml=           | Slack bot 应用配置                             |

前提是 Claude API 工作空间、可用的 =ant= CLI、Slack app、具有合适权限的
GitHub 凭据及对应服务访问。原文示例在 Anthropic
托管环境运行，不要求个人计算机持续在线。

以下保留官方操作入口；完整配置与脚本以官方仓库当前版本为准：

#+begin_src sh
claude update
#+end_src

#+begin_src text
/claude-api managed-agents-onboard https://claude.dev/blog/building-effective-agent-automations/
#+end_src

#+begin_src sh
ant apply vault.yaml
ant apply deployment.md
ant beta:deployments run --deployment-id <id>
#+end_src

=<id>= 从 =claude-lock.json= 获取。部署前还需注入凭据，并使用官方
=scripts/seed-preferences.sh= 写入真实偏好；*单独执行
=ant apply deployment.md= 不会自动创建偏好正文。* 凭据应留在
vault，不写入提示词、状态文件或 Git 仓库。

官方部署示例使用工作日 cron =32 7 * * 1-5=，时区
=America/New_York=。这只是示例配置，不是通用最佳时间；表达时间与日期格式时，调度时区和
Agent 解释时区必须一致。

* 权限与成本：限制出错范围
:PROPERTIES:
:CUSTOM_ID: 权限与成本限制出错范围
:END:
GitHub MCP 工具通过沙箱外的代理取得 vault 凭据，GitHub token 只授予读取权限。Slack 的 shell 请求使用 =$SLACK_BOT_TOKEN= 占位符；平台在访问获准主机时注入真实凭据，而不是把密钥明文放入沙箱。

MCP 无人值守的 =always_allow= 只表示工具调用无须人工逐次批准，*不代表 GitHub 具备写权限*。Slack token 同时担读取与发布，因此只邀请 bot 进入必要频道。网络出口也只放行必需主机。来自消息、PR 的内容即使夹带操作指令，也不应获得新增权限。

*〔补〕* 把来自 Slack 消息、GitHub PR、网页和 Agent
历史笔记的内容统一视为不可信输入。它们可以成为报告证据，但不能改变系统指令、发送频道、源白名单、权限或预算。仅有“提示词里写不要听从攻击文本”不足以构成隔离。

原文建议先观察真实运行成本，再把单次预算初设为正常开销的 *3--5
倍*，随后收紧。原例 =amount: "500"= 的单位为美分，即每轮 *5 美元*，不是
500 美元。达到预算时，托管运行可能以 =budget_reached= 暂停，而不是按照常规错误退出。必须把“触发”“暂停”“已完成发布”分开核验，不能把“按时触发过”误判为“已完成简报”。

* 反向验证：怎么证明它没有静默失效〔补〕
:PROPERTIES:
:CUSTOM_ID: 反向验证怎么证明它没有静默失效补
:END:
第一次上线之前，至少人为制造以下反例；这些是*建议的验收任务，不是已执行结果*。

1. *断开一个数据源。*
   预期：继续报告其余来源；故障源显示“本轮不可读”；该源 bookmark 不变。
2. *人为延迟一轮。* 预期：下一轮从真实 bookmark 补读，不因固定 24
   小时窗口漏项。
3. *对已发版本重跑。* 预期：检查 Slack 历史并阻止重复版本。
4. *模拟发送结果未知。* 预期：标 =maybe posted=；ledger 和 bookmark
   不前移；需先查消息实际存在与否。
5. *抓取后关闭一条待办。*
   预期：发布前复核发现状态已改变，不继续报告为“待处理”。
6. *更改偏好或让偏好读取失败。*
   预期：新偏好下轮生效；读取失败时停止而非使用旧规则。
7. *压低预算到不足一轮。*
   预期：记录预算停止原因，并把“运行不完整”与“没有变化”分开。
8. *模拟来源只返回最近 50 条。* 预期：发现分页未覆盖旧 bookmark，标记不完整，不前移进度。
9. *模拟 Slack 已发送、台账写入失败。* 预期：重跑先核对目标频道，补齐记录而不再次发布。
10. *模拟无重要新增且配置为不通知。* 预期：没有 Slack 消息，但保存可复核的完整读取和不发送记录；仅完整来源的 bookmark 可推进。
11. *制造同时间戳或迟到事件。* 预期：使用稳定游标或重叠补读与去重，不因时间戳相同而漏项。
12. *无重要新增但一个数据源不可读。* 预期：不把故障误写成无新增；记录故障并遵守已授权的异常通知规则，失败来源 bookmark 不变。
13. *偏好新增关注主题并要求追溯。* 预期：用已授权回溯范围内的来源历史或候选记录重新核查，先核对当前状态和 ledger 再决定是否通知；缺少历史时注明无法保证追溯完整。
14. *异常告警权限缺失或偏好读取失败。* 预期：记录故障但不擅自发送；有授权时才遵守指定频道、触发条件及频率限制，且确认实际发送。

实际验收需要交叉核对*外部 Slack 消息、内部 run 记录、ledger 和 bookmarks*。无发布分支应核实 run 中的完整读取与不发送决定，而不是要求一条本不存在的 Slack 消息；不能只问模型“任务是否成功”。

* 什么时候适合用，什么时候不要直接套
:PROPERTIES:
:CUSTOM_ID: 什么时候适合用什么时候不要直接套
:END:
适合：每天/每周追踪 GitHub
PR、团队协作消息、监管动态、漏洞或其他可提供增量标识的来源；有明确读者、筛选规则与单一发布出口的场景。

不要直接套：需要资金划转、用户限制、生产配置修改等高影响外部操作的自动化。此时发布权限模型不够，必须另加人工审批与专门的操作授权。对缺少稳定
ID、不可补读、分页会截断、来源随时删除历史的系统，bookmark
也不足以单独防漏。

*〔补〕*
若用于风险情报监测，建议把来源状态、证据状态、业务影响分开保存：来源读取成功只能说明“抓到材料”，不能说明“情报已确认”；有情报新增也不代表达到通知阈值。让过滤规则决定是否提醒，并保留未被发送事项的可追踪线索。

* 待确认
:PROPERTIES:
:CUSTOM_ID: 待确认
:END:
- 部署目标是否具备 Claude Managed Agents beta 权限、=ant= CLI 和所需 API 凭据。
- 目标来源是否提供可稳定追踪的 ID、增量读取机制和足够的历史分页能力。

- 是否授权异常通知及其目标频道、触发条件和频率限制；偏好变化是否要求追溯，以及候选记录应保留多久。
