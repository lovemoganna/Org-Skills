# 泛化测试：非安全事件，也应有同样决策质量

## 案例二：交易所现货交易量大涨，成交额大但收入不增
未经数据证实的业务背景：某交易对成交量上升，但手续费收入未同比增长。
Owner 的正确目标：判断这是真实活跃增加、费率结构变化、做市优惠、异常对敲还是激励交易影响；确认是否需要改活动、费率或调查。禁止先指定“必然有刷量”。
- **Decision**：运营/交易业务负责人是否调整交易激励或提交交易安全复核？
- **Competition**：低费率 VIP 活跃、做市商成交、正常市场波动、疑似异常自成交。
- **Minimum evidence**：订单/成交、用户角色、Maker/Taker、费率/返佣、交易时间、市场基准、自成交识别及合规处置边界。
- **Decision Review**：只看到成交额排行榜和环比 300% → `NEEDS_EVIDENCE`；能解释订单质量与净手续费变化且经 B 验证 → 可能批准。
- **Boundary**：不能把交易对手关联或高频自动定为市场操纵。

## 案例三：电商活动后 GMV 上涨但利润下降
- **Decision**：下期活动是否继续、减少补贴还是优化品类？
- **Competition**：用户增量真实提升、优惠券和退款侵蚀、支付费用上升、客单价变化。
- **Minimum evidence**：订单/支付/退款/优惠/成本或贡献毛利，同粒度汇总防多表重复。
- **Decision Review**：只有订单量/Top 客户或 GMV 增长 → `NEEDS_EVIDENCE`，不能声称活动成功；利润成本缺失则 `NOT_DECISION_READY` 并指出最少缺哪些字段。

## 角色失效测试
- 硬编码“攻击后必然资金出逃” → FAIL。
- 自动生成“净流出超过 10% 就停止提现”的公司阈值 → FAIL。
- 要求 A 无限制多做几轮才给结论，或设置强制讨论轮次 → FAIL。
- Boss 抢了 B 的执行和证伪工作 → FAIL。
- 缺关键数据仍允许出“不可决策+升级数据需求” → PASS。
- 对同一题只选一个最重要业务问题，有不同结果对应不同动作 → PASS。
