# Validator 与自检自修

Validator 独立于两张本体表。

本体定义业务知识。Validator 检查当前阶段是否合法。


## 交付完成性 Gate

检查：

1. 用户明确请求报告时，是否真正创建并交付报告文件？
2. 数据读取失败是否记录原始错误，而不是仅回复“继续”？
3. 是否分别标明 `已交付报告` 与 `已完成真实业务分析`？
4. 是否把文件元数据、历史验证、SQL 模板、Eval 样例冒充本轮 SQL Result？
5. 未得到完整同源字节时，是否停止 Finding、Decision Value 和 Dashboard？
6. 对已指定 URL，是否保存获取方式、SHA-256 与本地字节大小（成功时）？
7. 修复后是否重新测试原失败的 Source Gate，并只在成功后推进业务分析？

## 当前阶段检查

每个阶段先检查：

1. 输入事实是否来自当前有效证据链。
2. 本阶段是否只做自己的任务，没有越过 Gate。
3. 主体、粒度、单位、时间语义和关系路径是否兼容。
4. 参数是否闭合；未知信息是否明确标记。
5. SQL 或执行逻辑是否严格对应当前问题。
6. Result 是否真实执行并可复核。
7. 输出是否表达了数据不能证明的事实。
8. 是否产生信息增量；没有则停止。

具体检查按下方专项规则执行。


## 多粒度指标检查

1. 是否分别声明指标的原生粒度及单位。
2. 是否验证时间交集、Join 键唯一性与基数。
3. 是否先聚合后连接，防止年度/主体指标在细粒度记录上重复计量。
4. 是否独立回算 Join 前后指标合计；不一致时不得接受结果。
5. 是否把同期变化错误推断成因果。

## 复杂问题真实验证专项检查

复杂问题形成后检查：

```text
是否来自已验证 Signal？
新增对象是否已在阶段 9 激活？
问题参数是否闭合？
关系执行状态是什么？
待验证关系是否先做关系验证？
实际 SQL 是否只实现问题合同？
是否得到真实 Result？
Result 是否可复现或内部一致？
结果是否改变或细化当前判断？
```

### 阶段边界

正确：

```text
复杂问题
→ 关系前置验证
→ SQL
→ Result
→ Result 边界
→ 竞争解释
```

错误：

```text
复杂问题
→ 竞争解释
→ 再找数据证明
```

也错误：

```text
复杂问题
→ SQL 同时新增 country / KYC / network
```

未在阶段 9 激活的维度不得在复杂问题验证 SQL 中临时加入。

### 无信息增量

真实执行成功不代表必须继续。

如果 Result：

```text
没有改变当前判断
没有缩小解释范围
没有产生新的待解释结构
```

则停止该分支。

不得为了完成固定流程机械进入竞争解释。

## 证据作用域检查

每次阶段判断前，先确认事实 provenance：

```text
事实是什么？
来自哪个阶段？
该阶段是否仍然有效？
该事实是否在当前分析链真实验证？
上游修复后是否需要重新验证？
状态：已验证 / 待验证 / 失败
```

如果无法回答，默认“待验证”。

### 禁止跨轮继承

旧轮次、被回退阶段、作废分支中的事实，即使实际上仍然正确，也不能直接作为当前链证据。

正确处理：

```text
旧结果
→ 当前链待验证
→ 重新验证
→ 当前链已验证
```

### 数据中可见不等于已验证

真实数据中某事实客观存在，也不代表当前阶段已经获得使用该事实的证据权限。

如果本阶段规定“不执行新 SQL”，则未由当前链前序结果验证的子集事实只能保持待验证。

## 多跳关系语义检查

对多跳路径：

```text
A → B → C
```

只能继承每条已登记边的原始语义。

允许：

```text
A 与 C 通过 B 可达
```

不得自动升级为：

```text
A 直接导致 C
A 资助 C
A 转换成 C
A 是 C 的来源
```

除非这些关系已经单独登记并有证据支持。

本体可达性和因果语义必须分开。

## 局部组合专项检查

对每个候选维度依次检查：

```text
本体关系是否合法？
当前 Signal 范围内是否存在变化？
是否可能改变当前判断？
解释语义是否足够？
是否存在更短、更直接的候选？
当前状态应为：非法 / 合法但暂缓 / 合法并激活？
```

### 本体可达与价值分离

合法关系只证明：

```text
可以沿这条关系访问
```

不证明：

```text
现在值得沿这条关系分析
```

如果维度没有信息增量，应暂缓或淘汰当前分支。

### 常量维度

已知当前 Signal 范围内只有一个取值时：

```text
合法
+
常量
=
当前不激活
```

不得为了“多一个切片”继续展开。

### 语义不完整

例如地址字段只有：

```text
加密交易|关联|关联链上地址
```

但不知道 source / destination 角色。

此时是：

```text
合法但暂缓
```

不是非法。

### 跨对象执行合同

激活跨对象关系前必须记录：

```text
关系
join key
左侧类型
右侧类型
canonical 规范化
匹配完整性 / orphan 检查
已知限制
```

如果之前已经验证过类型兼容和完整匹配，应复用该已验证事实；不得重新凭感觉选择 CAST 或隐式转换。

## Signal 专项检查

每个 Signal 依次检查：

```text
Result 是否真实执行？
结果中是否存在明确结构或差异？
该结构是否提供信息增量？
问题自身是否已经包含合法比较对象？
是否真的需要历史或外部基线？
小样本只是限制外推，还是确实无法描述当前样本？
是否存在至少一个合法且可能改变后续判断的下一问题？
Signal 表述是否超过数据证据？
是否使用没有标准的强判断词？
```

### 不得机械否决

以下两条都不是统一否决条件：

```text
没有历史基线
样本很小
```

是否影响 Signal，要看当前问题要证明什么。

例如：

```text
Deposit = 0.081 BTC
Withdrawal = 0.020 BTC
```

可以支持：

```text
当前样本中 Deposit 高于 Withdrawal
```

但不能仅据此支持：

```text
BTC 流入异常
BTC 流入激增
长期存在净流入
```

### 下一问题检查

Signal 阶段只检查是否存在合法下一问题，不执行它。

下一问题必须：

```text
沿已登记本体关系展开
参数原则上可闭合
不同结果可能改变当前判断
```

如果只能继续做无价值字段切片，则停止。

## Eval 隔离检查

真实分析前检查：

```text
当前问题是否从当前数据、本体、指标和已验收阶段自然产生？
是否能在不读取 eval / example / expected_output 的情况下独立得到？
是否复用了测试题中的具体币种、阈值、时间范围或预期答案？
```

如果第三问为“是”，且这些参数不是当前真实任务独立提供或独立产生，则判定为测试污染。

处理方式：

```text
停止当前下游阶段
回到最近受影响阶段
只使用真实任务上下文重新生成
重新 Validator
通过后再继续
```

Eval 可以验证行为边界，但不能提供真实分析内容。

## 原子问题专项检查

每个原子问题执行以下检查：

```text
主体是什么？
指标是什么？
Rail / 币种 / 资产范围是什么？
状态范围是什么？
时间范围是什么？
比较对象是什么？
单位和粒度是否兼容？
能否直接生成一条确定查询？
不同结果分别改变什么判断？
结果与判断之间是否存在直接逻辑关系？
是否包含没有标准的模糊判断词？
```

任何关键参数未闭合时：

```text
原子问题
→ 候选问题方向
```

不得进入 SQL。

### 伪决策链

如果问题写：

```text
比较 A
→ 决定 B
```

Validator 必须确认 A 的不同结果确实能够直接决定 B。

如果中间需要额外业务规则、未知状态机、模型推断或人为选择，则该链无效。

### 模糊词修复

没有阈值时：

```text
“是否高度集中”
```

不得直接验证。

优先改成：

```text
Top 1 / Top 3 / Top 5 占比分别是多少？
```

先取得真实结果，再判断是否形成 Signal。

不得为了让问题可执行而临时发明 20%、50%、80% 等阈值。


## SQL 枚举安全检查

对枚举字段的分类逻辑执行：

```text
已知值是否显式列出？
未知值是否可能被 ELSE 误归类？
是否需要单独输出 unexpected_value_count？
```

例如：

```sql
CASE
  WHEN direction = 'deposit' THEN amount
  WHEN direction = 'withdrawal' THEN -amount
  ELSE NULL
END
```

优于：

```sql
CASE
  WHEN direction = 'deposit' THEN amount
  ELSE -amount
END
```

后者只有在完整业务定义证明字段只能有两个值时才可接受。当前数据样本只包含两个值，不等于业务域永久只有两个值。

## 指标专项检查

对每个指标依次检查：

```text
这是基础指标还是派生指标？
基础指标是否保持中性？
派生指标依赖是否清楚？
单位是否可直接计算？
主体和粒度是否一致？
时间口径是否与名称一致？
是否错误依赖 Signal 才允许定义？
```

典型错误：

```text
错误：
“已完成交易数”作为唯一基础交易量指标

优先修正：
“交易记录数”
+
status=completed 过滤条件
```

```text
错误：
还没有 Signal，所以不能建立主体资金占比

修正：
如果主体资金占比本身具有稳定业务意义、合法单位和明确分母，可以登记为派生指标。
是否形成 Signal，要等真实执行结果。
```

```text
错误：
status=completed + created_at
→ “本月完成交易数”

修正：
“本月创建且当前状态为 completed 的交易记录数”
```

指标自检不得通过增加未经证实的业务含义来修复。

## 规则库专项检查

对每条本体识别规则执行两个问题：

```text
这条规则是否形成了新的稳定业务组合语义？
这条规则是否说了组成原子没有证明的更强事实？
```

第一问为“否”，拒绝该规则。

第二问为“是”，拒绝该规则并回退到原子能够证明的语义。

例如：

```text
交易状态=completed
```

只能证明：

```text
当前记录状态为 completed
```

不能自动升级为：

```text
资金最终结算完成
链上已经最终确认
银行清算不可撤销
账户余额已经变更
```

## 组合判定

以下条件不能证明业务组合合法：

```text
SQL 可以 JOIN
字段类型兼容
数学上可以计算
字段名称相似
Lisp 可以表达
模型认为相关
```

无法证明关系合法时，拒绝组合。

## 竞争解释专项检查

先区分：

```text
当前解释
竞争解释
数据限制
```

竞争解释必须同时满足：

```text
与当前解释不同
能推翻或收缩当前解释
与已确认事实兼容
可以被数据区分
不依赖未登记关系
```

检查：

1. 是否把当前解释本身编号成竞争假设。
2. 是否把“小样本、缺历史基线、数据有限”等限制伪装成竞争解释。
3. 是否只是换一种说法，没有竞争性。
4. 是否已经被前序证据排除。
5. 是否明确“成立后会改变什么判断”。
6. 是否明确最小区分证据。
7. 是否在本阶段提前执行稳健性验证或生成 Finding。

不满足时删除。不要凑数量。

## 稳健性验证专项检查

只执行竞争解释需要的最小验证。

检查：

1. 每个 SQL / 检查是否对应一个明确竞争解释。
2. 是否机械运行与当前问题无关的检查。
3. 是否独立复核关键聚合、分母、JOIN、单位或时间口径。
4. 验证结果是否明确：保留、收缩或推翻当前解释。
5. 小样本和极端值是否只限制结论范围，没有被机械当作否决条件。
6. 没有真实验证 Result 时，是否错误升级为 Finding。

## 自检自修

每个阶段结束后执行：

```text
检查当前阶段
定位具体问题
只修当前阶段
重新检查
通过后继续
```

修复优先级：

1. 先修语义漂移。
2. 再修关系、主体、粒度、时间和单位问题。
3. 再修 Lisp 或结构问题。
4. 最后修表达和格式。

不得通过新增未经证实的事实让检查通过。

如果修复需要缺失事实，标记阻塞并停止。

如果问题暴露稳定的本体缺失或错误，返回本体阶段修正，并说明依据。

如果问题只属于当前查询或当前数据限制，保留为执行限制，不修改正式本体。

发生修复时记录：

```text
问题
修正
复检结果
```


## 运行时失败

运行时失败不得立即终止分析。

先读取 `runtime.md` 并尝试当前工具可用的等价运行时。只有兼容路径全部失败后，才允许标记执行阻塞。

不得为了通过 Validator 改用非等价数据入口。

## Dashboard Gate 专项检查

仅当 Finding 已验证且有 Decision Value 时，继续检查：

```text
使用者与决策动作明确？
是否有持续观察或可复用的展示场景？
指标口径与更新条件已确认？
展示比一次性报告有增量？
只保留决策者必须看到的指标？
```

不满足时，应明确输出“不生成 Dashboard”，而不是为了完成流程生成图表。

### 必测反例

- 4 条交易的一次性净额研究，只有分析口径价值：保留报告，不自动增加首页图表。
- 需要持续追踪的、口径稳定且直接关联动作的多期指标：可以进入 Dashboard 设计，但不得省略证据验证。
- 用户明确要求一次性 Dashboard：可以交付证据限定的分析展示，不把它包装成持续经营 KPI。
