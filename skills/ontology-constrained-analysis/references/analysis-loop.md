# 分析闭环

## 高质量指标

只有两张本体表通过 Gate 1 后，才能建立指标。

指标先分两层：

```text
基础指标
派生指标
```

基础指标直接量化已登记业务事实，例如：

```text
交易记录数
同一法币下的交易金额
同一加密资产下的交易数量
交易用户数
```

派生指标由基础指标经过稳定、可解释的计算得到，例如：

```text
状态占比
同一资产下的净交易量
同一单位范围内的主体资金占比
```

每个指标必须明确：

主体、粒度、单位、计算口径、时间口径、依赖原子、数据限制。

### 基础指标约束

基础指标应保持中性。

不要无必要把以下条件固化进基础指标：

```text
status
direction
channel
network
country
KYC
```

这些条件优先作为维度或过滤条件。只有当条件本身就是稳定业务定义的一部分时，才允许进入指标定义。

例如：

```text
交易记录数
```

优先于：

```text
已完成交易记录数
```

后者可以通过：

```text
交易记录数 + status=completed
```

得到。

### 派生指标约束

派生指标必须依赖已定义的基础指标或合法派生指标。

不得把不同单位强行合并。

例如：

```text
EUR + USD
BTC + ETH
```

不能直接相加。

净流量、占比、集中度等指标只有在主体、单位、粒度、时间和分母范围都明确时才合法。

### 指标与 Signal

Signal 不是指标建立的前置条件。

是否建立指标，只看：

```text
业务意义是否稳定
本体关系是否合法
口径是否明确
是否具有复用价值
```

真实数据执行后，某个指标结果是否值得继续解释，才由 Signal 判断。

因此不能因为“还没有 Signal”就拒绝一个本身合法、有稳定业务意义的指标；也不能因为某个指标常见，就机械生成它。

### 命名与时间语义

指标名称必须与真实时间口径一致。

例如：

```text
status=completed
时间归属=created_at
```

只能说明：

```text
在该时间范围创建、且当前记录状态为 completed 的交易
```

不能命名或解释成：

```text
该时间范围内完成的交易
```

除非存在可以证明“完成发生时间”的可靠时间字段和业务定义。

同样：

```text
status=completed
```

不能自动升级为：

```text
最终结算
不可撤销
余额已经变化
```

### 禁止机械生成

不得因为字段是数值型就自动 `SUM` 或 `AVG`。

不得因为字段是分类字段就自动生成 Count、TopN 或图表。

不得为了覆盖字段而创建指标。

指标只保留当前业务世界中具有稳定意义、合法口径和复用价值的量化对象。

## 原子问题

先区分两类内容：

```text
候选问题方向
可执行原子问题
```

候选问题方向只表示“可能值得分析什么”，例如：

```text
状态结构
资金方向
主体集中
时间分布
```

它不是原子问题，不能直接进入真实执行。

### 原子问题合同

一个问题只有同时满足以下条件，才可以进入真实执行：

1. 只改变一个主要判断。
2. 能通过一次明确查询回答。
3. 主体已明确。
4. 指标已明确。
5. Rail、资产或币种等必要业务范围已明确。
6. 状态范围已明确，或明确为“不限制状态”。
7. 时间范围已明确。
8. 比较对象已明确。
9. 单位与粒度兼容。
10. 当前数据能够回答。
11. 不同结果会改变什么判断已经明确。
12. 查询结果与该判断之间存在直接逻辑关系。

任一必要参数未闭合时，只能保留为候选问题方向，不得进入 SQL 阶段。

### 参数闭合

原子问题必须能够直接翻译成一条确定的数据验证。

例如：

```text
不合格：
各币种是净流入还是净流出？
```

缺少至少：

```text
时间范围
状态范围
具体币种或明确逐币种执行方式
```

合格示例：

```text
主体：
法币交易

指标：
净法币交易金额

范围：
当前允许数据的全部 created_at
currency = EUR
status = completed

比较：
EUR deposit amount
vs
EUR withdrawal amount

判断：
净值 > 0 → 当前样本中该范围表现为净流入
净值 < 0 → 表现为净流出
净值 = 0 → 平衡
```

如果需要对多个币种执行，必须明确：

```text
这是同一问题模板分别对每个币种独立执行
```

不得把不同币种金额合并成一次业务判断。

### 决策链检查

“为什么值得问”必须能落到一个真实判断。

错误：

```text
先比较 Fiat 与 Crypto 的状态分布，
再决定后续应该使用什么 status。
```

如果状态分布本身不能决定后续过滤规则，这就是伪决策链。

正确要求：

```text
结果 A → 判断 A
结果 B → 判断 B
结果 C → 判断 C
```

中间不得依赖未提供的业务规则或模型联想。

### 模糊判断词

以下词不能直接进入可验证问题：

```text
主要
少数
明显
高
低
异常
集中
活跃
大额
高频
```

除非存在明确标准。

例如：

```text
不合格：
资金是否主要由少数用户贡献？
```

可改成纯定量问题：

```text
Top 1、Top 3、Top 5 用户分别占同范围总金额的多少比例？
```

然后由真实结果决定是否形成 Signal。

如果任务已经提供“主要”“大额”“高频”等正式阈值，则可以直接使用该阈值。

### 问题价值

原子问题必须说明：

```text
为什么值得问
依据哪个指标
涉及什么主体
比较什么
不同结果会改变什么判断
当前数据是否能够回答
```

如果不同答案不会改变业务判断，降低优先级或停止。

不要为了覆盖指标或字段而制造问题。

## 真实执行

所有进入验证的问题必须真实执行。

### 真实分析与 Eval 隔离

真实分析的问题、参数和 SQL 必须来自当前任务的：

```text
真实输入
业务语义
两张本体表
指标
当前已验收的原子问题
```

不得从以下内容取得分析方向或答案：

```text
eval prompt
expected_output
assertions
examples
演示样本
先前失败测试中的目标答案
```

如果 Skill 刚因某个 Eval 或示例完成修复，必须重新执行当前真实任务的受影响阶段，再进入下游阶段。

不得把修复用测试题直接拿来充当真实分析问题。

### SQL 枚举安全

对 `direction`、`status`、`type` 等枚举字段，SQL 必须显式处理允许值。

错误：

```sql
CASE
  WHEN direction = 'deposit' THEN amount
  ELSE -amount
END
```

因为所有非 `deposit` 值都会被当成 `withdrawal`。

优先使用：

```sql
CASE
  WHEN direction = 'deposit' THEN amount
  WHEN direction = 'withdrawal' THEN -amount
  ELSE NULL
END
```

并在需要时单独检查未知枚举值数量。

当前数据恰好没有未知值，也不能证明这种 `ELSE` 写法安全。

至少保留：

当前问题、使用指标、实际执行逻辑或 SQL、真实 Result、能说明什么、不能说明什么。

没有执行结果时，标记“待执行”。停止该结果的下游推论。

## Signal

只有真实执行结果出现值得继续解释的信息结构时，才能形成 Signal。

Signal 可以来自：

```text
问题内部的合法比较
历史或外部基线比较
结构差异
集中
路径
状态偏移
其他真实数据事实
```

外部或历史基线不是所有 Signal 的必需条件。

如果原子问题本身已经定义了合法比较对象，例如：

```text
Deposit vs Withdrawal
Group A vs Group B
Top1 / Top3 / Top5 share
```

则真实结果可以直接提供内部比较。

### Signal 判定

一个 Result 升级为 Signal，至少满足：

1. 真实执行已完成。
2. 结果中存在明确的数据结构或差异。
3. 该结构提供了新的业务信息，而不是重复已知事实。
4. 至少存在一个本体关系合法、参数可闭合、并可能改变后续判断的下一问题。
5. Signal 表述不超过真实结果能够证明的范围。

如果以上条件不满足，保留为普通 Result。

### 小样本

小样本不能自动否决 Signal。

小样本会限制：

```text
稳健性
外推范围
原因判断
阈值判断
```

但不会抹除当前样本中真实存在的结构。

因此：

```text
4 条记录
```

可以支持：

```text
当前 4 条记录中的方向结构
```

但不能自动支持：

```text
长期规律
总体异常
未来趋势
全体用户规律
```

### 基线

需要历史或外部基线的判断包括：

```text
增长
下降
异常偏高
异常偏低
趋势变化
高于正常水平
```

不需要外部基线才能描述的结构包括：

```text
A 大于 B
净值为正或负
占比结构
同一范围内的路径或集中分布
```

是否需要基线，由问题语义决定，不机械统一要求。

### Signal 表述

没有明确标准时，不使用：

```text
异常
明显
显著
高
低
激增
骤降
```

改为直接陈述数据：

```text
Deposit = 0.081 BTC
Withdrawal = 0.020 BTC
Net = +0.061 BTC
```

或：

```text
当前样本存在 Deposit 高于 Withdrawal 的方向不对称结构。
```

这不等于异常，也不等于原因。

### 信息增量

Signal 必须能够推动分析继续收敛。

至少要能提出一个合法的下一问题，例如：

```text
当前结构是否由单一主体驱动？
当前结构是否由某一时间段驱动？
当前结构是否由某一合法业务维度驱动？
```

这里只验证“下一问题是否存在且合法”，不在 Signal 阶段执行该问题。

如果没有任何合法下一问题能够改变判断，则该 Result 不升级为 Signal，或在 Signal 后立即停止该分支。

## 局部组合

Signal 出现后，不得重新遍历全部字段、指标或原子。

只允许沿当前 Signal 已登记的本体关系扩展候选对象、属性或维度。

但：

```text
本体可达
≠
当前值得展开
```

本体只回答“能不能到达”。局部组合还必须回答“当前证据是否允许使用”和“这个维度现在有没有信息价值”。

### 证据作用域

阶段 9 只能使用当前有效分析链已经验证的事实。

每个事实至少区分：

```text
当前链已验证
当前链待验证
当前链验证失败
```

以下内容不得自动升级为“当前链已验证”：

```text
原始数据中肉眼可见但本流程尚未验证的事实
旧轮次分析结果
已经回退或作废分支中的验证结果
Eval / example / expected_output 中的事实
其他任务中的同名字段或结论
```

如果前序阶段修复导致某个下游阶段被回退，则受影响的旧验证结果失效，必须重新验证后才能继续使用。

阶段 9 不执行新 SQL。需要新数据验证的候选，只能标记：

```text
合法但暂缓
原因：当前证据链待验证
```

### 三态判定

每个候选维度必须进入以下一种状态：

```text
非法
合法但暂缓
合法并激活
```

`非法`：
没有已登记关系、主体/粒度/时间/单位不兼容，或关系路径不成立。

`合法但暂缓`：
关系合法，但当前证据未验证、信息增量不足、解释能力弱、优先级低，或需要先回答更直接的问题。

`合法并激活`：
关系合法，当前证据足以支持该关系语义，且不同结果可能改变当前 Signal 的解释、范围或下一步判断。

不得把“合法但暂缓”误写成“非法”。

### 常量维度

只有当“该维度在当前 Signal 范围内为常量”已经由当前有效证据链验证时，才能据此淘汰。

错误：

```text
原始数据里看起来 network 都一样
→ 当前阶段直接判定 network 为常量
```

正确：

```text
当前证据链已验证 network 在 Signal 子集只有一个取值
→ 当前分支不激活 network
```

如果尚未验证，只能标记：

```text
合法但暂缓
原因：变化性待验证
```

### 激活标准

每增加一个维度，必须回答：

```text
本体路径是什么？
当前链已经验证了哪些事实？
还有哪些事实待验证？
这个维度为什么可能改变当前判断？
不同结果会怎样改变解释或范围？
是否存在更短、更直接的候选维度？
```

无法回答时，不得激活。

优先选择最短关系路径和最直接的解释变量。

### 解释能力不足

关系合法，但语义不完整时，默认进入“合法但暂缓”。

例如：

```text
加密交易|关联|关联链上地址
```

如果当前只知道“有关联地址”，但不知道它在 deposit / withdrawal 中分别代表 source 还是 destination，则：

```text
关系合法
解释能力弱
→ 合法但暂缓
```

不得错误标记为非法，也不得基于未知方向作解释。

### 多跳路径

允许沿已经登记的本体关系形成多跳可达路径。

例如：

```text
加密交易 ← 用户 → 法币交易
```

可以支持：

```text
同一用户是否同时存在加密交易和法币交易
```

但不能自动支持：

```text
该加密入金资助了该法币出金
加密资产被兑换成法币
某笔资金从 Crypto 流向 Fiat
```

后者需要单独登记的资金来源、兑换、余额、ledger 或 transfer-reference 关系。

因此：

```text
多跳可达
≠
直接关系
≠
因果关系
≠
资金来源关系
```

### 跨对象关系执行合同

激活跨对象关系时，必须同时记录：

```text
激活对象
本体路径
join key
两侧实际数据类型
执行状态：已验证 / 待验证 / 失败
已验证规范化方式（如果存在）
必要的基数 / 匹配检查
已知限制
证据来源阶段
```

如果当前链尚未验证 join key 的规范化或匹配完整性，不得写“已验证”。

应写：

```text
执行状态：待验证
执行前要求：验证规范化与匹配完整性
```

不得继承旧轮次或作废分支中的 join 验证结果。

### 局部搜索空间输出

阶段结束时只输出：

```text
当前 Signal
候选维度
本体路径
三态判定
当前证据状态
激活理由
暂缓 / 淘汰理由
跨对象关系执行合同
最终局部搜索空间
```

本阶段不执行新 SQL，不生成复杂问题结论。

## 复杂问题

复杂问题只能从以下内容组合产生：

```text
已验证原子问题
真实 Signal
合法本体关系
阶段 9 已激活对象或维度
```

必须同时满足：

```text
原子存在
关系合法
主体兼容
粒度兼容
单位兼容
时间语义兼容
参数闭合
结构合法
当前 Signal 提供继续分析的理由
```

复杂问题阶段只负责形成一个可执行问题合同，不执行结果解释。

每个复杂问题至少明确：

```text
当前 Signal
新增对象或维度
本体路径
主体
指标
范围
状态
时间范围
比较对象
单位
不同结果会改变什么判断
关系执行前置条件
```

不得提前写“单主体驱动”“时间异常”“通道主导”等结果性结论。

如果关系执行前置条件仍为“待验证”，问题可以形成，但不能进入业务结果 SQL；下一阶段必须先完成关系验证。

### 多粒度指标防放大

如果查询同时使用多个原生粒度的指标（例如企业×年投资额与国家×年 GNP），先分别在原生粒度完成聚合，再按合法比较粒度连接。

执行前必须确认每张表的主键、时间覆盖和 Join 基数。执行后分别回算各指标的原表合计与 Join 后合计。如果不同，则不得直接使用 Join 后汇总值。

```text
同一日、年或国家值被复制到多条交易/用户/企业记录
≠
真实指标变大
```

不同粒度可以进行同年描述性对比，但共变不等于因果关系。

## 复杂问题真实验证

复杂问题形成后，必须单独进入真实验证阶段。

固定顺序：

```text
验证关系执行前置条件
执行复杂问题 SQL
取得真实 Result
执行结果一致性检查
说明能证明什么
说明不能证明什么
```

只有通过本阶段，才能进入竞争解释。

### 关系前置验证

跨对象问题必须先验证阶段 9 记录的执行合同，例如：

```text
join key 是否可安全规范化
是否存在 NULL / 非法值
是否存在 orphan
是否发生一对多放大
规范化后是否改变业务标识
```

关系验证失败时：

```text
复杂问题状态 = 执行失败
停止该分支
```

不得通过修改本体语义或隐式 CAST 强行通过。

### SQL 要求

SQL 必须直接对应复杂问题合同。

不得在 SQL 中临时增加：

```text
未激活维度
新阈值
新状态过滤
新时间窗口
新业务关系
```

枚举安全、单位兼容和时间语义继续遵守前述规则。

### Result 要求

至少记录：

```text
复杂问题
关系验证结果
实际 SQL
真实 Result
一致性检查
能说明什么
不能说明什么
```

如果查询无结果、失败或关系验证不通过，必须保留真实状态。

不得补造 Result。

### 竞争解释

只对已通过“复杂问题真实验证”的结果生成竞争解释。

先写清当前解释，再提出替代解释。**当前解释本身不是竞争假设。**

每个竞争解释必须：

```text
与当前解释不同
如果成立，会推翻或明显收缩当前解释
与已确认事实兼容
可以被数据区分
不依赖未登记关系
```

不要把“样本小、缺少历史基线、数据有限”等限制写成竞争解释。它们属于稳健性验证或结果边界。

已经被前序证据排除的解释不要重复验证。

每个竞争解释只记录：

```text
当前解释
替代解释
如果成立，会改变什么
最小区分证据
验证优先级
```

优先保留诊断性最强的 1–3 个解释。不要凑数量。

本阶段只定义竞争解释和区分证据。不要执行稳健性 SQL，不生成 Finding。

## 稳健性验证

只验证当前竞争解释需要的最小证据。

按问题选择检查。常见类型包括：

```text
单一主体或单笔记录驱动
极端值驱动
分母效应
数量与均值拆解
JOIN 放大
单位混用
时间口径
小样本敏感性
```

不要机械执行全部检查。

每个验证必须说明：

```text
验证哪个竞争解释
执行什么检查
结果是什么
当前解释被保留、收缩还是推翻
剩余限制是什么
```

没有真实验证结果，不得升级为 Validated Finding。

## Validated Finding

只有完成必要验证后，Signal 才能升级为 Validated Finding。

Finding 必须区分：

已确认事实、合理解释、仍未解决的问题、数据限制。

不得把相关性扩大为因果关系。

不得把单一主体、少量样本或短期现象扩大为整体规律。

## Decision Value

只有能够改变观察重点、调查顺序、资源配置、业务动作或管理判断的 Finding，才具有 Decision Value。

没有 Decision Value 的 Finding 不必进入 Dashboard。

## Dashboard

Dashboard 是结果呈现层，不是分析起点。

### 展示必要性 Gate

Decision Value 只是必要条件。还须逐项回答：

1. 谁会在什么决策场景使用？
2. 这是持续观察、定期复核，还是只有一次性的分析结果？
3. 数据粒度、分母、时间窗口和更新条件是否稳定？
4. Dashboard 是否比简短分析报告提供实质增量？
5. 哪些指标属于日常观察所必需，哪些只是研究过程中的验证细节？

上述条件不足时，返回 `不生成 Dashboard`，说明原因，保留可审计的 Finding 和分析报告。

如明确要求一次性分析型 Dashboard，可按交付要求展示已验证事实，但不得把历史样本推断成可持续监控指标。

不得为填满画面而加入图表、TopN、异常诊断过程或未经验证的指标。

### 展示内容

优先回答：

```text
发生了什么？
问题在哪里？
主要驱动是什么？
涉及哪些对象？
底层证据是什么？
下一步应该做什么？
```

不得从 KPI 卡片、饼图、柱图、TopN 或现成组件模板反推分析内容。

Dashboard 主要内容必须能回溯到具有 Decision Value 的 Validated Finding。

## 本体修正

真实验证发现必要原子缺失、关系定义错误、主体或粒度定义错误、稳定业务模式遗漏时，可以修正两张本体表。

必须说明原因和证据。

不得因为一次临时查询永久增加原子、关系或规则。

## 信息增量

只有下一步能够增加新事实、Signal、问题收敛、竞争解释验证、原判断修正或新合法分支时，才继续分析。

否则停止。
