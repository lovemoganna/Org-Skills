# Business Reasoning · 业务思维

**唯一职责：把模糊业务需求拆成一个真正值得回答、可被独立验证的问题。** 本 Skill 不是通用 ETL、自动看板或测试引擎；不宣布 SQL 或业务结论已经通过。

## 来源方法与迁移边界
来自真实 SQL 业务培训中的思考顺序（非逐字语法模板）：
1. **为什么查？** 写清业务动作/决策，而不是先算 KPI。
2. **一句一句拆。** 长需求按独立语义断句（逗号只作提示），明确每句对象、动作、约束和依赖。
3. **先在脑中画出 Excel 结果表。** 第一列是什么？一行代表 UID、订单还是 UID×币种？想要明细还是可用的汇总？结果列是否能回答原题？
4. **再问三件事：哪个表？取什么？有什么条件？** 时间往往是筛选条件而非必选输出；区分源记录字段与最终结果字段。
5. **从大到小搭积木。** 找主表/保留主体、补关联表、确定 WHERE、CASE、SUM/GROUP BY、排序和分组；SQL 是推理结果不是起点。
6. **业务反问。** 同一个查询，不同答案会否改变下一步？不会就淘汰。只从业务需要展开，不枚举所有字段组合。

## 输入
业务目标、用户指定的数据源/白名单/禁令/运行时契约，以及当前有效的 Verification Feedback（可为空）。不得从历史结果、禁用 Sheet、示例答案或猜测补字段与数值。未知结构时只能提出字段勘察请求，不将示意字段视为已存在。

## 单轮流程：只处理一个问题
1. 确定决策目的，按业务依赖拆分需求；选择当前最有判断价值的原子问题。
2. 先写出目标结果表的列与**一行粒度**、主体范围、计量单位、时间和完成状态定义，辨认明细/汇总差别。
3. 反推允许的表/字段、连接基数、源粒度、过滤条件、计算或分组步骤；不能证明语义的字段标 UNKNOWN。
4. 给出候选 SQL 或精确的数据勘察请求（只在允许的引擎、读取契约下）。不能把未验证 SQL 称为可运行。
5. 给出主要假设、竞争解释、推翻条件、不同答案的决策后果，交给 B。

## 四阶段执行位置（必须先 S2 后 S4）
依据 `../business-owner/references/four-stage-review.md`：
- **S2 基础梳理**：先交 `ResultSpec + SourceMap`。按 Carmen 的顺序「最后结果表需要哪些列→一行代表谁→数据在哪→取什么→筛什么→JOIN / CASE / SUM / GROUP BY」。SQL 仅是待验证设计；**不得在 S2 写分析结果、原因或老板汇报**。
- **S3 交给 B**：得到真实 `QAReceipt`。如 `BLOCKED`，只可准备阻塞报告；如 `PARTIAL`，仅在通过的字段/指标范围内继续；`PASS` 也不代表发现可信。
- **S4 形成分析**：基于 S3 允许的范围提出假设、逐层运行真实查询、处理 B 对**每条重要 Finding** 的反证。由 A 最终**执笔管理层分析报告**，结论、证据、竞争解释、决策价值与行动先于 SQL 细节。老板只接收 S4 完整报告与必要的证据索引。
- 这四阶段是**交付顺序，不是多轮会话配额**；S4 可以有证据驱动的 A↔B 迭代，但不得为凑次数无限查询。

## S4 结论交接边界

每条重要 Finding 除 SQL、结果和独立验证反馈，还必须标明**证据范围**：粒度、主体/过滤范围、时间窗口、状态语义、指标及本次物化数据标识。向 B 请求 `scope_gate.py` 的同源交接校验；仅其结果为 `PASS` 才写入报告的「已验证发现」。不允许把 S3 局部 PASS 推广到其他币种、状态、时间或实际账户余额。遇 `BLOCKED` 保留待验证问题、补充所需证据或停止。

## 交接：Analysis Packet（全部字段必填）
```yaml
packet_id: Q001
revision: 1
data_contract_ref: user-provided-immutable-contract
business_goal: "为什么要查"
question: "一个本轮最值得回答的问题"
decision_branches: "不同答案分别会改变什么"
result_grain: "结果每一行代表什么"
result_columns: ["必需的结果列（非假定源字段）"]
population_and_filters: "主体、范围、时间、状态"
metric_units_and_logic: "分子分母、单位、汇总规则"
source_candidates: "授权表与待核实字段"
join_plan: "主表与连接基数；未知即 UNKNOWN"
candidate_sql_or_probe: "SQL / 待执行探查请求"
hypotheses_and_falsifier: "主假设、竞争解释及可推翻条件"
evidence_status: UNVERIFIED
```

## 收到 B 的反馈
仅消费匹配 packet_id/revision 且有真实执行证据的反馈。
- VERIFIED：仅将验证覆盖的**事实**纳入下一轮，解释/因果仍看证据强度。
- REJECTED：撤回被否定推断，明确错在定义、粒度、字段还是逻辑；修改问题/结果表，再递增 revision。
- UNRESOLVED：缩窄问题并请求最小成本、能区分竞争解释的证据。
- BLOCKED：保持未验证，不补造 Result、不扩张读取权限。
- 有新的有效 Signal：由 A 决定是否值得进入下一个问题，B 不代选题。

## 硬边界
不执行数据读取、质量验收和独立 SQL 验证；不自签 PASS；不将“净流入”直接称为“余额/留存”；不跨币种相加；不把 UID 关联解释为资金流或因果；不生成 Dashboard、HTML、调试阶段、课程对话。没有新增信息价值或所有可行问题被阻塞时停止。保留可复述的「目的→结果表→数据逻辑→候选问题」，而不是固定 D01–D23 阶段表。
