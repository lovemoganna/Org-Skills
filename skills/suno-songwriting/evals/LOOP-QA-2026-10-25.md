## S2 TaskSpec

- `problem`：把长元提示变成有触发、路由、输入契约、产出、质检和可运行回归检查的 Skill。
- `necessary_conditions`：
  - N1：可识别触发场景和不适用边界。
  - N2：全曲创作、局部迭代、Style-only、音频对照互不覆盖。
  - N3：保留歌曲基本信息、完整歌词、Suno 复制粘贴文本和迭代标记。
  - N4：关键硬约束可检查，且不将静态检测包装成音乐试听。
  - N5：具备一轮有证据的 Loop 缺陷定位、修复和回归。
  - N6：不未经授权推送远程或修改现有生产 Skill。
- `scope.in`：Skill 文件、参考说明、输出模板、实例、测试脚本、QA 记录、ZIP。
- `scope.out`：远程 Git 提交/安装、音乐平台音频实际生成、独立外部试听、历史站点发布。
- `subtasks`：能力路由与契约；创作提示与模板；验收脚本与样例；Loop 审查与修复；打包。
- `deps`：Skill 规则 → 示例输出 → 验证 → 缺陷修正 → 回归 → 打包。
- `acceptance`：A1–A7（见 S4）。
- `risk`：任务路由膨胀、把草稿当实唱、AI 自评冒充独立 QA、发布越权。

## S3 ChainSpec

- `mode`: chain。
- `reason`: 命中 Loop 复杂度信号 ① 多个存在依赖的子任务、③ GitHub 读取与本地文件/测试需要不同工具；未编造独立评审者。
- `coverage`: A1/A2 由 SKILL.md 与引用覆盖；A3/A4 由实例与 CLI 测试；A5 由差异对照；A6 由修复复测；A7 由授权审查。
- `steps`：
  1. `source`：读取用户 Loop Skill 与仓库维护规范 → 规则依据；失败则停止声称“使用了 Loop”。
  2. `author`：编写独立 Skill、refs、案例 → 可安装目录；失败则修文件。
  3. `test`：跑样例/负例 → 失败证据；失败交给 S5 定位。
  4. `patch`：只修一个可复现缺陷 → 最小差异；失败停止而不宣称通过。
  5. `retest`：完整案例 + 局部案例 + 负例回归 → 测试回执；失败停止。
  6. `package`：归档并核对文件 → ZIP、QA 报告；失败不得提供下载链接。
