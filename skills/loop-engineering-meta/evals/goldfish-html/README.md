# Goldfish × Loop：真实代码任务配对实验（未完成）

## 目标和事实基线

验证在现有 `loop-engineering-meta` 编码流程前增加 **无历史上下文的 Goldfish 设计审查**，是否改善 Vibe Coding 的最终代码质量，且增量成本可接受。项目是用户真实的 `lovemoganna/Org-Skills` 中 `skills/html-design-lab`（Python 生成器 + 浏览器 HTML）。历史真实问题来自 2026-10-12 已合并的 PR #74，但**不能把这个历史 PR 的完成情况算成新实验结果**。

固定源仓库历史提交 `19c8488d1f2b199ea6dc937ba45d1a950d8e55f2`；两组都从该提交复制一份**独立、全新工作树**；执行者不得看到 PR #74 及后续源码，更不能检索已有的修复答案。验收者可以事后参考该 PR 校验目标相关性，但不能照搬补丁判断成败。使用 `cases.json` 中三类任务：原失败、历史功能不退化、边界泛化。三类任务每组至少 3 次，合计 **18 次真实代码执行**。

## 变量控制

| 要素 | 固定/变化 |
|---|---|
| 开始代码 | 同一 SHA 和完整依赖锁定 |
| 任务 | 两组输入逐字相同 |
| Agent | 同一种模型、版本、努力档、工具集、文件系统权限、预算上限 |
| CI | 同一 Python 版本、操作系统和 Chromium 版本 |
| 唯一区别 | 候选组在修改代码前执行 Goldfish 的独立设计审查 |
| 防泄露 | 审查者只有设计文档和公开任务契约，无原设计聊天及其他组结果 |
| 对抗复现 | worker 不接触 `judge.py`、PR #74 或别组工作树 |

同一 Agent 会话清理聊天记录但不隔离模型运行状态，不能声称“完全独立”。必须为每次 trial 创建新的执行会话与代码工作树。不能把手动复述三个角色写成“三个独立 Agent”。

## 双臂执行契约

**Baseline（现有 Loop）**：读取项目代码、冻结任务和基线，制定设计与验收，执行最小实现，运行现有测试，诊断修复，回归自检，提交工作树变更和日志。不得新增 Goldfish 环节。

**Candidate（Loop + Goldfish）**：采用完全相同任务和预算。完成初版设计后暂停改代码。向 **3 个全新会话**发送仅包含任务和独立设计文档的审查请求，各自从正确性、反例与工程风险提出缺陷（按证据注明）。汇总三份意见，修改设计并留下采纳/拒绝记录。然后从相同起点实现、测试、修复并回归。审查者不得写代码，不得共享评论或读设计聊天。若预算超限，按失败或未完成记录，不额外补跑。

对于 F01、R01、G01，**优先由任务执行者独立提出设计文档**，不能由对比实验主办者向候选组单独注入“正确答案”。若任务没有需要编码的变更，允许合法的最小修改或零修改，但要提交可以复现的结论和测试证据。

## 一次 trial 的必需证据

1. `run_id`、arm、case、worker/session ID、模型版本、冻结 SHA 和工具版本。
2. 开始/结束时间、使用量（如提供 `input_tokens`、`output_tokens`、`cost_usd`）；缺失时填写 `null`，不能猜值。
3. 任务输入与设计文档 SHA256；候选组的三个独立审查会话 ID、审查报告及设计修改差异。
4. 代码 diff、完整命令行与 stdout/stderr、CI 与浏览器报告；验收脚本返回码；测试结果不能只取最后一次成功而隐藏失败。
5. 环境信息、人工介入情况、退出原因和回滚路径。原始 trace 与 artifact 必须存在，可按路径追溯。

## 验收与统计

- **首次成功率**：首次提交给独立验收器时所有必要检查通过的次数 / 总 trial 次数（不能用修复三轮后的结果偷换）。
- **最终成功率**：预算内完成并通过独立验收的次数 / 总 trial 次数。
- **未检出缺陷**：独立验收器在最终产物中检测到但执行者未报告的可复现缺陷数量。仅有 3 个任务不能推断总体“缺陷漏检率”。
- **回归率**：原先通过的固定测试在最终产物中失败的 trial 数 / 全部 trial 数；记录失败用例和日志。
- **成本**：模型输入输出 token、官方计费/账单成本（若可读）和总耗时；额外三人审查时间必须计入候选成本。
- **裁决**：若真实 trial 缺失、隔离不可证、记录无法验证、候选存在新增关键回归，**不得提升 Skill**。3 次/组仅是探索性对照，不能声称统计显著。

## 执行方式

1. 主持人在隔离执行环境创建 18 个从 `frozen_start_sha` 复制的全新工作树，按随机但可追溯顺序运行两个 arm。打开 worker 前**不得公开验收脚本**。
2. 每个 trial 根据 `cases.json` 的一条任务生成设计文档（设计必须可脱离聊天阅读）。调用 `python3 -m unittest discover -s skills/html-design-lab/tests -v`；如有浏览器环境，再跑 `browser_review.py`。保存日志和 commit/diff。
3. 主持人对每份最终 artifact 使用 `judge.py <checkout> <case-id>` 独立评分，保留 JSON 文件与可复查的失败证据。评分脚本仅是静态/标准库部分验收；真正浏览器交互另用既有 Playwright 检查。未经浏览器复测不得宣称浏览器通过。
4. 把真实审查和执行日志整理成 `loop-engineering-meta/scripts/compare_trials.py` 所需的 record JSON，保留对应真实 artifact/trace/evidence 文件；该工具只校验记录形状，不能代替取证。
5. 对比首次成功/最终成功、未检出缺陷、回归和真实成本。仅在候选可重复改善且无关键回归时，才考虑向 `loop-engineering-meta` 提交小范围 Goldfish 可选门禁。否则保持原 Skill 不变。

**本文件是实验工具与执行契约，不是 18 次运行的结果。创建它或执行格式检查均不算真实 A/B。**
