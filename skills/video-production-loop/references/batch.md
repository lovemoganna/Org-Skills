# 批量与可恢复执行

## 批量计划

从 `assets/batch-plan.json` 创建真实计划。每条独立 job：id、主题、brief、输入 spec、profile、资产来源和输出目录。先验证重复 id、输出冲突、缺失源文件与总预算。

先完成一个有代表性的 pilot 再扩展剩余任务。若题材跨度很大，每一类选一个样片；pilot 技术/视听标准通过后才能共享它的模板决策。用户已认可的同类样片可以直接用，不重复设审批门槛。

目录建议：

```text
batch/
  plan.json
  jobs/<id>/
    project/                 各任务私有 spec/public/源码
    revisions/r001/          成片、证据、run-record.json
    revisions/r002/
    latest.json              仅指向通过本次验收的修订
  batch-report.json
```

每个 job 使用自己的工作目录。附带起点的 renders 日志名是固定的，多个任务不能共用一个 project 目录执行。缓存可共享，但不可变；不要把相同文件名当作内容相同。

## 调度与重试

- 默认一次渲染一个视频，单视频并发 2；根据 RAM/CPU/浏览器稳定性再调整。多个高并发渲染可能比串行更慢。
- TTS 默认串行，按服务的实际限制调并发；只重试暂时性错误。脚本时间上限与总批次预算都要明确。
- 有可用且获授权的多智能体能力时可分配独立 job；每个 agent 拥有独立输出路径，集成者负责最终验证。没有多智能体工具也能串行执行本 SOP。
- 单个内容错误隔离该 job，其他独立任务可继续；共享依赖失效时暂停依赖它的任务，不能每个任务反复撞同一个错误。

## 恢复与防止陈旧输出

保存每阶段状态、命令 argv、开始结束时间、实际退出码、文件哈希、当前问题。中断恢复先检查 artifacts 与 spec 的关联，不仅看状态字符串。

只要文本/voice/rate 改变，旁白缓存失效；剪辑区间/音量改变，混音失效；模板/字体改变，画面失效；渲染器依赖改变，至少做代表性回归。任何输入改变都产生新的 revision，不覆盖已交付版本。

失败的 stage 不能变成 verified。没有新文件或哈希仍对应旧配置时，标记 stale。批次成功数来自逐项验收记录，不来自启动命令数量。

最终清单包含每项 id、状态、成片路径、规格、来源、验证证据、未检查项和失败原因。成功任务先交付，失败任务明确隔离。恢复时只重新处理失败或依赖失效的项目。
