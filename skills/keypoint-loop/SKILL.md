# KeyPoint Loop｜问题关键点复用元 Skill

## 目标
用尽量少的试错找到**真正改变判断或结果的关键因素**，及时打断无信息增量的重复劳动，并记住下次可以复用的突破点。经验卡是手段，不是为了复盘而复盘。

## 何时使用
- 用户提供问题、处理过程、结果或复盘记录时：提炼可复用关键点。
- 用户提供多条经验时：识别同类，合并重复方法，保留重要差异。
- 用户遇到新问题时：先匹配已有方法；条件不符则不套用。
- 原始材料不足时：明确缺口，允许输出「待验证」，不能补造事实。

## 输入
当前问题及已知事实、采取的行动、观察到的结果；如有，附历史经验卡。
不用要求用户填表。优先从现有上下文提取。

## 突破点雷达（四种方法，只在必要时调用）

先问：「**眼下哪个判断/行动被什么卡住？**」再从以下四个角度快速检查；**不是每次跑四套分析**，没有信息增量就停止。

1. **识别对象（第一性原理 / 轻量本体）**：拆开真实对象、指标、字段维度、时间窗口、状态及其关系；标签、告警名、规则名不是结论。特别检查存量与流量、总量与净量、策略状态与运行环境、相关与因果是否被混用。**矛盾须属于同一对象、同一维度、同一适用范围下的互斥事实**；不同维度字段并存不等于矛盾。例如「本窗口无新增入金却有交易」并不自相矛盾（可能使用历史资产）；「策略状态为模拟、系统环境在线」也不自动矛盾。除非有字段定义和事实证据，不得断言混入、污染或真实线上拦截。
2. **挑战前提（竞争假设 / 反事实）**：当前解释之外，哪一个*最有力的替代解释*也能产生同样现象？什么证据可区分两者？不能靠「没观察到」推导「不存在」。**观测到口径变化/限制因素 ≠ 已证实其造成全部结果**；没有同口径重算、干预对照或等价验证时，原因与改善效果一律标为待检验。
3. **找限制因素（约束理论）**：不是挑最显眼的异常，而是找**最先妨碍正确决策的必要事实、约束或依赖**；优先一个成本低、能推翻错误方向的验证动作，不假设复杂问题必有单一根因。
4. **及时换思路（双环学习 / 案例推理）**：如果继续同一动作不能产生新证据、修正假设或改变结果，应停止重复，重新审查问题定义/前提/方法；从已证实旧案例中找同机制先例，成功和失败教训都可复用。

**关键点选择门槛**：验证或推翻这条信息后，判断、行动或结果会改变吗？如果不会，它只是背景；如果可能会但未验证，标「候选突破点」而非真因。不必强求「终极本质」，把下一步行动缩小到最有信息增量的一步。

## Loop：捕获 → 逆推 → 归并 → 封装 → 复测

1. **捕获**：明确真实目标、当前卡点、已试动作、实际结果；用「关键点选择门槛」筛掉热闹但不改变行动的信号。未观察到结果变化时，只能标「候选突破点」。
2. **逆推**：从观察到的变化倒查：哪个前提被证实/否定，什么证据改变了判断，什么因素实际阻碍行动？至少挑战一个足以改变结论的替代解释；没有结果或来源证据，不补造成功原因。
3. **归并**：先分清每案究竟是「概念/定义错误」「真实世界的证据缺口」「执行故障」「结果未达成」中的哪一种；层级不同通常不能合并。**仅凭缺少日志、配置或状态字典，不能判为执行故障**；必须存在实际失败动作和可追溯的失败证据。只有底层障碍或已证实机制、关键动作、验证方式、适用条件**逐项相同**才合并，任何一项不同仅建立关联。**「都缺数据」「都提同一名词」「都需要核实」「先找约束」「减少盲目努力」不是同因同法**；概念定义已改正，不必凭实际业务记录才能确认定义正确，真实行为存在与否另行核验。**归并门槛：先为各案提取具体签名〈已证实的障碍机制、可复用的具体动作、实际验收证据、适用前提〉；任一项不能匹配或机制仍未知，默认只建立关联，不合并。**例如，统计单位误把事件数当人数，与实体工序的产能瓶颈不是同机制；两个领域都把事件数当去重主体数，且同样通过重算验证，才可合并。
4. **封装**：写成「遇到【可观察触发条件】→先核对【关键前提/反证】→做【最小有效动作】→看【可复查结果】；若【失败信号】则停止/改路」。若根本没有解决问题，只保存「避免走错路」或下一步测试，不伪装成成功诀窍。
5. **复测**：用独立的新案例或反例尝试迁移；区分「原问题已修复」「同类方法在新案中复现」「跨领域泛化已验证」。**合成/假设案例即使内部给出修复结果，也只证明该设定下推理成立，不算真实业务验证或生产有效。**单次成功不等于已验证通用方法；无法执行时明确缺口，不自报通过。

## 输出（只展示有价值的信息）
**本次突破点**
- 问题/卡点：
- 关键证据或动作：
- 观察到的结果：
- 作用机制：已证实 / 推断 / 未知；能改变哪一项判断或行动：

**可复用方法卡**
- 名称：
- 适用信号与前提：
- 最小操作：
- 验证标准（什么结果会证伪本方法）：
- 不适用/反例：
- 来源案例：
- 状态：候选 / 单案有效 / 迁移已验证 / 有冲突

**归并结果**
- 新增 / 合并入【旧方法】 / 拆分【旧方法】 / 不归档
- 归并依据与重要差异：一句话

## 硬规则
- 事实、推断、未知分开；不编造结果、数字、证据或因果。**复述前逐项核对原始数值、单位、时间窗、方向箭头、指标粒度和字段名**；同一案例的次数/金额不得迁移到另一案例。不要把「计数单位变化」扩写为「分子分母变化」，也不要把 C→A 写成 A→C。
- 「做过」不等于「有效」；「结果变好」不等于「该动作导致结果变好」。区分「概念正确」「事实已查实」「操作已修复」「方法可迁移」，不得混为一谈。
- 不为凑分类强行合并；优先比较已知机制、动作、验证方式与边界，不按行业名词或表面相似度合并。
- 一条方法卡只解决一个可识别的问题；默认简短，只有关键限制不能删。
- 已有经验库时仅更新新增、修订或冲突的部分，保留来源；没有可访问的持久存储时只输出卡片，不声称已保存。
- 遇到无信息增量的重复尝试，必须指出为何该停/该换方向，并给出最小可验证动作；不能机械规定失败次数。
- 用户没要求完整复盘时，不扩展成报告、不建立评分体系、不添加多余流程。

## 快速调用
「用 KeyPoint Loop 处理以下材料：先找可能推翻当前思路的关键前提/反证，锁定最省力的突破点；无信息增量就停止旧方向；再与已有经验按机制和验证方式归并，输出最短可执行方法卡。未知不编造。」

## 自检
输出前确认：
1. 关键点是否能指向材料中的具体事实或动作？数字、单位、路径方向和口径是否忠实原文？
2. 解释是否把推断伪装成因果？尤其不能把口径/配置变化直接写成指标变化的唯一原因，或把名义产能数字当成已测量的实际效果。
3. 合并是否满足同因同法，是否保留例外？
4. 是否把不同维度字段并存误当矛盾，或把没有证据误当没有发生？只有同一属性在相同条件下互斥才叫矛盾。
5. 合并前是否逐项确认问题层级、障碍、动作、验证方式、边界完全相容？共享术语或缺数据即合并，应判失败。
6. 是否明确最小验证动作、停止条件，且没有把单案效果说成通用效果？
7. 下次遇到同类问题，读卡片的人能否立即执行并判断有效性？
任一项失败，降低结论强度或不封装。
