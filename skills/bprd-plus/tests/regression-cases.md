# bprd-plus Regression Cases

## 原失败样本：DuckDB Editor Pro 执行计划重构

输入是一份复杂系统重构需求，包含 Structured Plan、Profiling、Execution Model、Auto Layout、HTML Node + SVG Edge、Explain / Data / Cost Lens、Operator Registry、性能指标语义、失败隔离和未知算子兼容要求。

验收：

1. 默认 BRD 只保留目标、当前问题、方案与系统行为、约束与边界、验收标准、待确认六类信息。
2. 不输出材料解析过程、泛化推理过程、自检过程或方法论说明。
3. 不丢失用户给出的技术事实和硬约束。
4. 不把当前 SQL、已知算子、固定拓扑或当前指标集写成系统边界。
5. 未提供的项目文件名、组件名、接口和字段必须标记待确认或留给执行阶段扫描。
6. 最终结果必须明显短于旧版完整 Phase 输出，但仍可直接交给 Vibe Coding Agent 执行。

## 历史通过样本：风控事件接入

输入涉及 AML、Fraud、制裁、交易监控、RFI、STR 或策略事件。

验收：

1. 读取 `references/risk-control.md`。
2. 保留 Trigger、Input、Output、Data Source、Decision、Action、Evidence 所需信息。
3. 不因为主 Skill 精简而丢失风控字段、处置或证据要求。
4. 仍使用主 Skill 的短 BRD 结构，不把风控检查过程写进正文。

## 泛化样本 A：非风控系统改造

输入是编辑器、可视化、数据库、编译器或其他软件模块重构。

验收：

1. 不生成 AML、Fraud、RFI、STR 等无关章节。
2. 先提取系统不变量和变化维度，再写系统行为。
3. 新类型、缺失字段、结构变化和失败状态必须有兼容、降级或拒绝规则。

## 泛化样本 B：规范标准类需求

输入要求统一命名、分类、人工操作或执行标准。

验收：

1. 重点输出定义、规则、边界和验收。
2. 不强行展开系统架构、字段模型或风控事件模型。

## 泛化样本 C：信息缺失但不阻塞

输入缺少负责人、最终文件名、具体组件名等不影响核心需求成立的信息。

验收：

1. 使用“待确认”标记。
2. 继续生成可执行 BRD。
3. 不因为存在非阻塞缺口强制停止等待用户确认。

## 泛化样本 D：关键事实缺失

输入缺失会直接改变目标、范围或核心行为的关键事实，且无法从提供材料或工具确认。

验收：

1. 明确指出阻塞项。
2. 不自行补造。
3. 只有确实无法继续形成正确 BRD 时才停止。

## Compactness 回归

任何 BRD 完成后执行：

1. 同一事实只保留一次。
2. 删除不改变开发、测试、验收、边界或证据判断的句子。
3. 删除“进一步提升、有效促进、从而实现”等空泛价值句。
4. 内部分析、路由、泛化和反例过程默认不进入正文。
5. 不能为了变短删除事实、技术细节、约束或验收条件。
 
## 多来源需求冲突

输入同时保留旧约束（继续使用 Chart.js）和新反馈（改用 ECharts），未说明授权优先级。

验收：

1. 同时保留双方来源，不悄悄选择任一方案。
2. 说明该冲突影响技术栈和实施范围；仅阻塞相关部分。
3. 未冲突的扫描、格式一致性和验收条件继续编写。
4. 不编造项目当前实现。

## 验收证据边界

输入只有“修复全项目可视化缺陷”的任务描述，未给代码、运行结果或测试记录。

验收：

1. 可以编写验收方法，不得写成“已修复”“已验收”。
2. 缺失的实施与复验证据标记待核验。
3. 只因结构检查或构建通过，不得宣称实际业务质量通过。
