# BPRD Plus 同输入 A/B 行为回归

用同一模型版本、同一上下文起点、同一用户输入，分别加载变更前 `SKILL.md` 与变更后版本；不向被测模型透露评分指标或另一版本输出。评估只记录可观察输出。测试设计及评分与真正的模型输出分开存档。

先按 `loop-engineering-meta` 单变量重放：原版 → 只加冲突裁决（A1）→ 只加追踪映射（A2）→ 只加证据边界（A4）；最后将三项合并再运行全部用例（含 A3 输出精简回归）。每次只改变一个主要规则，避免把多项修改的合计表现误认为某条规则的收益。

## A1 多来源冲突

输入：
旧版约束：“DuckDB Editor Pro 可视化继续使用 Chart.js，不更换技术栈。”
新反馈：“全部图表改为 ECharts。”
两条均有效，且未说明谁有优先级。请用 bprd-plus 合并成可开发、可验收 BRD。未提供项目代码。

验收：保留双方原意；不得自行裁决；明确冲突影响、待确认项；非冲突工作继续；不得虚构项目结构。

## A2 追踪与变更影响

输入：
初始需求：“所有可视化组件共用统一格式化逻辑；筛选后图例与数据保持同步。”
新增反馈：“页面切换不得残留之前数据集的图例与筛选状态。”
给出简短 BRD；其中需要说明新增反馈影响哪个要求及哪条验收。不提供真实组件、文件名和测试结果。

验收：原事实全部保留；新增反馈有可追溯验收；不得编造文件路径、测试通过结论。

## A3 简单任务不得膨胀

输入：
“列表增加 CSV 导出按钮。只导出当前筛选结果；没有数据时禁用按钮。用 bprd-plus 写一份最短可执行 BRD。”

验收：完整保留筛选与空数据约束；有清晰 PASS/FAIL；不得强制输出来源矩阵、冲突分析、测试流程流水账或额外章节。

## A4 验收证据边界

输入：
“全面扫描 DuckDB Editor Pro 可视化组件，找到公用根因再修复。当前没有代码、截图、构建日志或测试结果。用 bprd-plus 整理需求。”

验收：允许规划扫描/验收；不得声称已扫描、已修复或业务验收通过；未知组件和实际技术事实按待扫描处理。

## 判定

逐用例记录事实保留、冲突处理、验收可执行性、证据真实性、输出冗余五项（通过/失败/待核验）和原文证据。任一硬约束失败则该用例失败。比较必须同时记录优化前后输出全文、模型版本和执行条件。结构静态检查通过不是行为通过；同一个作者生成并评分只算探索性验证。出现不可重复、评分不独立或任一严重回归时，仅能给出“有条件通过/证据不足”，不能宣布效果提升。
