# BPRD Plus

## 目标

把非结构化业务输入编译成结构化、可验证、可追踪的风控 BRD。

核心链路：

`材料 → 事实 → 需求 → 概念/字段 → 系统行为 → 验收标准 → 生命周期`

不要把任务理解为“润色一份 BRD”。先理解需求，再建模，再生成，再独立验证。

## 适用输入

支持：

- 会议纪要
- 需求描述
- 领导口头或书面反馈
- 旧版 BRD
- PRD
- 接口文档
- 原型/截图说明
- 历史方案
- 数据字段说明

如果输入是文件，先读取文件内容；不要根据文件名猜测内容。

## 核心原则

1. 事实优先。不得补造表名、字段名、接口、数据、规则、负责人或结论。
2. 缺失信息使用“待确认”标记，不用模型推测替代。
3. 区分事实、推论、假设和待确认项。
4. 需求边界必须明确包含和不包含什么。
5. 风控需求必须落到事件、字段、决策、处置和证据。
6. 复杂需求先拆概念，再决定字段。
7. 字段类型必须同时满足业务语义、API 类型和 SQL 类型约束。
8. 生成者不能验收自己的结果。
9. 修改已有 BRD 时优先定向修改，不无理由重写整篇。
10. 不改变用户原始事实、数据、立场和约束。
11. 高风险动作先检查权限、影响范围和安全边界。
12. 连续两轮没有有效状态变化时停止并报告阻塞。

## BRD 类型路由

先判断需求类型：

### Type A：事件接入型

适用于把新的风控事件或策略接入系统。

重点：

`Event → Trigger → Input → Output → Data Source → Risk Usability`

### Type B：系统改造型

适用于现有系统存在结构性问题，需要系统或流程改造。

重点：

`现状 → 核心矛盾 → 修正方案 → 系统改造 → 数据字段 → 人工规范 → AI规范 → 验收`

### Type C：规范标准型

适用于统一业务口径、人工操作、分类体系或执行标准。

重点：

`现状差异 → 标准定义 → 执行规则 → 边界 → 验收`

## Phase 1：材料解析与信息提取

### Step 1：材料解析

识别：

- 材料类型
- 核心需求主题
- 可直接使用的信息
- 明显缺失的信息
- 是否存在旧版 BRD
- 是否存在历史方案
- 是否存在数据或技术材料

输出材料清单后停止，等待确认。

### Step 2：八维度信息提取

逐项检查：

| 维度 | 核心问题 |
|---|---|
| 需求来源 | 谁提出？是否有书面记录？ |
| 需求动机 | 为什么现在做？不做有什么后果？ |
| 需求边界 | 本版本做什么？明确不做什么？ |
| 现状调研 | 系统是否已有相关功能？ |
| 数据现状 | 数据来源、表、字段、负责人是否明确？ |
| 技术可行性 | 是否与开发进行初步确认？ |
| 依赖关系 | 是否依赖其他项目、团队或系统？ |
| 风控专项 | 事件、字段、决策、处置、合规约束是什么？ |

缺失信息明确写：

`[待确认：具体缺口]`

输出缺口清单后停止，等待确认。

## Phase 2：BRD 生成

在 Phase 1 确认后生成 BRD。

顺序：

1. 读取适用模板和字段规则。
2. 根据 Type A/B/C 路由结构。
3. 对字段执行业务语义建模。
4. 写出需求背景、问题、目标、范围、方案、系统需求、数据字段、依赖、验收等内容。
5. 所有无法从材料确认的信息保留“待确认”。
6. 不用空泛价值描述替代具体需求。
7. 不为了完整而虚构内容。

### 字段建模

每个关键字段至少确认：

- 业务名称
- 字段含义
- 数据来源
- 是否必填
- 空值规则
- 枚举/取值范围
- API 类型
- SQL 类型
- 精度/单位
- 计算逻辑
- SQL 使用方式

金融金额、比例、时间、ID、枚举、布尔值等必须按实际语义选择类型。

## Phase 2.5：去 AI 味

正文应：

- 直接描述事实和问题
- 直接说明方案
- 删除空泛的“进一步提升”“有效促进”“从而实现”等套话
- 不改变事实、结论和需求边界
- 不为了降低 AI 味而丢失关键条件

“去 AI 味”只能改变表达，不得改变业务含义。

## Phase 3：独立自检

生成完成后，不得直接宣布完成。

独立检查：

### A. 风控可用性

- 需求是否能指导实际风控执行？
- 事件是否明确？
- 字段是否足够支持判断？
- 决策和处置是否明确？
- 证据和留痕要求是否明确？

### B. 结构完整性

- 背景、问题、目标、范围是否一致？
- 方案是否解决核心问题？
- 系统需求是否可开发？
- 验收标准是否可验证？
- 是否存在前后矛盾？

### C. 数据与字段

- 字段是否有明确业务含义？
- 类型是否与业务语义一致？
- 枚举是否完整且可验证？
- 数据来源是否明确？
- 是否存在类型冲突或字段语义过载？

### D. 待确认项

检查所有“待确认”：

- 是否确实来自材料缺口？
- 是否已经在其他章节得到确认？
- 是否有可以直接从材料得到的答案却错误标记为待确认？

### E. 改造型专项

Type B 必须额外检查：

`现状问题 → 改造方案 → 系统行为 → 数据变化 → 人工行为 → AI行为 → 验收`

必须形成闭环。

## 生命周期

需求对象状态：

`incoming → refined → active → released`

废弃需求进入：

`archived`

每次正式修改保留变更记录。

已归档 BRD 收到新反馈时：

- 不重跑完整 Phase 1
- 读取当前 BRD 和变更上下文
- 定位受影响章节
- 定向修改
- 版本号递增
- 再执行必要的自检

## 领导反馈

当用户提供领导反馈：

1. 判断当前 BRD 状态。
2. 草稿阶段：回到 Phase 2 定向修改。
3. 已归档：进入迭代子流程，不重跑 Phase 1。
4. 保留领导反馈对应的修改原因。
5. 不把一次性反馈扩大成无依据的永久规则。

只有用户明确表示“以后都这样”等长期规则时，才将其视为可沉淀的规范。

## 调用行为

### 完整流程

用户可以说：

`用 bprd-plus 根据以下材料写 BRD：<材料>`

执行：

`Phase 1 → 确认 → Phase 2 → 确认 → Phase 3 → 确认 → 归档`

### 指定文件

`用 bprd-plus 针对这个文件写 BRD：<文件>`

直接读取指定文件，跳过无关材料扫描。

### 继续

`用 bprd-plus 继续写 BRD`

从当前草稿状态继续，不重复已经完成且已确认的阶段。

### 自检

`用 bprd-plus 自检这份 BRD`

只执行独立验证，不重写正文。

### 定向修改

`用 bprd-plus 按下面的反馈修改 BRD：<反馈>`

只修改受影响章节，并重新执行相关验证。

## 输出要求

默认采用结论先行、短句、明确动作的中文表达。

不要：

- 编造事实
- 编造数据
- 编造技术实现
- 用长篇背景掩盖问题
- 重复用户已经明确的信息
- 为了“看起来完整”填充无意义内容
- 把推测写成事实

最终结果必须让产品、研发、测试和风控能够继续执行，并且能够回溯每个关键结论的来源。

## 工作协议

每一轮执行遵循：

`Intent → Boundary → State → Plan → Act → Observe → Verify → Decide → Compact → Continue/Stop`

其中：

- Intent：用户真正要解决的问题
- Boundary：本轮做什么、不做什么
- State：事实、证据、假设、缺失信息、阻塞
- Plan：最小有效动作
- Verifier：独立验收标准
- Stop Condition：成功、失败、超预算或无进展时停止

工具输出必须验证后才能作为结论。
