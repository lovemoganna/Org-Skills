# BPRD Plus

## 目标

把非结构化业务输入编译成结构化、可验证、可追踪的风控 BRD。

核心链路：

`材料 → 事实 → 需求 → 问题空间/不变量 → 概念/字段 → 系统行为 → 验收标准 → 反例验证 → 生命周期`

不要把任务理解为“润色一份 BRD”。先理解需求，再建模，再生成，再独立验证。

## 适用输入

支持：

- 会议纪要
- 需求描述
- 领导口头或书面反馈
- 旧版 BRD
- PRD
- 接口文档
- 原型/截图说明
- 历史方案
- 数据字段说明

如果输入是文件，先读取文件内容；不要根据文件名猜测内容。

## 核心原则

1. 事实优先。不得补造表名、字段名、接口、数据、规则、负责人或结论。
2. 缺失信息使用“待确认”标记，不用模型推测替代。
3. 区分事实、推论、假设和待确认项。
4. 需求边界必须明确包含和不包含什么。
5. 风控需求必须落到事件、字段、决策、处置和证据。
6. 复杂需求先拆概念，再决定字段。
7. 字段类型必须同时满足业务语义、API 类型和 SQL 类型约束。
8. 生成者不能验收自己的结果。
9. 修改已有 BRD 时优先定向修改，不无理由重写整篇。
10. 不改变用户原始事实、数据、立场和约束。
11. 高风险动作先检查权限、影响范围和安全边界。
12. 连续两轮没有有效状态变化时停止并报告阻塞。
13. 样例不是需求边界。不得把当前案例、截图、SQL、事件或字段组合直接当成系统的完整问题空间。
14. 先识别变化维度和稳定不变量，再写系统方案；不得先按样例设计，再用更多样例补洞。
15. 未知类型、缺失字段、边界状态和未来扩展必须有明确的兼容、降级或拒绝策略。
16. 示例只用于说明和回归，不得成为核心逻辑的硬编码前提。
17. 验收必须同时覆盖原样本、结构性反例和未知输入；只通过当前样本不得宣布完成。

## BRD 类型路由

先判断需求类型：

### Type A：事件接入型

适用于把新的风控事件或策略接入系统。

重点：

`Event → Trigger → Input → Output → Data Source → Risk Usability`

### Type B：系统改造型

适用于现有系统存在结构性问题，需要系统或流程改造。

重点：

`现状 → 核心矛盾 → 修正方案 → 系统改造 → 数据字段 → 人工规范 → AI规范 → 验收`

### Type C：规范标准型

适用于统一业务口径、人工操作、分类体系或执行标准。

重点：

`现状差异 → 标准定义 → 执行规则 → 边界 → 验收`

## Phase 1：材料解析与信息提取

### Step 1：材料解析

识别：

- 材料类型
- 核心需求主题
- 可直接使用的信息
- 明显缺失的信息
- 是否存在旧版 BRD
- 是否存在历史方案
- 是否存在数据或技术材料

输出材料清单后停止，等待确认。

### Step 2：八维度信息提取

逐项检查：

| 维度 | 核心问题 |
|---|---|
| 需求来源 | 谁提出？是否有书面记录？ |
| 需求动机 | 为什么现在做？不做有什么后果？ |
| 需求边界 | 本版本做什么？明确不做什么？ |
| 现状调研 | 系统是否已有相关功能？ |
| 数据现状 | 数据来源、表、字段、负责人是否明确？ |
| 技术可行性 | 是否与开发进行初步确认？ |
| 依赖关系 | 是否依赖其他项目、团队或系统？ |
| 风控专项 | 事件、字段、决策、处置、合规约束是什么？ |

缺失信息明确写：

`[待确认：具体缺口]`

输出缺口清单后停止，等待确认。


## Phase 1.5：泛化建模（Generalization Gate）

Phase 1 完成后，在写 BRD 前先判断当前材料描述的是“单一案例”还是“可重复出现的问题类型”。

只要需求涉及系统能力、规则、UI、流程、数据模型、事件类型、策略类型或未来可扩展对象，就必须执行本阶段。纯一次性人工任务可以标记“不适用”，但必须说明原因。

### Step 1：区分样例与问题空间

明确：

- 当前材料中的具体样例是什么
- 样例代表的对象类型是什么
- 哪些信息只是本次实例值
- 哪些要求必须对同类对象普遍成立
- 哪些情况明确不在本版本范围内

不得用“支持所有”替代边界定义。应写成可验证的能力边界，例如：

`对于系统能够返回结构化输入的任意实例，统一进入同一模型和处理链路；未知类型采用明确降级，不要求预先穷举全部类型。`

### Step 2：识别变化维度

至少检查：

| 变化维度 | 核心问题 |
|---|---|
| 类型 | 是否会出现新事件、新算子、新状态、新类别？ |
| 结构 | 层级、分支、组合、嵌套、顺序是否会变化？ |
| 字段 | 字段是否可选、缺失、新增、改名或类型变化？ |
| 数量 | 0、1、多条、大规模输入时是否仍成立？ |
| 状态 | 成功、失败、部分成功、未知、空数据如何处理？ |
| 版本 | 上游系统或协议升级后是否需要改核心逻辑？ |
| 边界 | 哪些输入应兼容、降级、拒绝或标记待确认？ |

不适用的维度可以跳过，但不得因为当前样例未出现就默认不存在。

### Step 3：提取系统不变量

把需求改写为不依赖具体样例值的系统契约。

每条不变量至少说明：

- 适用对象
- 必须始终成立的行为
- 允许变化的部分
- 未知输入如何处理
- 失败时如何降级
- 如何验收

示例：

`未知类型可以缺少增强解释，但不得导致核心结构解析和基础展示失败。`

### Step 4：过拟合检查

出现以下任一情况时，禁止直接进入 Phase 2：

- 核心逻辑依赖某个样例中的固定顺序
- 为每个新类型都需要修改核心流程
- 可选字段被当成必填字段
- 当前示例中的数量、层级或结构被写死
- Registry、枚举或映射表被错误地当成系统能否运行的前置条件
- 验收只描述“这个样例能跑通”

必须先把这些依赖抽象为数据驱动、结构驱动、能力边界或明确拒绝规则。

### Phase 1.5 输出

进入 Phase 2 前，必须得到：

`对象 → 变化维度 → 稳定不变量 → 未知输入策略 → 边界 → 泛化契约`

如果无法形成泛化契约，明确标记阻塞或待确认，不得用具体样例假装通用方案。

## Phase 2：BRD 生成

在 Phase 1 确认后生成 BRD。

顺序：

1. 读取适用模板和字段规则。
2. 根据 Type A/B/C 路由结构。
3. 读取 Phase 1.5 的泛化契约；系统行为先按不变量编写，再使用样例说明。
4. 对字段执行业务语义建模。
5. 写出需求背景、问题、目标、范围、方案、系统需求、数据字段、依赖、验收等内容。
6. 示例必须标明其说明性质，不得把示例值、固定顺序或已知类型写成系统前提。
7. 所有无法从材料确认的信息保留“待确认”。
8. 不用空泛价值描述替代具体需求。
9. 不为了完整而虚构内容。

### 字段建模

每个关键字段至少确认：

- 业务名称
- 字段含义
- 数据来源
- 是否必填
- 空值规则
- 枚举/取值范围
- API 类型
- SQL 类型
- 精度/单位
- 计算逻辑
- SQL 使用方式

金融金额、比例、时间、ID、枚举、布尔值等必须按实际语义选择类型。

## Phase 2.5：去 AI 味

正文应：

- 直接描述事实和问题
- 直接说明方案
- 删除空泛的“进一步提升”“有效促进”“从而实现”等套话
- 不改变事实、结论和需求边界
- 不为了降低 AI 味而丢失关键条件

“去 AI 味”只能改变表达，不得改变业务含义。

## Phase 3：独立自检

生成完成后，不得直接宣布完成。

独立检查：

### A. 风控可用性

- 需求是否能指导实际风控执行？
- 事件是否明确？
- 字段是否足够支持判断？
- 决策和处置是否明确？
- 证据和留痕要求是否明确？

### B. 结构完整性

- 背景、问题、目标、范围是否一致？
- 方案是否解决核心问题？
- 系统需求是否可开发？
- 验收标准是否可验证？
- 是否存在前后矛盾？

### C. 数据与字段

- 字段是否有明确业务含义？
- 类型是否与业务语义一致？
- 枚举是否完整且可验证？
- 数据来源是否明确？
- 是否存在类型冲突或字段语义过载？

### D. 待确认项

检查所有“待确认”：

- 是否确实来自材料缺口？
- 是否已经在其他章节得到确认？
- 是否有可以直接从材料得到的答案却错误标记为待确认？

### E. 改造型专项

Type B 必须额外检查：

`现状问题 → 改造方案 → 系统行为 → 数据变化 → 人工行为 → AI行为 → 验收`

必须形成闭环。

### F. 样例过拟合

检查：

- 是否把当前案例当成完整需求边界？
- 是否存在固定类型、固定顺序、固定层级、固定数量等隐含假设？
- 是否只有已知类型才能进入核心流程？
- 可选指标或字段缺失时是否会破坏主流程？
- 示例是否被错误写成实现规则？
- 验收是否只证明当前样例通过，而没有证明系统契约成立？

任一答案存在风险时，不得宣布 BRD 完成，必须回到 Phase 1.5 修正泛化契约。


## Phase 3.5：反例与泛化验证（Counterexample Gate）

Phase 3 通过后，必须主动尝试证明 BRD 会失败，而不是继续证明当前样例正确。

### A. 原失败样本

重新执行最初暴露问题的输入，确认修复没有丢失原始需求。

### B. 结构性反例

根据 Phase 1.5 的变化维度至少选择三类反例。优先检查：

- 单元素与多元素
- 深层与宽分支
- 空输入与缺失字段
- 未知类型
- 极端数量或边界值
- 顺序变化
- 部分成功或部分数据可用
- 上游增加新类型但核心契约不变

反例必须改变“结构或能力条件”，不能只替换名称和数值。

### C. 未知输入测试

对未来未知类型执行验证：

- 核心流程是否仍能运行？
- 是否可以安全降级？
- 是否保留原始证据？
- 是否只失去增强能力，而不是整个功能失效？
- 是否需要修改核心架构才能接入本应兼容的新类型？

如果每新增一个同类对象都必须修改核心架构，则判定泛化失败。

### D. 验收分层

验收标准必须区分：

1. **不变量验收**：任何边界内输入都必须成立。
2. **代表性样例**：验证常见业务场景。
3. **反例验收**：验证缺失、未知、极端和结构变化。
4. **边界外行为**：明确拒绝、降级或待确认。

不得用“列出更多样例”替代不变量验收。

### E. 类型专项

Type A：至少验证新事件类型、字段缺失或新数据源时是否仍符合事件契约。

Type B：至少验证输入结构、状态、规模或版本变化后，系统核心模型是否仍成立。

Type C：至少验证边界案例、例外情况和新增分类是否仍符合标准定义。

### 判定

只有以下条件同时满足才通过：

- 当前样例通过
- 泛化契约没有被反例推翻
- 未知输入存在明确处理方式
- 新增同类对象不要求重写核心架构
- 验收标准覆盖不变量，而不是只覆盖示例

失败时回到 Phase 1.5 或 Phase 2 定向修正，再重新验证。

## 生命周期

需求对象状态：

`incoming → refined → active → released`

废弃需求进入：

`archived`

每次正式修改保留变更记录。

已归档 BRD 收到新反馈时：

- 不重跑完整 Phase 1
- 读取当前 BRD 和变更上下文
- 定位受影响章节
- 定向修改
- 版本号递增
- 再执行必要的自检

## 领导反馈

当用户提供领导反馈：

1. 判断当前 BRD 状态。
2. 草稿阶段：回到 Phase 2 定向修改。
3. 已归档：进入迭代子流程，不重跑 Phase 1。
4. 保留领导反馈对应的修改原因。
5. 不把一次性反馈扩大成无依据的永久规则。

只有用户明确表示“以后都这样”等长期规则时，才将其视为可沉淀的规范。

## 调用行为

### 完整流程

用户可以说：

`用 bprd-plus 根据以下材料写 BRD：<材料>`

执行：

`Phase 1 → 确认 → Phase 1.5 → Phase 2 → 确认 → Phase 3 → Phase 3.5 → 确认 → 归档`

### 指定文件

`用 bprd-plus 针对这个文件写 BRD：<文件>`

直接读取指定文件，跳过无关材料扫描。

### 继续

`用 bprd-plus 继续写 BRD`

从当前草稿状态继续，不重复已经完成且已确认的阶段。

### 自检

`用 bprd-plus 自检这份 BRD`

执行 Phase 3 和 Phase 3.5。默认不重写正文；若发现样例过拟合，明确指出被哪个反例击穿，并给出应回到 Phase 1.5 修正的契约。

### 定向修改

`用 bprd-plus 按下面的反馈修改 BRD：<反馈>`

只修改受影响章节，并重新执行相关验证。

## 输出要求

默认采用结论先行、短句、明确动作的中文表达。

不要：

- 编造事实
- 编造数据
- 编造技术实现
- 用长篇背景掩盖问题
- 重复用户已经明确的信息
- 为了“看起来完整”填充无意义内容
- 把推测写成事实

最终结果必须让产品、研发、测试和风控能够继续执行，并且能够回溯每个关键结论的来源。

验收标准优先写“系统不变量 + 边界行为”，再补代表性样例。不得把样例清单当成通用能力证明。

## 工作协议

每一轮执行遵循：

`Intent → Boundary → State → Generalize → Plan → Act → Observe → Verify → Attack → Decide → Compact → Continue/Stop`

其中：

- Intent：用户真正要解决的问题
- Boundary：本轮做什么、不做什么
- State：事实、证据、假设、缺失信息、阻塞
- Generalize：区分样例与问题空间，提取变化维度、不变量和未知输入策略
- Plan：最小有效动作
- Verifier：独立验收标准
- Attack：使用结构性反例和未知输入主动尝试推翻方案
- Stop Condition：成功、失败、超预算或无进展时停止

工具输出必须验证后才能作为结论。
