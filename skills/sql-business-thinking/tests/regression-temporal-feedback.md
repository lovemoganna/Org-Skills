# 反馈观察时点：独立回归案例

## 目标

校验 Autopilot 在观察“事件完成—评分/投诉”关系时，区分结果创建、实际提交及事件完成时间；不将总体相关性直接提升为“完成后结果”或因果解释。

## 正例：事件前反馈拉高表面关联

使用与业务数据完全隔离的 VALUES 小样本：晚完成记录中同时存在完成前低分、完成后高分；另有准时完成后评分。
验收：列出三个时间层的样本量与结果数；发现总体晚完成低分率与仅完成后低分率可能不同；说明抽样选择与混杂，不能断言晚完成造成低分。

## 反例：反馈全部发生在完成后

所有反馈的实际提交时间晚于完成时间。验收：事件前组为零；总体与事件后同口径结果相同，不得为了完成检查凭空声称“前期评价偏差”或强造问题。

## 边界：结果时间缺失或创建时间可用但提交时间缺失

至少一条反馈没有可验证实际提交时间。验收：单独列入“时间未知”，不得分派到完成后；不能静默以 review_creation/request_created 替代答评/提交时间。

## 复合键与多评价

同一订单有多次评价或评价标识重用。验收：先确认评价记录粒度和评分选择策略；明确过滤/聚合后的分母，防止 JOIN 重复和评分加权偏差。

## 独立执行与验收证据

先运行三个 VALUES 对抗例，再将当前合法数据自主发现的评价/投诉信号按事件时间顺序复算，记录实际 SQL、Result 和结论变化。禁止将 VALUES 样本加入真实业务数据，禁止把历史样本结果固化为生产数字；若无法在干净上下文独立运行 worker，只能报“规则与 SQL 回归通过，Skill 行为 E2E 未验证”。

参考复测结果：独立 DuckDB VALUES 案例中，early_feedback 的完成前记录为1、完成后为2，all_after 的完成前为0、完成后为3，unknown_time 的未知时点为1。具体数值是测试 fixture，不是经营数据。
