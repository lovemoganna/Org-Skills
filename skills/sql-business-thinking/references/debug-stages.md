# 分步调试协议

目标：为 `sql-business-thinking` 增加可定位、可重跑、可回退的分步调试能力。正式方法论、阶段顺序、业务逻辑、运行时约束和输出约束保持不变。

## 1. 两种执行方式

### 正常模式

正常模式用于正式使用。

系统按照现有方法论自动连续执行完整流程。阶段之间自动传递结果。不得要求用户逐阶段确认。不得因为存在调试协议而增加正式使用步骤、降低自动执行效率或改变原有输出。

### 调试模式

调试模式只在用户明确要求“调试模式”“只跑某阶段”“重跑某阶段”“从某阶段继续”或等价维护指令时启用。

一次只执行指定阶段。当前阶段完成后立即停止，不自动进入下一阶段。

维护者可以：

1. 检查当前阶段。
2. 重跑当前阶段。
3. 修正当前阶段。
4. 明确将当前阶段标记为通过。
5. 明确进入下一阶段。
6. 从某个已满足依赖的阶段继续。
7. 在全部阶段通过后执行一次完整链路回归。

调试模式不得改变正式运行行为。

## 2. 状态

只使用以下状态：

```text
待执行
待检查
通过
需修正
需回退
阻塞
```

含义：

`待执行`：当前阶段尚未运行。

`待检查`：当前阶段已经产出结果，等待维护者确认。

`通过`：当前阶段已经确认。该输出默认锁定，可作为后续阶段输入。

`需修正`：问题属于当前阶段。只修当前阶段，不改上游。

`需回退`：当前阶段发现根因来自已确认的上游阶段。停止当前阶段，明确指出需要回退的阶段。

`阻塞`：缺少合法上游输入、运行环境、权限、数据或其他必要条件。不得自动补跑上游或绕过约束。

## 3. 上游锁定与回退

后续阶段只能读取状态为“通过”的必需上游结果。

已通过的上游结果默认锁定。后续阶段不得静默修改、重算、补写或重新解释这些结果。

如果当前阶段发现上游结果错误：

1. 立即停止当前阶段。
2. 状态设为“需回退”。
3. 明确指出根因所在阶段。
4. 明确说明当前证据。
5. 不在当前阶段内部修改上游结果。

维护者明确回退并重跑上游阶段后，如果该阶段输出发生变化，所有依赖旧输出的下游阶段结果自动失效，状态恢复为“待执行”或重新验证。不得继续复用已失效的下游结果。

## 4. 单阶段重跑

允许指定任意阶段单独重跑。

重跑时复用已经确认且仍有效的上游结果。不得为了重跑当前阶段自动重新执行全部上游。

如果数据 revision、Skill revision、输入范围、业务口径或必要上游结果已经变化，旧上游结果不再视为有效。必须明确指出失效原因，再决定从哪个阶段回退。

允许使用阶段 ID 或阶段名称指定阶段。

示例：

```text
调试模式：只跑 D05 本体原子知识库
调试模式：重跑 本体识别规则库
调试模式：从 D10 SQL 与真实结果继续
调试模式：完整链路回归
```

不要求用户使用固定命令格式。自然语言表达清楚目标即可。

## 5. 每阶段固定输出

调试模式每一步至少输出：

```text
当前阶段：
依赖阶段：
输入：
本阶段任务：
输出：
检查结果：
通过条件：
状态：
```

“输出”必须是当前阶段自己的产物，不得提前生成后续阶段内容。

“检查结果”只检查当前阶段职责及其输入契约，不重复执行全部流程。

“通过条件”必须可判断。不得使用“看起来合理”“基本没问题”等模糊标准。

阶段运行完成但尚未得到维护者确认时，默认状态为“待检查”。当前阶段内部检查失败时使用“需修正”。发现上游根因时使用“需回退”。

## 6. 调试阶段

### D01 范围与执行契约

依赖阶段：无。

输入：用户请求、数据源、允许范围、SQL 方言、读取方式、运行环境和显式约束。

当前任务：确定数据范围、执行语义、运行时路径、权限边界和不可变约束。

输出：已确认的执行契约。

检查内容：是否遗漏显式数据范围；是否区分 Data Contract 与 Runtime Bootstrap Contract；是否存在越权读取、写入或运行时替换。

通过条件：后续阶段所需数据范围、读取语义、运行时和权限边界明确，无未解决冲突。

### D02 数据勘察

依赖阶段：D01。

输入：已确认执行契约和允许数据。

当前任务：识别表、字段、行粒度、主键、外键、时间字段、金额、单位、状态和可连接关系。

输出：数据集一页纸、基础结构事实和 Analysis Map 的数据部分。

检查内容：是否只读取授权范围；是否正确识别每表一行代表什么；是否存在未经验证的字段或关系推断。

通过条件：后续质量检查和业务语义还原所需的数据结构事实完整且可追溯。

### D03 数据质量

依赖阶段：D01、D02。

输入：已确认执行契约和数据勘察结果。

当前任务：执行当前结构触发的 Mandatory Data Quality 检查，并记录对下游的允许、限制或阻塞。

输出：数据质量检查结果和状态。

检查内容：关键检查是否真实执行；未执行是否被错误写成 PASS；失败是否正确传播到依赖分析。

通过条件：所有当前必须执行的数据质量检查均有明确状态，下游影响明确。

### D04 业务语义还原

依赖阶段：D02、D03。

输入：已确认数据结构和数据质量结果。

当前任务：识别数据描述的业务对象、事件、主体、关系、状态、粒度、单位和时间语义。

输出：业务语义模型。

检查内容：是否把技术字段直接等同于业务知识；对象和关系是否有真实数据依据；是否混入指标、结论或风险判断。

通过条件：能够明确回答“这个数据集描述什么业务世界”，且业务对象与关系边界稳定。

### D05 本体原子知识库

依赖阶段：D04。

输入：已确认业务语义模型。

当前任务：按照本体协议生成最小可用、MECE 的本体原子知识库。

输出：本体原子知识库。

检查内容：原子是否重复、遗漏、过度拆分或只是机械复制字段；类型、单位和值域是否正确。

通过条件：原子具有稳定业务语义，可独立参与关系、计算、判断或组合；继续拆解不再产生新的独立业务语义。

### D06 本体识别规则库

依赖阶段：D05。

输入：已确认本体原子知识库和业务语义模型。

当前任务：生成由已登记原子构成的业务行为和业务模式。

输出：本体识别规则库及人类可读 Lisp。

检查内容：规则是否描述“发生了什么”；是否把 GROUP BY、JOIN、SUM、TopN、完成率、数据质量或稳健性检查误写成业务规则；Lisp 是否引用未登记原子或演变为复杂 DSL。

通过条件：每条规则都可追溯到合法原子和关系，规则定义、识别标准和 Lisp 语义一致。

### D07 高质量指标

依赖阶段：D05、D06。

输入：已确认原子知识库和识别规则库。

当前任务：从真实业务对象、业务模式和数据能力中提炼高质量指标。

输出：指标集合及口径。

检查内容：指标是否由字段机械生成；主体、粒度、单位、口径和数据限制是否明确。

通过条件：每个指标都能说明它量化什么业务现象，并能被当前数据合法计算或明确标记限制。

### D08 原子问题

依赖阶段：D07。

输入：已确认指标和当前已知事实。

当前任务：生成最小可验证业务问题。

输出：原子问题集合。

检查内容：一个问题是否只改变一个主要判断；是否说明为什么值得问；是否能由现有数据回答。

通过条件：每个问题均有明确指标、主体、验证方式和可能改变的判断。

### D09 问题质量与优先级

依赖阶段：D08。

输入：已确认原子问题和当前问题边界。

当前任务：检查触发原因、结果影响、可回答性和优先级，选出当前值得执行的问题。

输出：通过的问题、淘汰问题及原因、当前唯一问题。

检查内容：是否存在“无论结果如何都不改变下一步”的低价值问题；是否出现字段清单式查询。

通过条件：当前问题有明确触发原因、结果影响、可回答性和优先级。

### D10 SQL 与真实结果

依赖阶段：D01、D03、D09。

输入：已确认当前问题、数据契约和质量约束。

当前任务：生成并执行只回答当前问题的 SQL，获得真实 Result。

输出：SQL、真实 Result、执行证据和结果边界。

检查内容：SQL 是否对应当前问题；JOIN、时间、单位、粒度和别名是否正确；Result 是否真实执行并完成标量归一化。

通过条件：SQL 与业务问题一一对应，Result 可追溯，且没有绕过任何阻塞约束。

### D11 分析信号

依赖阶段：D10。

输入：已确认真实 Result。

当前任务：判断 Result 是否形成值得继续解释的分析信号。

输出：分析信号或“无高价值信号”。

检查内容：是否把最高、最低、Top1、比例等描述值直接当成原因或结论；信号是否有真实证据。

通过条件：分析信号只描述已观察事实，不超出数据证据。

### D12 本体局部展开与复杂问题

依赖阶段：D05、D06、D11。

输入：已确认分析信号和本体关系。

当前任务：只沿当前信号的合法本体邻居展开，形成有证据来源的复杂问题。

输出：候选复杂问题、合法关系路径和当前下一问题。

检查内容：是否重新扫描全部字段；每个新增维度是否能解释为什么可能改变判断；复杂问题是否引用已验证原子问题或分析信号。

通过条件：复杂问题满足主体、关系、粒度、单位、时间语义和结构兼容，且具有明确问题价值。

### D13 竞争解释

依赖阶段：D11、D12。

输入：已确认分析信号和复杂问题。

当前任务：建立主解释、合理竞争解释、反证条件和区分解释所需的诊断验证。

输出：假设边界。

检查内容：是否只有单一故事；解释是否可以被当前数据验证；是否把相关性直接写成因果。

通过条件：至少存在一个主解释和一个合理竞争解释，或明确说明当前数据为何只能保持未解决。

### D14 稳健性验证

依赖阶段：D10、D13。

输入：已确认主解释、竞争解释和真实结果。

当前任务：执行真正可能改变解释可信度的稳健性测试。

输出：稳健性结果和解释状态变化。

检查内容：测试是否能推翻或削弱当前判断；是否机械重复同类指标；数据不足时是否伪造验证。

通过条件：关键结论至少经过一次有意义的压力测试，或明确证明当前数据无法完成该验证。

### D15 已验证发现

依赖阶段：D11、D13、D14。

输入：已确认分析信号、竞争解释和稳健性结果。

当前任务：把证据充分的分析信号晋级为已验证发现。

输出：已验证发现、未解决问题和数据限制。

检查内容：事实、解释和限制是否分开；是否存在因果扩大、小样本外推或单点扩大。

通过条件：每个已验证发现都能回指真实证据、竞争解释和必要稳健性结果。

### D16 决策价值

依赖阶段：D15。

输入：已验证发现。

当前任务：判断哪些发现会改变观察重点、调查顺序、资源配置、业务动作或管理判断。

输出：决策级发现和被降级的发现。

检查内容：是否因为“有发现”就自动进入报告核心或 Dashboard；是否存在没有实际决策影响的内容。

通过条件：每个决策级发现都有明确的决策价值；低价值发现被降级或删除。

### D17 报告规格与可视化计划

依赖阶段：D16。

输入：决策级发现、证据、限制和用户交付要求。

当前任务：建立 ReportSpec、答案覆盖、图表候选、信息层级和布局骨架。

输出：ReportSpec 和可视化计划。

检查内容：是否重新分析或改口径；图表是否由独立结论决定；单位、信息预算和回答覆盖是否正确。

通过条件：每个核心问题都有可见答案，每个主要视图有独立结论，ReportSpec 不新增未验证业务事实。

### D18 最终报告或 Dashboard

依赖阶段：D17。

输入：已确认 ReportSpec、SQL、Result 和展示要求。

当前任务：生成最终 HTML、报告或 Dashboard。

输出：最终 Artifact。

检查内容：Renderer 是否修改数字、SQL、口径或结论；是否泄露内部过程说明；正式交付是否满足指定文件和交互要求。

通过条件：Artifact 忠实实现已确认 ReportSpec，没有生成新的分析事实。

### D19 成品验收

依赖阶段：D18。

输入：最终 Artifact 和当前执行证据。

当前任务：执行 Rendered QA、移动端、交互、异步 readiness、内容资格和回归验收。

输出：验收结果、缺陷清单和最终状态。

检查内容：是否真实渲染；当前 Artifact digest 是否匹配；被阻塞内容是否仍被展示；是否存在布局、交互或证据链问题。

通过条件：所有当前强制验收通过；未执行的检查不得写为 PASS。

## 7. 从指定阶段继续

“从 Dxx 继续”只表示把 Dxx 设为下一执行阶段，不表示自动忽略上游。

开始前必须确认 Dxx 的所有必需依赖均为“通过”，并且仍然有效。

如果依赖缺失，返回“阻塞”，列出缺失阶段。不得自动执行这些阶段。

如果依赖有效，执行 Dxx 后停止。只有维护者再次明确继续时才进入 Dxx+1。

## 8. 完整链路回归

当 D01 至 D19 分别通过后，允许执行一次完整链路回归。

完整回归使用正常模式的连续执行行为：

```text
D01 → D02 → ... → D19
```

回归过程中不等待人工逐阶段确认。目标是验证：

1. 单阶段正确后，串联仍然正确。
2. 阶段之间结果传递没有漂移。
3. 正常模式没有被调试控制逻辑降速或打断。
4. 调试模式新增的锁定、回退和状态机制没有改变正式业务结果。

如果完整回归失败，先定位最早出现偏差的阶段，再回到调试模式修复。不得直接在最终 Artifact 层补丁。

## 9. 工程实现边界

调试阶段是控制协议，不是新的业务方法论。

当前仓库已经采用“主 Skill + references + tests”结构，因此优先在现有 Skill 内增加调试路由，并把阶段契约放在独立 reference 中。除非后续真实测试证明单文件控制无法满足复用、隔离或测试要求，不拆成多个 Skill，不引入新的业务状态机框架。

实现形式以后可以调整，但 D01 至 D19 的职责、输入输出契约和回退规则不得因工程重构而改变。
