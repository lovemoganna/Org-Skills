# 分步调试协议

目标：按指定范围执行、检查、修正。单阶段请求只跑一阶段；明确请求完整连续执行时，顺序完成所有适用阶段。已授权自动修复、复测和验收时，不逐阶段等待确认。

正常模式连续执行；明确要求调试、重跑、阶段继续或完整 Skill 压测时启用 Debug。用户后续改为“完整执行”，覆盖此前“仅当前阶段”的范围限制，不覆盖数据与权限契约。

## 0. 五段主流程与 Dxx 调试映射

普通 Direct / Autopilot 只按主入口的五段执行，以下 Dxx 卡片仅在调试、失败定位或需要精确记录子阶段结果时展开；**五段不是额外五道验收，也不是增加五份输出**。

| 主段 | 子阶段（每个 Dxx 仅归属一段） | 输出所有权 |
|---|---|---|
| M1 数据可信 | D01–D03 | 数据与运行契约、真实表、质量 Gate |
| M2 业务与选题 | D04–D09 | 本体、筛选后的当前问题 |
| M3 证据调查 | D10–D16 | SQL、真实 Result、分析信号、诊断/反证 |
| M4 发现与决策 | D17–D19 | 已验证发现、行动判断、可选看板资格 |
| M5 交付与验收 | D20–D23 | Spec、可视化计划、实体产物、Rendered QA |

* **无重复职责：**M2 决定“问什么”，M3 决定“证据说了什么”，M4 决定“能下什么判断”，M5 只呈现且不重新分析。M1 的技术 Gate 在全程持续生效。
* **无额外轮数：**M3 得到新 Result 后，只有实际新增判断价值才回 M2 的 D08/D09；不得回头重做全部 D04–D07，也不得预写下一批 SQL。M3 完成诊断/稳健性需要新查询时同样先回 D08/D09。
* **无强制深度：**没有合格问题可以停止；没有因果证据可以仅交描述性报告；不能据此伪造深度 PASS。Dashboard-only 按 D07→D19→D20–D23 的既有快捷路径，不强制 D08–D18。
* **异常精定位：**主段只报告一项汇总状态及关键证据；出现失败才展开对应 Dxx、Gate 和原始 SQL/Result。不得以汇总 PASS 掩盖子 Gate FAIL / BLOCKED；历史结果仍不能冒充本轮执行。

## 1. 语言规则

所有调试步骤使用短句。每句只表达一个动作。

优先使用：

```text
输入
任务
输出
检查
通过
状态
```

规则：

1. 先写动作，再写对象。
2. 同一概念只用一个名称。
3. 删除背景解释、同义重复和不影响执行的说明。
4. 技术名词只在无法准确中文化时保留英文。
5. 检查结果必须写事实，不写“看起来正常”“基本没问题”。
6. 需要说明原因时，只说明会改变执行的原因。

## 2. 状态

只使用：

```text
待执行
待检查
通过
需修正
需回退
阻塞
```

含义：

`待执行`：尚未运行。

`待检查`：完成检查，但缺少用户确认或充分的客观验证证据。

`通过`：用户已确认；或用户明确预授权自动验收，且已完成可核验的阶段执行和回归。输出默认锁定。

`需修正`：问题属于当前阶段。只修当前阶段。

`需回退`：根因来自上游。停止当前阶段并指出回退位置。

`阻塞`：缺少合法输入、环境、权限或数据。停止，不绕过。

模型自检通过不得自动写成“通过”。默认需用户确认。用户明确授权自动修复、复测和验收时，只有实际执行与客观检查均通过，才可标“通过”，并记录预授权与验证证据。无法客观证明时仍为“待检查”。

## 3. 执行范围

**单阶段请求：**一次只执行指定阶段；完成即停，不为方便补跑未授权上游。

**完整连续执行请求：**从 D01 开始，按依赖和实际分析循环执行适用阶段；每阶段保留输入、真实证据、状态及版本。已获自动修复与验收授权时不逐阶段暂停。某阶段阻塞后先验证合法替代运行位置；仍阻塞则停，后续标“待执行”，不可用旧结果或预置 SQL 充数。

**从指定阶段继续：**检查依赖均通过且仍有效；缺失则列出依赖并阻塞，不自动补跑。

“下一步”表示进入当前逻辑上的下一阶段，**不等于固定的 Dxx+1**。

## 4. 自检自修

每个阶段内部执行同一个循环：

```text
执行
↓
对照检查项
↓
定位根因
↓
最小修正
↓
重跑当前阶段
↓
重新检查
```

先用失败日志定位具体断言、输入、执行步骤与预期结果。构造最小案例复现后，再分类根因。没有复现或直接证据时标“未定位”，不得按表面症状修复。

| 根因类型 | 判定证据 | 处理 |
|---|---|---|
| Skill 缺陷 | 真实输入符合契约，但规则缺失、冲突或指导出错误行为 | 最小修改当前规范，验证旧例与反例 |
| 执行偏差 | 规范正确，但执行没有遵守输入、顺序、证据或版本 | 修实际产物或执行步骤，不改正确规范 |
| 环境问题 | 最小案例证实运行时、权限、网络或依赖失败 | 修合法运行链路；仍不可用则阻塞 |
| 测试错误 | 正确行为被测试误判，或断言、夹具、触发路径存在错误 | 修测试及其引用，不放宽正确验收标准 |

根因类别与处理位置分开记录：当前阶段可就地修复；上游缺陷需回退；越权或无法获取证据则阻塞。不能把“上游阶段”“环境阻塞”当作根因证明。每项记录失败日志、最小复现、修复 Diff、复测结果。

自修规则：

1. 先找根因，再修改。
2. 一次只改一个根因。
3. 修后必须重新执行当前阶段。
4. 完成判断只使用本轮新证据，不使用旧结果代替。
5. 同一问题重复出现且没有新证据时停止，不继续试错。
6. 自修只能发生在当前阶段。不得顺手修改上游或下游。
7. 默认自检通过后为“待检查”。已获得明确预授权自动验收时，可凭实际执行和客观回归标“通过”，不能只靠模型自评。
8. 用户已授权修复本阶段时，直接修正并重测，不重复索取批准；但涉及越权写入、改变已锁定上游或无法验证的事实时必须停止。

如果一个阶段包含多个可以独立失败的检查，拆成子步骤分别执行和记录状态。不得用一个总状态掩盖多个故障源。

## 5. 调试状态记录

调试模式必须维护最小状态记录：

| 字段 | 含义 |
|---|---|
| 阶段 ID | 当前步骤 |
| 阶段名称 | 当前职责 |
| 状态 | 当前状态 |
| 依赖阶段 | 已确认上游 |
| 输入标识 | 数据 revision、Skill revision 或等价引用 |
| 输出标识 | 当前输出的可比较引用 |
| 用户确认 | 明确确认或本轮预授权范围 |
| 失效原因 | 哪个变化使结果失效 |

已通过阶段**默认锁定**。下游只能读取，不得静默修改、重算或重新解释。

上游重跑后：

1. 比较新旧输出。
2. 输出无实质变化且依赖仍有效，下游可保持原状态。
3. 输出发生实质变化，依赖旧输出的下游恢复“待执行”，并记录失效原因。

## 6. 每阶段固定输出

每次只返回：

```text
当前阶段：
依赖阶段：
输入：
本阶段任务：
输出：
检查结果：
通过条件：
状态：
```

发生问题时再补：

```text
根因：
修正：
回退阶段：
```

“输出”只包含当前阶段产物。不得提前生成后续阶段内容。

## 7. 阶段卡片

### D01 范围与执行契约

依赖：无。

输入：用户请求、数据源、SQL 方言、读取方式、运行环境、显式约束。

任务：锁定数据范围、执行语义、运行时、权限和不可变约束。

输出：执行契约。

检查：范围是否完整；Data Contract 与 Runtime Bootstrap Contract 是否分离；是否越权。

通过：范围、读取、运行时和权限无未解决冲突。

### D02 数据勘察

依赖：D01。

输入：执行契约、授权数据。

任务：识别表、字段、行粒度、键、时间、金额、单位、状态和可连接关系。

输出：数据集一页纸、结构事实。

检查：是否只读授权范围；每表粒度是否明确；字段和关系是否有数据依据。

通过：后续数据质量和业务语义所需结构事实完整、可追溯。

### D03 数据质量

依赖：D01、D02。

输入：执行契约、结构事实。

任务：执行当前结构触发的 Mandatory Data Quality 检查。

输出：检查结果、状态、下游影响。

检查：必须执行的检查是否真实运行；未执行是否误写 PASS；失败是否正确传播。

通过：所有必需检查都有明确状态和影响范围。

多个独立质量检查必须拆为 D03 子步骤，分别执行、分别确认。

### D04 业务语义还原

依赖：D02、D03。

输入：结构事实、数据质量结果。

任务：识别业务对象、事件、主体、关系、状态、粒度、单位和时间语义。

输出：业务语义模型。

检查：是否把字段直接当业务知识；关系是否有依据；是否混入指标或结论。

通过：能明确回答“数据描述什么业务世界”，对象和关系边界稳定。

### D05 本体原子知识库

依赖：D04。

输入：业务语义模型。

任务：生成最小可用、MECE 的本体原子。

输出：本体原子知识库。

检查：是否重复、遗漏、过度拆分或机械复制字段；类型、单位和值域是否正确。

通过：每个原子有稳定业务语义，并可独立参与关系、计算、判断或组合。

### D06 本体识别规则库

依赖：D04、D05。

输入：业务语义模型、本体原子知识库。

任务：生成由已登记原子构成的业务行为和业务模式。

输出：本体识别规则库、人类可读 Lisp。

检查：规则是否描述“发生了什么”；方向字段是否被错误解释为已经完成的业务结果；存在独立状态字段时是否区分“方向行为”和“已完成行为”；是否混入 GROUP BY、JOIN、SUM、TopN、完成率、质量检查或稳健性检查；Lisp 是否引用未登记原子。

通过：每条规则可追溯到合法原子和关系；方向、状态和完成语义不混淆；规则与 Lisp 语义一致。

### D07 高质量指标

依赖：D05、D06。

输入：原子知识库、识别规则库。

任务：生成少量候选指标，并筛掉低价值指标。不得建立额外指标 DSL，不得枚举全部字段、状态、维度和度量组合。

输出：保留指标、淘汰指标及原因。

检查：每个候选指标是否能回溯到 D05/D06；是否真的可能改变后续判断；是否只是因为字段存在或技术上能计算才生成；是否与其他指标重复；统计主体、结果粒度、分析范围、单位和口径是否明确；金额或数量名称是否忠实于订单/交易记录语义；比例、DISTINCT 和可加性约束是否正确；方向或状态是否被过度命名为成功率、完成率或处理效率。

通过：只保留少量有业务意义、可合法计算、可能改变判断的指标。低价值切片、重复指标和机械组合已淘汰。D08 直接基于这些指标生成原子问题。

### D08 候选问题

依赖：D07；分析循环中可接收 D13、D15、D16 的新问题。

输入：D07 保留指标、D03 已知数据质量事实、D05/D06 业务语义和当前问题边界。

任务：生成少量可独立验证、可能改变后续判断的问题。不按状态、方向、渠道、网络机械拆分，不规定问题数量，不执行 SQL。

输出：保留问题、触发依据、不同答案会改变什么；淘汰或暂缓问题及原因。没有合格问题时输出空集。

检查：是否能回溯到指标和本体；是否重复 D03 已知事实；答案不同是否真的改变判断；主体、粒度、时间和状态语义是否成立；小样本能否支持所问的差异或集中判断；pending/processing/confirming（进行中）是否被错误合并为 failed/cancelled（终态非完成）；是否预设异常、集中、因果或真实 SQL 结果。

通过：只保留合法且值得验证的问题，明确样本限制。拒绝低价值或证据不足的问题，允许零个候选。

### D09 问题质量与优先级

依赖：D08。

输入：D08 已保留的问题、来源指标、本体语义、现有数据能力和问题边界。

任务：先筛质量，再确定优先级。最多选择一个当前问题；没有合格问题时返回空集，不为推进流程强行选择。不写 SQL、不验证结果。

输出：入选问题及理由、两个可能结果对应的后续判断、必要口径和样本限制；淘汰或暂缓项及原因。无合格问题时输出“当前无可推进问题”。

检查：问题是否超出 D08 授权范围；是否有合法本体来源和当前数据支撑；答案不同是否会改变调查方向或停止判断；是否只是计数、TopN 或机械切片；是否把小样本描述误称统计显著、系统性问题或因果；是否因为“只剩一个候选”就自动入选。多个候选没有可辩护的优先级时不得编造评分或随意挑选。

通过：最多保留一个有明确判断后果、可回答且限制清楚的问题；或有依据地拒绝全部候选。D09 不能预设结果，也不执行 D10。

### D10 SQL 设计

依赖：D01、D03、D09。

输入：当前问题、执行契约、数据质量约束。

任务：只设计回答当前问题的 SQL。不执行。

输出：唯一待执行 SQL、预期粒度、查询假设。

检查：SQL 是否对应当前问题；JOIN、时间、单位、粒度、过滤和别名是否正确；是否绕过阻塞。涉及状态占比时，检查分子分母是否同范围、按正确粒度汇总，是否区分完成、进行中、终态非完成及未知状态；分母为零是否返回 NULL；是否保留小样本限制。不得用 SQL 设计结果预设异常或差异。

通过：SQL 在授权运行时具备可执行条件，逻辑完整；不含实际 Result 或业务结论。

### D11 SQL 执行与真实结果

依赖：D01、D03、D10。

输入：已确认 SQL、运行时、数据 revision。

任务：执行 D10 的 SQL。不得改写业务逻辑。

输出：真实 Result、执行证据、归一化结果、执行状态。

检查：执行 SQL 是否与 D10 一致；revision 是否正确；运行时是否合规；Result 是否归一化。

通过：Result 可追溯到当前 SQL、当前数据和当前运行环境。

SQL 逻辑错误：需回退 D10。运行环境或权限问题：在 D11 修复或标“阻塞”。

### D12 结果解释与分析信号

依赖：D11。

输入：已通过的 D11 Result、执行证据与口径。

任务：先解释数字，再判断是否有值得进一步核查的分析信号。不生成 SQL，不提出新的分析问题。

输出：已观察事实、分析信号或“无高价值信号”、证据引用和结论边界。

检查：是否同时看比例、分子分母和状态构成；完成占比接近时是否漏掉非 completed 记录的状态类型差异；是否把少量记录夸大为统计显著或系统性异常；是否把历史 pending/processing 称为“当前仍在处理”；是否将 failed/cancelled 合称实际失败；是否把相关、排名或比例当原因；是否添加 Result 未支持的事实或行动结论。

通过：每条事实能回指当前 D11 Result。真正值得进一步核查的差异只标为受限分析信号，说明样本规模和未验证事项；不能以分析信号代替 D13 的问题展开或 D17 的已验证发现。

### D13 本体局部展开

依赖：D05、D06、D12。

输入：D12 已确认的分析信号、D05 原子和 D06 合法关系；没有可追溯信号时不展开。

任务：仅沿与当前信号直接相关、已登记且能改变后续判断的本体关系生成候选问题。不重新扫描字段，不执行 SQL，不假设新结果。允许零个候选。

输出：候选问题、原信号、合法关系路径及不同答案对应的下一步；淘汰路径及原因。

检查：关系是否真实存在于本体及授权表；是否把同一粒度的状态构成误说成资金流向或原因；主体、事件、粒度和时间是否兼容；少量个案是否被不当推广为群体规律；是否复述 D11/D12 已知事实或仅为填满候选列表而增加用户、渠道、时间等维度；是否先行选择 D08/D09 的答案或执行 D10/D11 SQL。

通过：只保留少量有可追溯路径、不同答案会改变后续核查方式的问题；无法验证本体关系或没有新增决策价值时淘汰，允许空集。

需要验证时回 D08，不直接跳到 D10。

### D14 竞争解释

依赖：D12；D13 可作为补充输入。

输入：D12 已确认的分析信号、已有 Result、D13 合法关系和数据限制。

任务：提出能够被后续证据区分的竞争假设及反证条件。先区分可验证的记录分布假设与当前数据无法识别的业务根因。没有证据支持的假设不得指定为“主解释”；不执行 SQL。

输出：并列假设、各自的反证条件、所需证据、仍无法解释的原因及边界。证据不足时明确保持未解决。

检查：是否引用真实 D11/D12 证据；假设是否互斥或能产生不同验证结果；是否把用户集中、渠道集中、时间顺序当成已观察事实；是否把记录分布当成成因；是否遗漏当前数据不含失败原因或状态流转日志的限制；是否重复执行 D13 或提前写 SQL。

通过：有至少一组证据可区分的假设及明确反证条件，且没有提前选择赢家；无法形成可检验解释时如实标未解决，不凑故事。

### D15 诊断验证设计

依赖：D14。

输入：D14 并列竞争假设、各自的反证条件、已通过的 D11/D12 证据与数据限制。D14 没有证据偏好的主解释时，不得强造主解释。

任务：仅设计能区分竞争假设的最小诊断问题。不执行 SQL，不追加分析维度或推断原因。

输出：唯一诊断问题、限定的记录范围、必需字段、互斥结果分支与不能判定的情形。

检查：是否把 D14 未验证的 uid 归属写成已知事实；是否保持 fiat_order_id 一条记录一个事件的粒度；字段及关系是否都在授权数据中；“同一 uid / 不同 uid / 证据无效”是否分别影响 H1/H2 或保留未解决；是否错误推断故障原因、资金关联或当前实时状态；是否提前生成 SQL。

通过：一条最小诊断问题即可区分已登记的竞争假设，并明确证据不足的停机条件。不可识别根因继续保持未解决。

需要验证时将诊断问题送回 D08，不直接跳 D10。

### D16 稳健性验证设计

依赖：D12、D14。D15 的诊断问题若尚未执行，不得冒充已取得诊断结果。

输入：D12 已确认的判断、D11 实际 Result、D14 未解决的竞争解释与数据限制。

任务：只设计一个能动摇当前判断的敏感性检验。明确哪些口径保持不变、哪些假设变化。不执行 SQL，不补造新结果。

输出：一个稳健性问题、原口径与替代口径、可用字段、对照条件、结论变化或无法判定时的处理。

检查：检验是否针对真实判断而非机械增加维度；是否未经标注改变分母或统计主体；是否把历史 pending/processing 当作终态；是否把对照口径替换为原始业务指标；是否凭小样本宣称显著性、系统性问题、用户归属或失败原因；是否把未执行的诊断当证据；若当前证据已足够或无法验证，是否说明下一步而不强造 SQL。

通过：稳健性检验有明确可推翻或收紧的判断及数据来源；原口径保持锁定、替代口径单独标记，不能推出根因。没有合理检验时如实停止。

需要执行新问题时先返回 D08，不直接跳 D10 或 D17。

### D17 已验证发现

依赖：D12；相关 D14 至 D16 的检查结果可用于收紧结论。未执行的诊断不能当已完成验证。

输入：已通过的 D11 Result 和 D12 事实、相关检查结果、数据口径及限制。

任务：只晋级有实际证据支持的描述性事实或已完成的敏感性判断。因果解释、用户归属和无法核验的机制继续标未解决。不执行新 SQL，不用测试模拟值冒充证据。

输出：已验证发现及其来源与适用口径、被降级判断、未解决问题、数据限制。可以没有业务根因型发现。

检查：是否逐项回指真实 Result 和数据 revision；是否把测试或 D15 未执行的 uid 诊断当证据；原分母和替代分母是否明确分开、方向排序翻转是否如实收紧结论；历史状态是否被当作当前状态；是否把少量记录外推为显著性、总体规律、风险或原因。

通过：只有可以独立复算且有真实证据的事实和限定结论晋级；其余保持未解决，不为填充报告虚构发现。

### D18 决策价值

依赖：D17。

输入：D17 已验证发现、原始与辅助口径、数据限制，以及已知的分析目标。

任务：只判断哪些发现足以改变一个具体判断。区分口径/解释决策与实际运营动作；没有行动依据时不虚构处置优先级。不重新分析、不执行 SQL。

输出：决策级发现（可为空）、保留为报告证据但不足以直接行动的事实、被拒绝的动作主张、仍缺少的决策证据。

检查：每个决策级发现是否有 D17 来源、明确判断变化和适用范围；分母变化导致方向排序翻转时是否禁止用单一 completed 占比给方向排名；是否把 25 条历史记录或 2 条终态非完成记录直接说成系统性风险或当前待办；是否编造业务阈值、损失规模、根因、用户身份或资源配置；是否把报告价值等同 Dashboard 资格。

通过：只晋级有证据且会改变明确判断的内容；无法支持运营动作时明确写“当前不能决定”。允许零项，不为填满报告或看板强造结论。

### D19 看板资格

仅在交付包含 Dashboard / 看板时执行。

依赖：D07。若当前分析已经产生 D17 已验证发现或 D18 决策级发现，可作为补充输入，但不是 Dashboard-only 的必需前置。

输入：高价值指标、看板目标和用户角色；如已有 D17/D18 结果，同时读取已验证发现和决策需求。

任务：判断哪些数据需要长期、重复、快速监控。看板资格与分析深度分开判断。

输出：看板核心项、下钻项、排除项及原因。

检查：是否需要持续监控；是否会随业务变化；变化后是否需要关注或行动；是否可稳定重复计算；是否能快速判断当前状态；是否只是一次性诊断证据或分析过程；是否因为分析很深就自动进入看板；是否遗漏简单但长期重要的基础状态指标。

通过：核心看板只保留持续重要、可重复计算、变化后需要关注或行动、适合快速读取的数据。一次性根因、诊断过程、竞争解释和稳健性证据默认不进核心看板。

### D20 交付规范

依赖：Report = D18；Dashboard = D19；Hybrid = D18 + D19。依赖必须实际完成且状态为“通过”。

输入：已确认的交付类型，以及对应上游输出及证据引用。
Report：D18 决策级发现、证据、限制；引用的实际 Result 必须能追溯到 D11。
Dashboard：D19 看板资格结果、口径、限制。
Hybrid：两组已通过的输入。

任务：只按已确认交付类型整理内容。不改变交付类型，不重新分析、不选图。依赖缺失、未通过或证据不可核验时标“阻塞”，不得产出空壳 Spec；应指出缺失阶段，不自动补跑。

输出：
Report：ReportSpec。
Dashboard：DashboardSpec。
Hybrid：彼此独立的 ReportSpec 与 DashboardSpec。
阻塞：依赖缺口与恢复条件，不生成正式 Spec。

检查：依赖状态是否真实有效；每个可展示结果是否有来源及 Gate 状态；是否把候选问题、指标定义或测试样例冒充已验证发现；交付类型是否被改变；两个 Spec 是否交叉；是否新增事实、SQL 或选图。D18 已完成但没有决策级发现时，可以如实输出“无决策级发现”，不能虚构发现。

通过：所需上游均已通过且证据可追溯，正式 Spec 只组织已确认内容；测试样例不能替代真实任务结果。

### D21 可视化计划

依赖：D20 已通过，且 Spec 有可核验的内容引用。

输入：已确认 ReportSpec / DashboardSpec、内容证据和可视化要求。

任务：只从可展示的 D20 内容生成独立 VisualizationPlan。不重新分析、不改写 D20、不生成 Artifact。D20 阻塞或缺失时停止，不凭样例补齐。

输出：VisualizationPlan 与布局骨架；依赖不足时仅输出阻塞原因。

检查：每个 content_ref 是否真实存在且未被 Gate 阻断；报告图是否服务结论和证据；Dashboard 图是否服务快速监控；单位、重复、布局是否正确；是否改动 D20 或编造数字。

通过：所有展示项都能回指有效 D20 内容，表达方式不改变数据语义；模拟样例通过不等于真实任务通过。

### D22 最终 Artifact

依赖：D20、D21。

输入：ReportSpec / DashboardSpec、可视化计划、SQL、Result、交付要求。

任务：生成 HTML、报告或 Dashboard。不新增分析事实。

输出：最终 Artifact。

检查：Renderer 是否修改数字、SQL、口径或结论；Dashboard 是否混入未通过 D19 的内容；是否泄露内部过程；是否满足交付要求。

通过：Artifact 忠实实现已确认内容。Dashboard 核心层只展示通过看板资格的数据。

### D23 成品验收

依赖：D22。

输入：最终 Artifact、执行证据。

任务：执行当前强制 QA。

输出：验收结果、缺陷、最终状态。

检查：Rendered QA、移动端、交互、异步 readiness、内容资格、证据链和回归；Dashboard 额外检查核心项资格与首屏信息预算。

通过：所有强制检查真实执行并通过。未执行不得写 PASS。

D23 中可以独立失败的 QA 必须拆成子步骤，分别执行、分别确认。

## 8. 分析循环

D08 至 D17 不是一次性直线。

主循环：

```text
D08 候选问题
→ D09 问题质量
→ D10 SQL 设计
→ D11 SQL 执行
→ D12 结果解释
```

D12 后按证据选择：

```text
还有值得回答的问题 → D08
需要业务关系展开 → D13 → D08
需要解释主要现象 → D14 → D15 → D08
需要压力测试 → D16 → D08
证据足够 → D17
没有信息增量 → 结束当前分析分支
```

任何回到 D08 的问题，都必须重新经过 D09、D10、D11、D12。

## 9. 回退与继续

当前阶段发现上游错误：

1. 停止。
2. 状态设“需回退”。
3. 指出根因阶段和证据。
4. 不在当前阶段修上游。

单阶段运行遇上游缺陷需先取得回退授权；完整连续执行已有自动修复授权时，可在原授权范围内回退、修复并复测，涉及数据越权、仓库写入或变更已锁定事实仍须停止。

从某阶段继续只执行该阶段；完整连续执行按已授权范围推进。

## 10. 完整链路回归

只有本轮适用阶段均有真实证据且状态通过，才可宣称完整链路验收。用户明确预授权的客观自动验收可替代逐次人工确认；未获预授权时仍需逐阶段确认。

完整回归按正常模式连续执行，保留真实分支与**分析循环**，不能机械走一次 D01 至 D23；每个业务 SQL 与最终 Artifact 须绑定当前 Skill、数据和 runner revision。

回归失败时，定位最早偏差阶段，再回调试模式。不得只修最终 Artifact。

## 11. 工程实现边界

本协议只定义逻辑阶段、输入、输出、依赖、检查和状态，**不决定最终工程拆分方式**。

最终可以采用**单个 Skill 内部分段、多个独立 Skill、子模块**、状态文件或其他形式。当前保持未确定。

现有 `debug-stages.md` 只是协议存放位置，不代表最终模块边界。


## 12. 调查深度专属验收（不改原阶段依赖）

仅在用户要求深度调查或深度分析 Report/Autopilot 时启用，不强制扩展 Learn、简单 Direct 或 Dashboard：

- D08/D09：每个当前问题记录真实触发依据与两种答案分别改变的判断；无差别的 TopN、机械切片、集合重叠须淘汰，允许空集。
- D10/D11：当前问题通过 D09 后才设计并执行 SQL；绑定 question_id、实际 SQL/Result SHA、run/Skill/data revision；预置 Gate SQL 不作为动态分析证据。
- D12：记录实际 Result 如何改变判断及下一问/停机原因；D01–D23 每阶段一句 PASS 不能代替逐次结果驱动的 Frontier。
- D13：合法主体、事件时间、方向等关系具备时，应评估与当前问题有关的行为顺序或重复模式，保留采纳/淘汰依据；不得仅凭 TopN 停止调查，也不得硬造异常。
- D14–D16：调查型主发现要求 H1/H2 各自可观察预测与反证，至少一个真实执行的区分测试与一次负控/稳健性 Result。未执行或不具鉴别力时标 unresolved。
- D17/D18：描述性事实可晋级为已验证描述，但不能当调查深度 PASS。不能据同 UID、同额、邻近时间宣称资金闭环、真实结算、洗钱、欺诈或应采取限制动作。
- D20/D23：报告主发现应有具体事件/主体、合法行为关系、实测诊断与反例、业务限制和可执行调查下一步；无高价值发现则明确 `DESCRIPTIVE_ONLY` 或 `NO_DECISION_GRADE_FINDING`，不伪造结论。结构化 trace 校验必须与实际 SQL 的证据链相符，机器检查通过不等于业务真值和完整 E2E 通过。

最小 trace 契约：`meta(run,skill,data)`、`questions(id,trigger,parent?,branches)`、`results(id,question,run,skill,data,sql_sha,result_sha,status)`、`updates(source,observed,change,next?)`、`findings(id,kind,evidence,claim,limits,alternatives?,diagnostic?,robustness?,decision_change?)`、`report(findings,depth)`。用 `tests/check_investigation_trace.py <trace.json>` 检查结构。其他格式可先无损映射到此结构；测试夹具或旧 run 不得冒充本轮真实调查。
