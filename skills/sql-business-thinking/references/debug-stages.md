# 分步调试协议

目标：为 `sql-business-thinking` 增加可定位、可重跑、可回退的分步调试能力。正式方法论、阶段顺序、业务逻辑、运行时约束和输出约束保持不变。

## 1. 两种执行方式

### 正常模式

正常模式用于正式使用。

系统按照现有方法论自动连续执行完整流程。阶段之间自动传递结果。不得要求用户逐阶段确认。不得因为存在调试协议而增加正式使用步骤、降低自动执行效率或改变原有输出。

### 调试模式

调试模式只在用户明确要求“调试模式”“只跑某阶段”“重跑某阶段”“从某阶段继续”或等价维护指令时启用。

一次只执行指定阶段。当前阶段完成后立即停止，不自动进入下一阶段。

维护者可以：

1. 检查当前阶段。
2. 重跑当前阶段。
3. 修正当前阶段。
4. 明确将当前阶段标记为通过。
5. 明确进入下一阶段。
6. 从某个已满足依赖的阶段继续。
7. 在全部阶段通过后执行一次完整链路回归。

调试模式不得改变正式运行行为。

## 2. 状态

只使用以下状态：

```text
待执行
待检查
通过
需修正
需回退
阻塞
```

含义：

`待执行`：当前阶段尚未运行。

`待检查`：当前阶段已经产出结果，等待维护者确认。

`通过`：当前阶段已经确认。该输出默认锁定，可作为后续阶段输入。

`需修正`：问题属于当前阶段。只修当前阶段，不改上游。

`需回退`：当前阶段发现根因来自已确认的上游阶段。停止当前阶段，明确指出需要回退的阶段。

`阻塞`：缺少合法上游输入、运行环境、权限、数据或其他必要条件。不得自动补跑上游或绕过约束。

## 3. 上游锁定与回退

后续阶段只能读取状态为“通过”的必需上游结果。

已通过的上游结果默认锁定。后续阶段不得静默修改、重算、补写或重新解释这些结果。

如果当前阶段发现上游结果错误：

1. 立即停止当前阶段。
2. 状态设为“需回退”。
3. 明确指出根因所在阶段。
4. 明确说明当前证据。
5. 不在当前阶段内部修改上游结果。

维护者明确回退并重跑上游阶段后，如果该阶段输出发生变化，所有依赖旧输出的下游阶段结果自动失效，状态恢复为“待执行”或重新验证。不得继续复用已失效的下游结果。

## 4. 单阶段重跑

允许指定任意阶段单独重跑。

重跑时复用已经确认且仍有效的上游结果。不得为了重跑当前阶段自动重新执行全部上游。

如果数据 revision、Skill revision、输入范围、业务口径或必要上游结果已经变化，旧上游结果不再视为有效。必须明确指出失效原因，再决定从哪个阶段回退。

允许使用阶段 ID 或阶段名称指定阶段。

示例：

```text
调试模式：只跑 D05 本体原子知识库
调试模式：重跑 本体识别规则库
调试模式：从 D10 SQL 设计继续
调试模式：完整链路回归
```

不要求用户使用固定命令格式。自然语言表达清楚目标即可。

## 5. 每阶段固定输出

调试模式每一步至少输出：

```text
当前阶段：
依赖阶段：
输入：
本阶段任务：
输出：
检查结果：
通过条件：
状态：
```

“输出”必须是当前阶段自己的产物，不得提前生成后续阶段内容。

“检查结果”只检查当前阶段职责及其输入契约，不重复执行全部流程。

“通过条件”必须可判断。不得使用“看起来合理”“基本没问题”等模糊标准。

阶段运行完成但尚未得到维护者确认时，默认状态为“待检查”。当前阶段内部检查失败时使用“需修正”。发现上游根因时使用“需回退”。

## 5A. 调试状态记录

调试模式必须维护一份最小状态记录。它用于判断当前步骤是否可执行、上游是否仍有效、下游是否需要失效。状态记录是逻辑契约，不规定必须保存为文件、表格、JSON、数据库或其他工程形式。

至少记录：

| 字段 | 含义 |
|---|---|
| 阶段 ID | 当前步骤唯一编号 |
| 阶段名称 | 当前职责 |
| 状态 | 待执行 / 待检查 / 通过 / 需修正 / 需回退 / 阻塞 |
| 依赖阶段 | 当前步骤依赖的已确认步骤 |
| 输入标识 | 当前输入、数据 revision、Skill revision 或等价引用 |
| 输出标识 | 当前步骤输出的可比较引用或摘要 |
| 用户确认 | 是否由用户明确确认通过 |
| 失效原因 | 如果结果失效，说明由哪个上游变化触发 |

规则：

1. 阶段执行成功后只能自动进入“待检查”。模型自检通过不得自动写成“通过”。
2. 只有用户明确确认当前阶段没有问题后，状态才能变为“通过”。
3. “通过”后输出锁定。下游只能读取，不得静默修改。
4. 重跑当前阶段时，先比较新旧输出。如果输出未发生实质变化且依赖仍有效，下游可以保持原状态。如果输出发生变化，所有依赖旧输出的下游阶段恢复为“待执行”，并记录失效原因。
5. 数据 revision、Skill revision、输入范围、业务口径或上游输出变化时，必须先检查受影响阶段是否仍有效。不得默认复用。
6. 状态记录只服务调试和验证，不进入正式业务报告。

## 6. 调试阶段

阶段定义是逻辑责任边界。每次调试只执行一个阶段。

### D01 范围与执行契约

依赖阶段：无。

输入：用户请求、数据源、允许范围、SQL 方言、读取方式、运行环境和显式约束。

当前任务：确定数据范围、执行语义、运行时路径、权限边界和不可变约束。

输出：已确认的执行契约。

检查内容：是否遗漏显式数据范围；是否区分 Data Contract 与 Runtime Bootstrap Contract；是否存在越权读取、写入或运行时替换。

通过条件：后续阶段所需数据范围、读取语义、运行时和权限边界明确，无未解决冲突。

### D02 数据勘察

依赖阶段：D01。

输入：已确认执行契约和允许数据。

当前任务：识别表、字段、行粒度、主键、外键、时间字段、金额、单位、状态和可连接关系。

输出：数据集一页纸和基础结构事实。

检查内容：是否只读取授权范围；是否正确识别每表一行代表什么；是否存在未经验证的字段或关系推断。

通过条件：后续质量检查和业务语义还原所需的数据结构事实完整且可追溯。

### D03 数据质量

依赖阶段：D01、D02。

输入：已确认执行契约和数据勘察结果。

当前任务：执行当前结构触发的 Mandatory Data Quality 检查，并记录对下游的允许、限制或阻塞。

输出：数据质量检查结果和状态。

检查内容：关键检查是否真实执行；未执行是否被错误写成 PASS；失败是否正确传播到依赖分析。

通过条件：所有当前必须执行的数据质量检查均有明确状态，下游影响明确。

### D04 业务语义还原

依赖阶段：D02、D03。

输入：已确认数据结构和数据质量结果。

当前任务：识别数据描述的业务对象、事件、主体、关系、状态、粒度、单位和时间语义。

输出：业务语义模型。

检查内容：是否把技术字段直接等同于业务知识；对象和关系是否有真实数据依据；是否混入指标、结论或风险判断。

通过条件：能够明确回答“这个数据集描述什么业务世界”，且业务对象与关系边界稳定。

### D05 本体原子知识库

依赖阶段：D04。

输入：已确认业务语义模型。

当前任务：按照本体协议生成最小可用、MECE 的本体原子知识库。

输出：本体原子知识库。

检查内容：原子是否重复、遗漏、过度拆分或只是机械复制字段；类型、单位和值域是否正确。

通过条件：原子具有稳定业务语义，可独立参与关系、计算、判断或组合；继续拆解不再产生新的独立业务语义。

### D06 本体识别规则库

依赖阶段：D04、D05。

输入：已确认业务语义模型和本体原子知识库。

当前任务：生成由已登记原子构成的业务行为和业务模式。

输出：本体识别规则库及人类可读 Lisp。

检查内容：规则是否描述“发生了什么”；是否把 GROUP BY、JOIN、SUM、TopN、完成率、数据质量或稳健性检查误写成业务规则；Lisp 是否引用未登记原子或演变为复杂 DSL。

通过条件：每条规则都可追溯到合法原子和关系，规则定义、识别标准和 Lisp 语义一致。

### D07 高质量指标

依赖阶段：D05、D06。

输入：已确认原子知识库和识别规则库。

当前任务：从真实业务对象、业务模式和数据能力中提炼高质量指标。

输出：指标集合及口径。

检查内容：指标是否由字段机械生成；主体、粒度、单位、口径和数据限制是否明确。

通过条件：每个指标都能说明它量化什么业务现象，并能被当前数据合法计算或明确标记限制。

### D08 候选问题

依赖阶段：D07。分析循环中也可以接收 D13、D15、D16 产生的新问题。

输入：已确认指标、当前已知事实和当前问题边界。

当前任务：生成一个或多个最小可验证候选问题。首次进入时生成原子问题；循环进入时接收复杂问题、诊断问题或稳健性问题。

输出：候选问题集合。

检查内容：每个问题是否有明确证据来源；是否只改变一个主要判断；是否能说明为什么值得问。

通过条件：候选问题都有可追溯来源，不存在凭模型经验直接生成的“高级问题”。

### D09 问题质量与优先级

依赖阶段：D08。

输入：已确认候选问题和当前问题边界。

当前任务：检查触发原因、结果影响、可回答性和优先级，只选出当前唯一值得执行的问题。

输出：当前问题、被淘汰问题及原因。

检查内容：是否存在“无论结果如何都不改变下一步”的低价值问题；是否出现字段清单式查询。

通过条件：当前问题有明确触发原因、结果影响、可回答性和优先级。

### D10 SQL 设计

依赖阶段：D01、D03、D09。

输入：已确认当前问题、执行契约和数据质量约束。

当前任务：只设计回答当前问题的 SQL，不执行 SQL，不解释尚未出现的 Result。

输出：唯一待执行 SQL、预期结果粒度和必要查询假设。

检查内容：SQL 是否与当前问题一一对应；JOIN、时间、单位、粒度、过滤和别名是否正确；是否绕过任何阻塞约束。

通过条件：SQL 逻辑完整、边界明确，可在授权运行时执行，且没有混入实际 Result 或业务结论。

### D11 SQL 执行与真实结果

依赖阶段：D01、D03、D10。

输入：已确认待执行 SQL、运行时和数据 revision。

当前任务：执行已确认 SQL，记录真实 Result 和执行证据。不得在本阶段改写业务 SQL 逻辑。

输出：真实 Result、执行证据、标量归一化结果和执行状态。

检查内容：执行的 SQL 是否与 D10 完全一致；数据 revision 和 Skill revision 是否正确；运行时是否符合契约；Result 是否完成必要归一化。

通过条件：真实 Result 可追溯到当前 SQL、当前数据和当前执行环境。SQL 逻辑错误时“需回退 D10”；运行环境或权限问题在 D11 内修正或标记阻塞。

### D12 结果解释与分析信号

依赖阶段：D11。

输入：已确认真实 Result。

当前任务：只解释当前 Result 能确认的事实，并判断是否形成值得继续解释的分析信号。不生成新的 SQL。

输出：已观察事实、分析信号或“无高价值信号”、结论边界。

检查内容：是否把最高、最低、Top1、比例等描述值直接当成原因或结论；是否出现没有 Result 支持的新事实。

通过条件：输出只描述当前证据能够支持的事实，分析信号不超出证据。

### D13 本体局部展开

依赖阶段：D05、D06、D12。

输入：已确认分析信号和本体关系。

当前任务：只沿当前信号的合法本体邻居展开，生成有证据来源的复杂候选问题。不判断最终优先级，不执行 SQL。

输出：候选复杂问题及其合法关系路径。

检查内容：是否重新扫描全部字段；每个新增维度是否能说明为什么可能改变当前判断；主体、关系、粒度、单位和时间语义是否兼容。

通过条件：所有候选复杂问题都有合法关系路径和明确问题价值。需要验证时返回 D08，再进入 D09。

### D14 竞争解释

依赖阶段：D12。D13 结果可作为补充输入。

输入：已确认主要分析信号、已有证据和相关本体关系。

当前任务：建立主解释、合理竞争解释和反证条件。不执行诊断 SQL。

输出：假设边界。

检查内容：是否只有单一故事；解释是否能被当前数据区分；是否把相关性写成因果。

通过条件：至少存在一个主解释和一个合理竞争解释，或明确说明当前数据为什么无法建立可区分解释。

### D15 诊断验证设计

依赖阶段：D14。

输入：已确认主解释、竞争解释和反证条件。

当前任务：设计最能区分竞争解释的诊断问题。只设计验证问题，不执行 SQL。

输出：诊断问题、不同结果对应的解释变化和所需证据。

检查内容：诊断问题是否真正能够区分解释；是否只是继续增加描述维度。

通过条件：不同诊断结果会导致至少一个解释被支持、削弱、否定或保持未解决。通过后把诊断问题送回 D08。

### D16 稳健性验证设计

依赖阶段：D12、D14。通常在至少一轮诊断结果完成后执行。

输入：当前主要判断、已完成诊断证据和数据限制。

当前任务：设计一个真正可能改变当前判断可信度的稳健性问题。只设计测试，不执行 SQL。

输出：稳健性问题、压力测试方式和判断变化条件。

检查内容：是否机械重复同类指标；测试是否真的可能推翻或收紧结论；数据不足时是否强行设计不可执行测试。

通过条件：测试具有明确反证价值，或明确记录当前数据无法进一步验证。需要执行时把稳健性问题送回 D08。

### D17 已验证发现

依赖阶段：D12。若当前信号需要竞争解释或稳健性验证，还必须依赖相关 D14 至 D16 循环结果。

输入：已确认分析信号、诊断证据、稳健性证据和数据限制。

当前任务：判断证据是否足以把分析信号晋级为已验证发现。

输出：已验证发现、未解决问题和数据限制。

检查内容：事实、解释和限制是否分开；是否存在因果扩大、小样本外推或单点扩大；必要验证是否实际完成。

通过条件：每个已验证发现都能回指真实 Result、必要竞争解释和稳健性证据；证据不足时保持未解决，不强行晋级。

### D18 决策价值

依赖阶段：D17。

输入：已验证发现。

当前任务：判断哪些发现会改变观察重点、调查顺序、资源配置、业务动作或管理判断。

输出：决策级发现和被降级的发现。

检查内容：是否因为“有发现”就自动进入报告核心或 Dashboard；是否存在没有实际决策影响的内容。

通过条件：每个决策级发现都有明确决策价值；低价值发现被降级或删除。

### D19 ReportSpec

依赖阶段：D18。

输入：决策级发现、证据、限制和用户交付要求。

当前任务：只建立答案覆盖、信息层级和 ReportSpec。不选择最终图表，不生成 Artifact。

输出：ReportSpec。

检查内容：每个主问题是否有可见答案；ReportSpec 是否重新分析、改口径或新增未验证事实。

通过条件：ReportSpec 完整覆盖应回答的问题，且只引用已确认内容。

### D20 可视化计划

依赖阶段：D19。

输入：已确认 ReportSpec 和可视化要求。

当前任务：选择图表候选、信息布局和展示方式。不重新分析数据，不生成最终 Artifact。

输出：可视化计划和布局骨架。

检查内容：图表是否由独立结论决定；单位是否诚实；是否存在重复图、模板填槽或信息预算问题。

通过条件：每个主要视图对应一个独立结论，展示方式不改变数据语义。

### D21 最终 Artifact

依赖阶段：D19、D20。

输入：已确认 ReportSpec、可视化计划、SQL、Result 和交付要求。

当前任务：生成最终 HTML、报告或 Dashboard。不新增分析事实。

输出：最终 Artifact。

检查内容：Renderer 是否修改数字、SQL、口径或结论；是否泄露内部过程说明；是否满足指定文件和交互要求。

通过条件：Artifact 忠实实现已确认 ReportSpec 和可视化计划，没有生成新的分析事实。

### D22 成品验收

依赖阶段：D21。

输入：最终 Artifact 和当前执行证据。

当前任务：执行 Rendered QA、移动端、交互、异步 readiness、内容资格和回归验收。

输出：验收结果、缺陷清单和最终状态。

检查内容：是否真实渲染；当前 Artifact digest 是否匹配；被阻塞内容是否仍被展示；是否存在布局、交互或证据链问题。

通过条件：所有当前强制验收通过；未执行的检查不得写为 PASS。

### 分析循环

D08 至 D17 不是固定一次通过的直线。

允许的主要流转：

```text
D08 候选问题
→ D09 问题质量
→ D10 SQL 设计
→ D11 SQL 执行
→ D12 结果解释
```

D12 之后根据证据选择下一逻辑阶段：

```text
无高价值信号，但仍有值得回答的问题 → D08
需要沿业务关系继续追问 → D13 → D08
需要解释主要现象 → D14 → D15 → D08
需要压力测试当前判断 → D16 → D08
证据已经足够且没有必要继续验证 → D17
没有信息增量可继续产生 → 结束分析分支
```

任何回到 D08 的问题都必须重新经过 D09、D10、D11、D12。不得因为它来自复杂问题、诊断问题或稳健性问题就绕过问题质量、SQL 设计、真实执行和结果解释。

## 7. 从指定阶段继续

“从 Dxx 继续”只表示把 Dxx 设为下一执行阶段，不表示自动忽略上游。

开始前必须确认 Dxx 的所有必需依赖均为“通过”，状态记录中的输入和上游版本仍然有效。

如果依赖缺失或已经失效，返回“阻塞”，列出缺失或失效阶段。不得自动执行这些阶段。

如果依赖有效，只执行 Dxx 并停止。用户明确确认当前阶段通过并说“下一步”时，才按照当前阶段定义的下一逻辑阶段继续。分析循环中的“下一步”不等于固定的 Dxx+1，必须由当前 Result 和方法论决定。

## 8. 完整链路回归

只有所有实际用到的阶段都分别测试并得到用户确认后，才能执行完整链路回归。

完整回归使用正常模式连续执行，不逐阶段暂停。它必须遵守原方法论真实流转，包括 D08 至 D17 的分析循环，而不是机械执行一次 D01 → D22。

目标：

1. 验证单阶段正确后，串联仍然正确。
2. 验证阶段之间结果传递没有漂移。
3. 验证分析循环能根据真实 Result 选择下一逻辑阶段。
4. 验证正常模式没有被调试控制逻辑降速或打断。
5. 验证调试模式新增的锁定、回退和状态记录没有改变正式业务结果。

如果完整回归失败，先定位最早出现偏差的阶段，再回到调试模式修复。不得直接在最终 Artifact 层补丁。

## 9. 工程实现边界

本协议只定义逻辑阶段、输入输出、依赖、检查和状态，不决定最终工程拆分方式。

当前步骤最终采用单个 Skill 内部分段、多个独立 Skill、子模块、状态文件或其他实现形式，保持未确定。现有 `debug-stages.md` 只是当前仓库存放调试契约的位置，不代表最终模块边界。

后续只有在真实测试证明某种工程形式存在明确必要性时，才单独决定工程拆分。无论实现形式如何变化，都不得改变正式方法论的目标、业务逻辑、阶段职责和已确认约束。
