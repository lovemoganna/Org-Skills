# 分步调试协议

目标：把完整方法论拆成可独立执行、独立检查、反复调试的小步骤。一次只跑一个步骤。当前步骤未确认，不进入下一步。

正常模式继续自动完成完整流程。调试模式只在用户明确要求“调试模式”“只跑某阶段”“重跑某阶段”“从某阶段继续”或等价指令时启用。

## 1. 语言规则

所有调试步骤使用短句。每句只表达一个动作。

优先使用：

```text
输入
任务
输出
检查
通过
状态
```

规则：

1. 先写动作，再写对象。
2. 同一概念只用一个名称。
3. 删除背景解释、同义重复和不影响执行的说明。
4. 技术名词只在无法准确中文化时保留英文。
5. 检查结果必须写事实，不写“看起来正常”“基本没问题”。
6. 需要说明原因时，只说明会改变执行的原因。

## 2. 状态

只使用：

```text
待执行
待检查
通过
需修正
需回退
阻塞
```

含义：

`待执行`：尚未运行。

`待检查`：已完成并通过模型自检，等待用户确认。

`通过`：用户已确认。输出默认锁定。

`需修正`：问题属于当前阶段。只修当前阶段。

`需回退`：根因来自上游。停止当前阶段并指出回退位置。

`阻塞`：缺少合法输入、环境、权限或数据。停止，不绕过。

模型自检通过不得自动写成“通过”。只有用户明确确认当前阶段没有问题后，状态才能变为“通过”。

## 3. 一次只执行一个步骤

调试模式一次只执行指定阶段。

当前阶段完成后立即停止。不得自动执行下一阶段，也不得为了“方便”补跑缺失上游。

从指定阶段继续时，先检查全部依赖是否为“通过”且仍有效。依赖缺失或失效时，状态为“阻塞”，列出缺失阶段，**不得自动执行这些阶段**。

“下一步”表示进入当前逻辑上的下一阶段，**不等于固定的 Dxx+1**。

## 4. 自检自修

每个阶段内部执行同一个循环：

```text
执行
↓
对照检查项
↓
定位根因
↓
最小修正
↓
重跑当前阶段
↓
重新检查
```

根因只分四类：

| 根因 | 处理 |
|---|---|
| 当前阶段 | 只修当前阶段，再重跑 |
| 上游阶段 | 标“需回退”，停止 |
| 环境、权限、数据 | 标“阻塞”，停止 |
| 协议或步骤定义 | 标“需修正”，指出协议缺口，不擅自改方法论 |

自修规则：

1. 先找根因，再修改。
2. 一次只改一个根因。
3. 修后必须重新执行当前阶段。
4. 完成判断只使用本轮新证据，不使用旧结果代替。
5. 同一问题重复出现且没有新证据时停止，不继续试错。
6. 自修只能发生在当前阶段。不得顺手修改上游或下游。
7. 当前阶段自检通过后，状态仍为“待检查”，等待用户确认。

如果一个阶段包含多个可以独立失败的检查，拆成子步骤分别执行和记录状态。不得用一个总状态掩盖多个故障源。

## 5. 调试状态记录

调试模式必须维护最小状态记录：

| 字段 | 含义 |
|---|---|
| 阶段 ID | 当前步骤 |
| 阶段名称 | 当前职责 |
| 状态 | 当前状态 |
| 依赖阶段 | 已确认上游 |
| 输入标识 | 数据 revision、Skill revision 或等价引用 |
| 输出标识 | 当前输出的可比较引用 |
| 用户确认 | 是否明确确认 |
| 失效原因 | 哪个变化使结果失效 |

已通过阶段**默认锁定**。下游只能读取，不得静默修改、重算或重新解释。

上游重跑后：

1. 比较新旧输出。
2. 输出无实质变化且依赖仍有效，下游可保持原状态。
3. 输出发生实质变化，依赖旧输出的下游恢复“待执行”，并记录失效原因。

## 6. 每阶段固定输出

每次只返回：

```text
当前阶段：
依赖阶段：
输入：
本阶段任务：
输出：
检查结果：
通过条件：
状态：
```

发生问题时再补：

```text
根因：
修正：
回退阶段：
```

“输出”只包含当前阶段产物。不得提前生成后续阶段内容。

## 7. 阶段卡片

### D01 范围与执行契约

依赖：无。

输入：用户请求、数据源、SQL 方言、读取方式、运行环境、显式约束。

任务：锁定数据范围、执行语义、运行时、权限和不可变约束。

输出：执行契约。

检查：范围是否完整；Data Contract 与 Runtime Bootstrap Contract 是否分离；是否越权。

通过：范围、读取、运行时和权限无未解决冲突。

### D02 数据勘察

依赖：D01。

输入：执行契约、授权数据。

任务：识别表、字段、行粒度、键、时间、金额、单位、状态和可连接关系。

输出：数据集一页纸、结构事实。

检查：是否只读授权范围；每表粒度是否明确；字段和关系是否有数据依据。

通过：后续数据质量和业务语义所需结构事实完整、可追溯。

### D03 数据质量

依赖：D01、D02。

输入：执行契约、结构事实。

任务：执行当前结构触发的 Mandatory Data Quality 检查。

输出：检查结果、状态、下游影响。

检查：必须执行的检查是否真实运行；未执行是否误写 PASS；失败是否正确传播。

通过：所有必需检查都有明确状态和影响范围。

多个独立质量检查必须拆为 D03 子步骤，分别执行、分别确认。

### D04 业务语义还原

依赖：D02、D03。

输入：结构事实、数据质量结果。

任务：识别业务对象、事件、主体、关系、状态、粒度、单位和时间语义。

输出：业务语义模型。

检查：是否把字段直接当业务知识；关系是否有依据；是否混入指标或结论。

通过：能明确回答“数据描述什么业务世界”，对象和关系边界稳定。

### D05 本体原子知识库

依赖：D04。

输入：业务语义模型。

任务：生成最小可用、MECE 的本体原子。

输出：本体原子知识库。

检查：是否重复、遗漏、过度拆分或机械复制字段；类型、单位和值域是否正确。

通过：每个原子有稳定业务语义，并可独立参与关系、计算、判断或组合。

### D06 本体识别规则库

依赖：D04、D05。

输入：业务语义模型、本体原子知识库。

任务：生成由已登记原子构成的业务行为和业务模式。

输出：本体识别规则库、人类可读 Lisp。

检查：规则是否描述“发生了什么”；方向字段是否被错误解释为已经完成的业务结果；存在独立状态字段时是否区分“方向行为”和“已完成行为”；是否混入 GROUP BY、JOIN、SUM、TopN、完成率、质量检查或稳健性检查；Lisp 是否引用未登记原子。

通过：每条规则可追溯到合法原子和关系；方向、状态和完成语义不混淆；规则与 Lisp 语义一致。

### D07 高质量指标

依赖：D05、D06。

输入：原子知识库、识别规则库。

任务：生成少量候选指标，并筛掉低价值指标。不得建立额外指标 DSL，不得枚举全部字段、状态、维度和度量组合。

输出：保留指标、淘汰指标及原因。

检查：每个候选指标是否能回溯到 D05/D06；是否真的可能改变后续判断；是否只是因为字段存在或技术上能计算才生成；是否与其他指标重复；统计主体、结果粒度、分析范围、单位和口径是否明确；金额或数量名称是否忠实于订单/交易记录语义；比例、DISTINCT 和可加性约束是否正确；方向或状态是否被过度命名为成功率、完成率或处理效率。

通过：只保留少量有业务意义、可合法计算、可能改变判断的指标。低价值切片、重复指标和机械组合已淘汰。D08 直接基于这些指标生成原子问题。

### D08 候选问题

依赖：D07；分析循环中可接收 D13、D15、D16 的新问题。

输入：指标、已知事实、当前问题边界。

任务：生成最小可验证候选问题。

输出：候选问题集合。

检查：是否有证据来源；是否只改变一个主要判断；是否值得问。

通过：所有问题都有来源和验证目标，没有凭经验生成的“高级问题”。

### D09 问题质量与优先级

依赖：D08。

输入：候选问题、当前问题边界。

任务：检查触发原因、结果影响、可回答性和优先级，只选当前唯一问题。

输出：当前问题、淘汰问题和原因。

检查：不同结果是否会改变下一步；是否存在字段清单式查询。

通过：当前问题有明确触发、影响、可回答性和优先级。

### D10 SQL 设计

依赖：D01、D03、D09。

输入：当前问题、执行契约、数据质量约束。

任务：只设计回答当前问题的 SQL。不执行。

输出：唯一待执行 SQL、预期粒度、查询假设。

检查：SQL 是否对应当前问题；JOIN、时间、单位、粒度、过滤和别名是否正确；是否绕过阻塞。

通过：SQL 可在授权运行时执行，逻辑完整，不含实际 Result 或业务结论。

### D11 SQL 执行与真实结果

依赖：D01、D03、D10。

输入：已确认 SQL、运行时、数据 revision。

任务：执行 D10 的 SQL。不得改写业务逻辑。

输出：真实 Result、执行证据、归一化结果、执行状态。

检查：执行 SQL 是否与 D10 一致；revision 是否正确；运行时是否合规；Result 是否归一化。

通过：Result 可追溯到当前 SQL、当前数据和当前运行环境。

SQL 逻辑错误：需回退 D10。运行环境或权限问题：在 D11 修复或标“阻塞”。

### D12 结果解释与分析信号

依赖：D11。

输入：真实 Result。

任务：只解释当前 Result，并判断是否形成分析信号。不生成 SQL。

输出：已观察事实、分析信号或“无高价值信号”、结论边界。

检查：是否把最高、最低、Top1、比例直接当原因；是否出现无 Result 支持的新事实。

通过：所有陈述都由当前 Result 支持，分析信号不越界。

### D13 本体局部展开

依赖：D05、D06、D12。

输入：分析信号、本体关系。

任务：只沿合法本体邻居生成复杂候选问题。

输出：候选复杂问题、合法关系路径。

检查：是否重新扫全部字段；新增维度为什么可能改变判断；主体、关系、粒度、单位和时间是否兼容。

通过：所有候选问题都有合法路径和明确价值。

需要验证时回 D08。

### D14 竞争解释

依赖：D12；D13 可作为补充输入。

输入：主要分析信号、已有证据、本体关系。

任务：建立主解释、竞争解释和反证条件。不执行 SQL。

输出：假设边界。

检查：是否只有单一故事；解释是否可被当前数据区分；是否把相关写成因果。

通过：至少有一个主解释和一个合理竞争解释，或明确说明为什么只能保持未解决。

### D15 诊断验证设计

依赖：D14。

输入：主解释、竞争解释、反证条件。

任务：设计最能区分解释的诊断问题。不执行 SQL。

输出：诊断问题、结果分支、所需证据。

检查：不同结果是否真的改变解释；是否只是增加描述维度。

通过：不同结果会支持、削弱、否定某个解释，或保持未解决。

通过后把诊断问题送回 D08。

### D16 稳健性验证设计

依赖：D12、D14。

输入：当前判断、诊断证据、数据限制。

任务：设计一个可能推翻或收紧当前判断的稳健性问题。不执行 SQL。

输出：稳健性问题、测试方式、判断变化条件。

检查：是否有反证价值；是否机械重复指标；数据是否支持。

通过：测试可能改变判断，或明确记录无法继续验证。

需要执行时把问题送回 D08。

### D17 已验证发现

依赖：D12；需要竞争解释或稳健性时，还依赖相关 D14 至 D16 循环结果。

输入：分析信号、诊断证据、稳健性证据、数据限制。

任务：判断证据是否足以晋级为已验证发现。

输出：已验证发现、未解决问题、数据限制。

检查：事实、解释和限制是否分开；是否因果扩大、小样本外推或单点扩大。

通过：每个发现都能回指真实 Result 和必要验证。证据不足时保持未解决。

### D18 决策价值

依赖：D17。

输入：已验证发现。

任务：判断哪些发现会改变观察重点、调查顺序、资源配置、业务动作或管理判断。

输出：决策级发现、被降级发现。

检查：是否因为“有发现”就自动升级为决策信息；是否能说明具体改变什么判断或动作。

通过：每个决策级发现都有明确决策价值。分析深度本身不构成看板资格。

### D19 看板资格

仅在交付包含 Dashboard / 看板时执行。

依赖：D07。若当前分析已经产生 D17 已验证发现或 D18 决策级发现，可作为补充输入，但不是 Dashboard-only 的必需前置。

输入：高价值指标、看板目标和用户角色；如已有 D17/D18 结果，同时读取已验证发现和决策需求。

任务：判断哪些数据需要长期、重复、快速监控。看板资格与分析深度分开判断。

输出：看板核心项、下钻项、排除项及原因。

检查：是否需要持续监控；是否会随业务变化；变化后是否需要关注或行动；是否可稳定重复计算；是否能快速判断当前状态；是否只是一次性诊断证据或分析过程；是否因为分析很深就自动进入看板；是否遗漏简单但长期重要的基础状态指标。

通过：核心看板只保留持续重要、可重复计算、变化后需要关注或行动、适合快速读取的数据。一次性根因、诊断过程、竞争解释和稳健性证据默认不进核心看板。

### D20 交付规范

依赖：Report = D18；Dashboard = D19；Hybrid = D18 + D19。依赖必须实际完成且状态为“通过”。

输入：已确认的交付类型，以及对应上游输出及证据引用。
Report：D18 决策级发现、证据、限制；引用的实际 Result 必须能追溯到 D11。
Dashboard：D19 看板资格结果、口径、限制。
Hybrid：两组已通过的输入。

任务：只按已确认交付类型整理内容。不改变交付类型，不重新分析、不选图。依赖缺失、未通过或证据不可核验时标“阻塞”，不得产出空壳 Spec；应指出缺失阶段，不自动补跑。

输出：
Report：ReportSpec。
Dashboard：DashboardSpec。
Hybrid：彼此独立的 ReportSpec 与 DashboardSpec。
阻塞：依赖缺口与恢复条件，不生成正式 Spec。

检查：依赖状态是否真实有效；每个可展示结果是否有来源及 Gate 状态；是否把候选问题、指标定义或测试样例冒充已验证发现；交付类型是否被改变；两个 Spec 是否交叉；是否新增事实、SQL 或选图。D18 已完成但没有决策级发现时，可以如实输出“无决策级发现”，不能虚构发现。

通过：所需上游均已通过且证据可追溯，正式 Spec 只组织已确认内容；测试样例不能替代真实任务结果。

### D21 可视化计划

依赖：D20 已通过，且 Spec 有可核验的内容引用。

输入：已确认 ReportSpec / DashboardSpec、内容证据和可视化要求。

任务：只从可展示的 D20 内容生成独立 VisualizationPlan。不重新分析、不改写 D20、不生成 Artifact。D20 阻塞或缺失时停止，不凭样例补齐。

输出：VisualizationPlan 与布局骨架；依赖不足时仅输出阻塞原因。

检查：每个 content_ref 是否真实存在且未被 Gate 阻断；报告图是否服务结论和证据；Dashboard 图是否服务快速监控；单位、重复、布局是否正确；是否改动 D20 或编造数字。

通过：所有展示项都能回指有效 D20 内容，表达方式不改变数据语义；模拟样例通过不等于真实任务通过。

### D22 最终 Artifact

依赖：D20、D21。

输入：ReportSpec / DashboardSpec、可视化计划、SQL、Result、交付要求。

任务：生成 HTML、报告或 Dashboard。不新增分析事实。

输出：最终 Artifact。

检查：Renderer 是否修改数字、SQL、口径或结论；Dashboard 是否混入未通过 D19 的内容；是否泄露内部过程；是否满足交付要求。

通过：Artifact 忠实实现已确认内容。Dashboard 核心层只展示通过看板资格的数据。

### D23 成品验收

依赖：D22。

输入：最终 Artifact、执行证据。

任务：执行当前强制 QA。

输出：验收结果、缺陷、最终状态。

检查：Rendered QA、移动端、交互、异步 readiness、内容资格、证据链和回归；Dashboard 额外检查核心项资格与首屏信息预算。

通过：所有强制检查真实执行并通过。未执行不得写 PASS。

D23 中可以独立失败的 QA 必须拆成子步骤，分别执行、分别确认。

## 8. 分析循环

D08 至 D17 不是一次性直线。

主循环：

```text
D08 候选问题
→ D09 问题质量
→ D10 SQL 设计
→ D11 SQL 执行
→ D12 结果解释
```

D12 后按证据选择：

```text
还有值得回答的问题 → D08
需要业务关系展开 → D13 → D08
需要解释主要现象 → D14 → D15 → D08
需要压力测试 → D16 → D08
证据足够 → D17
没有信息增量 → 结束当前分析分支
```

任何回到 D08 的问题，都必须重新经过 D09、D10、D11、D12。

## 9. 回退与继续

当前阶段发现上游错误：

1. 停止。
2. 状态设“需回退”。
3. 指出根因阶段和证据。
4. 不在当前阶段修上游。

用户确认回退后，才重跑上游。

从某阶段继续时，只执行该阶段。用户确认通过后，再进入下一逻辑阶段。

## 10. 完整链路回归

只有本次实际使用的阶段都已分别测试并由用户确认后，才执行完整链路回归。

完整回归使用正常模式连续执行，不逐阶段暂停。必须遵守真实分支和**分析循环**，**而不是机械执行一次 D01 → D23**。

回归失败时，定位最早偏差阶段，再回调试模式。不得只修最终 Artifact。

## 11. 工程实现边界

本协议只定义逻辑阶段、输入、输出、依赖、检查和状态，**不决定最终工程拆分方式**。

最终可以采用**单个 Skill 内部分段、多个独立 Skill、子模块**、状态文件或其他形式。当前保持未确定。

现有 `debug-stages.md` 只是协议存放位置，不代表最终模块边界。
