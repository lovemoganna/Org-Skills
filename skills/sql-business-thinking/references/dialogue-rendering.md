# 人物会话与教学回放协议 V7

用于用户明确要求 star / Lucy、学习者 / 分析师、领导下任务后的讨论推演、师生、角色模拟或从头推演的任务。

核心原则：**人物会话不是把结果拆成对白，而是把“任务如何经过质疑、核事实、修判断，最终变成可汇报结论”完整呈现出来。**

---

## 1. Conversation Arc Contract

当用户要求“领导 → star → Lucy → star 汇报”或类似工作讨论时，正文必须形成一条连续状态链：

```text
Assignment
→ Framing
→ Decomposition
→ Evidence
→ Disagreement
→ Revision
→ Synthesis
→ Report-back
```

每个阶段可以合并，但以下四个节点不可缺：

1. **任务起点**：谁让 star 判断什么；
2. **证据形成**：star / Lucy 实际核到了什么；
3. **判断修正**：至少一次原判断因为证据而改变；
4. **任务终点**：最终由 star 把结论汇报回任务发起人。

禁止把会话做成彼此独立的“错题卡”或“知识点卡片”。后一段必须继承前一段已经确认的事实与决策。

---

## 2. 角色职责

### 领导 / Task Owner

只负责：

- 下达要解决的问题；
- 给出需要的判断或动作；
- 必要时规定交付边界。

不要让领导参与 SQL 细节，也不要把领导写成旁白。

### star / Analysis Owner

star 是任务负责人，不是“专门犯错的新手”。他必须：

- 先复述和收住任务；
- 主动提出第一版分析口径或假设；
- 在拿到新事实后更新判断；
- 能主动识别至少一个问题，而不是所有问题都等 Lucy 指出；
- 最终自己整合结论并向领导汇报。

star 可以犯新手错误，但错误必须符合其水平且真的会改变数字、粒度、JOIN、口径或结论。

### Lucy / Reviewer

Lucy 负责：

- 补充遗漏；
- 质疑未经验证的假设；
- 提醒需要核对的事实；
- 验证 star 的新判断是否被证据支持。

Lucy 不是“提前知道最终答案的全知专家”。没有证据时，Lucy 只能指出要检查什么，不能提前宣布最终数字。

---

## 3. Turn Delta Gate

每一句人物台词必须至少产生一种增量：

```text
FACT      新事实
JUDGMENT  新判断 / 修正判断
QUESTION  会改变下一步的关键问题
DECISION  新口径 / 新动作 / 新边界
```

如果一句话只是：

- “对。”
- “明白。”
- “好的。”
- 重复上一句已经说过的数字；
- 把最终结论换个说法再说一次；

就删除或并入前后句。

人物不是为了“看起来有对话”而说话。

---

## 4. Progressive Knowledge Gate

人物只能知道当前阶段已经出现的事实。

例如：

- 没跑用户汇总前，不得提前说 Top 3 = 83.48%；
- 没检查 `effective_date` 前，不得提前把结果叫“快照估值”；
- 没检查交集 / 并集前，不得提前说重叠率；
- 没核数据质量前，不得提前说有哪一条异常记录。

如果最终结论在对话开头就已经完整出现，会话判失败。

---

## 5. 分歧与修正

分歧必须来自真实分析风险，不为制造戏剧强行反驳。

高价值分歧通常包括：

- 不同币种是否能直接相加；
- 交易行数是否等于用户数；
- 时间维表是否能按业务时间点匹配；
- JOIN 是否放大；
- Top N 是否有区分度；
- 百分比分母是否正确；
- 均值是否能代表典型用户；
- 数据异常能否自行修值；
- 描述性集中是否能外推成风险。

至少一次要体现：**star 的原判断 → Lucy 提出证据问题 → 新事实出现 → star 自己改判断。**

---

## 6. 阶段组织

一段工作讨论只解决一个状态变化。推荐每阶段 2～4 个来回，默认不超过 4 个。

每阶段结构：

```text
当前问题
→ star 提出判断 / 下一步
→ Lucy 补充或质疑
→ 数据 / SQL 给出新事实
→ star 更新判断
→ （必要时）Lucy 验证边界
```

正文可以在阶段末尾显示一条非角色元信息：

```text
当前决策：...
新增事实：...
口径修正：...
```

它只能总结这一阶段真正发生的状态变化，不能写 Skill 调用。

---

## 6A. Code-in-Conversation Contract

当用户明确要求“代码必须产生在 star / Lucy 会话过程中”时，人物会话与代码不再是两条信息通道，而是一条因果链：

```text
当前问题
→ star 提出判断 / 查询意图
→ Lucy 补充、质疑或收紧边界
→ 生成只解决当前问题的 SQL
→ 记录/实时结果
→ star 基于结果更新判断
→ Lucy 验证边界（如必要）
→ 下一问题
```

硬规则：

1. **SQL 前必须有动机。**代码出现前，人物已经说清“为什么查、查什么、结果用于决定什么”。
2. **Result 后必须有状态变化。**结果出现后，至少有一句人物台词把新证据转成 FACT / JUDGMENT / DECISION；否则这段 SQL 是脱离叙事的日志。
3. **一段 SQL 只解决当前问题。**禁止为了省事把后面几个阶段的计算一次写进来。
4. **不事后补代码。**如果人物已经说出结论，再在页面后面集中放 SQL，判失败。
5. **Single Code Source。**正文原位 SQL 就是唯一权威代码实例；不得在附录复制第二套可执行 SQL。
6. **Result Dependency。**具体数字、比例、异常行第一次进入对白前，必须已经有对应 result 节点。

### Code Growth Gate

`Code-in-Conversation` 只解决“代码放在哪里”，还不够保证“代码是怎么产生的”。用户明确要求代码循序渐进产生时，必须再满足：

```text
star 提出最小查询意图
→ 代码草稿 A（最小骨架/局部条件）
→ Lucy 指出一个真实缺口
→ 代码草稿 B（只补这个缺口）
→ star 确认当前查询边界
→ 唯一可执行 SQL
→ Result
→ star/Lucy 基于 Result 改判断
```

硬规则：

1. **至少一次可见代码增量。** `对白 → 完整 SQL` 不算“逐步产生”。
2. **草稿不是第二套 SQL。**草稿只展示新增片段、骨架或 diff，标明“草稿 / 不单独执行”；最终每个问题仍只有一个可执行 `<pre>`。
3. **增量必须来自对白。**代码变化必须能指出是哪一句质疑/决定触发的，禁止为了演示而机械拆行。
4. **每次只补一种逻辑。**例如先补 `WHERE status='completed'`，再补时间 JOIN；不要一轮同时加入过滤、JOIN、聚合、排序。
5. **Result 前不允许解释 Result。**可以解释预期用途，不能预告数字。

### One Step One Query

当前推进点的最小单元是：

```text
一个问题 + 一段代码生长 + 一个最终可执行 SQL + 一个 Result + 一个判断变化
```

如果一个阶段里出现两个独立 SQL，读者会失去“现在到底在判断什么”的定位。第二个查询必须另起推进点。

### Human State Transition

人物会话模式里，Result 之后不要再插入：

- “这一步确认：……”
- “暂时不能推出：……”
- “截至目前我们知道：……”
- 累计事实清单。

这些内容如果重要，必须由 star/Lucy 用自然工作语言表达，并且只表达**刚刚变化的那一个状态**。

### Evidence Adjacency

产生判断的证据必须紧邻判断。正文不得让读者在会话与独立 SQL 附录之间来回跳。

推荐：

```text
star：我先确认汇率有没有覆盖交易日。
Lucy：资产覆盖和时间覆盖分开查。
[SQL：只查资产与 effective_date 覆盖]
[Result]
star：资产覆盖没问题，但只有一个 effective_date。继续查交易日精确匹配。
```

禁止：

```text
人物连续讨论 8 个结论
↓
页面最后统一放 10 个 SQL
```

### No Rolling Summary

推进过程中不要维护“截至目前的全部结论”“当前已知 6 条事实”这类滚动摘要。它会让读者把注意力从当前问题移到全局状态。

允许：
- 当前一步的局部判断；
- 下一步要验证的问题；
- 最终 report-back。

禁止：
- 首屏提前展示最终 KPI；
- 每阶段重复累计全部已知事实；
- 在对应 SQL 之前剧透后续数字。

## 7. 反问预算

分三级：

1. 目标 / 口径不明：只问一个带选项的问题；
2. 有合理默认：说明默认值后直接推进；
3. 事实 / 术语：直接回答。

每阶段最多反问 2 次。连续两轮反问后必须推进到：

- SQL；
- 数据检查；
- 或阶段结论。

禁止把人物讨论写成访谈问卷。

---

## 8. Report-back Traceability Gate

最终必须由 star 向任务发起人汇报，而不是让 Lucy 替 star 下最终结论。

最终汇报至少分：

```text
结果
判断
限制 / 待跟进
```

每个关键结论都必须能回指前序某个证据节点：

| 最终结论 | 前序必须出现的依据 |
|---|---|
| 总交易额 | 金额口径 + 汇率口径 + 用户聚合 |
| Top N 贡献 | 排序 + population + Top N 选择理由 |
| 用户重叠 | 两类集合 + 交集 + 并集分母 |
| 数据质量限制 | 对应质检事实 |
| 不能外推的判断 | 明确的结论边界 |

如果最终汇报出现前面从未讨论 / 验证过的新数字、新口径或新判断，判失败。

---

## 9. 信息通道

最终 Artifact 分开：

1. **人物会话**：任务与判断如何形成；
2. **代码生长与验证**：在 Code-in-Conversation 模式中原位嵌入人物会话，不再单独建验证台；普通模式才可放验证台。
3. **Skill Trace**：内部调用哪个 Skill、为什么。

人物台词不得出现：

```text
调用 Skill
关卡通过
按协议
根据路由
进入第 N 关
```

如果正文已经完整展示权威人物会话，不再在附录保留另一个旧版人物全文；避免出现“双重真相”。

---

## 10. 视觉规则

- star 左，Lucy 右；领导任务使用独立 brief，不伪装成聊天气泡；
- 气泡最大宽度 70%～72%，移动端 85%～86%；
- 会话是连续工作线程，不是大量彩色卡片；
- 每个阶段有明确标题，但不写“盲点 1 / 错误 2”羞辱式标签；
- 阶段结论只用一条小型决策行；
- 最终 star 汇报使用独立 Report-back 块，并可提供证据锚点；
- 默认角色回放可把 SQL 与 Skill Trace 分离；但进入 Code-in-Conversation 模式后，SQL + Result 必须原位插入人物回合之间，Skill Trace 仍然分离。

---

## 11. Dialogue QA

交付前逐项检查：

### Arc
- 是否从任务发起开始？
- 是否由 star 最终汇报结束？
- 中间阶段是否真的继承前一步状态？

### Role Balance
- star 是否承担综合、判断与收敛，而不只是犯错？
- Lucy 是否负责挑战与验证，而不是提前公布所有答案？
- 去掉姓名后，角色职责是否仍然能从语言中区分？

### Turn Delta
- 每句是否新增 FACT / JUDGMENT / QUESTION / DECISION？
- 是否存在无效“对 / 好 / 明白”回合？
- 是否有重复最终数字的假对白？

### Knowledge State
- 有没有人物提前知道尚未验证的数字或异常？
- 判断是否随着证据逐步更新？

### Code / Evidence（Code-in-Conversation 模式）
- 每个 SQL 前是否已有明确查询动机？
- 每个 SQL 后是否由人物使用结果推进判断？
- 是否存在“人物先知道数字、SQL 后补”的倒序？
- 同一个 SQL 是否只保留一个可执行实例？
- 是否把 SQL 复制到独立附录形成第二套事实顺序？
- 是否存在跨阶段滚动汇总干扰当前推进点？

### Traceability
- 最终 star 汇报的每个结论是否能回指前面的事实？
- 最终汇报有没有突然出现的新数字 / 新口径？

### Presentation
- 人物会话是否正文可见？
- SQL / Skill Trace 是否和人物对白分离？
- 桌面 / 移动端是否仍能清楚区分角色？

任一失败，人物会话不算完成。

### Code Growth
- 每个推进点是否只有一个当前问题和一个最终可执行 SQL？
- 是否至少有一次由对白触发的可见代码增量？
- 草稿是否明确不是可执行权威版本？
- 是否存在“完整 SQL 突然蹦出来、对白只负责解释”的假渐进？
- Result 后是否由人物自己完成判断变化，而不是旁白摘要？
- 是否删除所有跨阶段滚动汇总？
