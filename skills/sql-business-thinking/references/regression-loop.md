# Artifact Regression Loop

用于用户要求“持续扫描 → 修正 → 自检 → 再修正，直到稳定”的 HTML / 报告任务。

## 1. 基线

先保存当前可运行版本。任何修改失败都能回退；禁止在唯一可运行版本上做不可逆覆盖。

## 2. 每轮扫描五个面

### A. 内容覆盖

- 每个主问题/子问题有正文 Answer Block；
- 数字一致；
- 结论不越界；
- 关键限制靠近受影响结论。

### B. 功能

- 初始化；
- fallback；
- 运行按钮；
- SQL/结果映射；
- 折叠；
- 打印；
- 错误状态。

### C. UI / 布局

- 首屏信息优先级；
- 桌面宽度；
- 移动端；
- 长表/代码溢出；
- 颜色是否只承担层级/状态；
- Meta 信息是否抢主任务。

### C2. 人物会话（任务明确要求时）

- 先核对当前请求的角色绑定；显式人物名必须原样保留，未指定时才回退到默认 `Star/Lucy`；

- 是否有完整 Conversation Arc：任务下达 → 推演 → Analysis Owner report-back；
- 本轮绑定的 Analysis Owner 是否承担综合、判断和收敛，而不是只负责犯错；
- 本轮绑定的 Reviewer 是否只补充 / 质疑 / 验证，没有提前知道未验证答案；
- 每句是否新增 FACT / JUDGMENT / QUESTION / DECISION；
- 是否存在无信息确认句、重复最终数字的假对白；
- 最终汇报能否逐项反查到前序证据；
- 是否把“调用 Skill / 关卡”写进人物台词；
- 对话是否被 SQL、结果表、Skill Trace 打碎；
- 正文与附录是否存在两个不一致的人物版本；
- 移动端是否仍能清楚区分本轮绑定的 Analysis Owner / Reviewer。

### D. 数据逻辑

- 粒度；
- 时间匹配；
- JOIN 基数；
- Top N；
- NULL；
- 口径命名。

### E. 生成机制

每个真实缺陷都问：

```text
为什么 Skill 会生成这个缺陷？
是缺规则、规则冲突、验收缺失，还是 Renderer bug？
能否写成下一次自动避免的规则？
```

## 3. 修正优先级

只修高价值问题：

P0：数据/结论错、功能不可用、丢主答案。
P1：信息优先级错、关键限制隐藏、移动端破版、JOIN/时间语义风险。
P2：明显可读性/交互问题。
P3：纯审美微调，不做，除非它影响理解。

## 4. 每轮自检

修完必须重新跑：

- DOM 结构；
- JS 语法；
- ID/按钮映射；
- 关键数字字符串/ReportSpec；
- 渲染烟测；
- 移动端结构：实际测量 `scrollWidth <= clientWidth + 1`；Grid/Flex 内的代码/表格容器检查 `min-width:0` 与局部 `overflow-x:auto`；
- 人物会话结构与角色约束（如适用）；
- 与上一版业务结论 diff。
- HTML 实体文件交付：默认路径存在、文件非空、最终回复链接与实际文件一致（如适用）。

正确内容若发生无授权变化，视为回归，立即修复或回退。

## 5. Skills 回写

记录：

| 暴露缺陷 | 根因 | 修正 | 可泛化规则 | 当前报告验证 |
|---|---|---|---|---|

只要可泛化，就回写到 SKILL 或 references。然后用当前报告再生成/再检查一次，确认规则真的能阻止同类问题。

## 6. 停止条件

只有同时满足才停止：

- 无 P0/P1；
- P2 剩余项不值得继续改；
- 关键答案覆盖完整；
- 运行时/交互无明显阻断；
- 桌面/移动端结构成立；
- Skills 缺陷已回写并由当前报告反向验证；
- 继续修改只会变成纯审美偏好。
