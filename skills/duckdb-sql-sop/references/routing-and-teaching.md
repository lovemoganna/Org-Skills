# 动态路由与渐进教学（V2.2）

## 任务模式

| 模式 | 触发条件 | 比较重点 |
|---|---|---|
| 教学驱动 | 学 SQL / 学分析思维，没有明确业务决策 | 分析信息增量、教学增量、可理解性、思维递进 |
| 业务驱动 | 有明确业务决策、运营问题或调查目标 | 业务目标相关性、决策价值、信息增量 |
| 混合 | 用户同时明确要求真实业务分析与教学训练 | 两种目标兼顾，不凭空创造业务目标 |

## 动态步骤

1. Phase 0 之后列出真实字段、类别、时间、关系与数据质量支持的少量候选业务问题，附一行理由。此时不要先建立 `valid_*`、`normalized_*`、`user_flow` 等预设事实层。
2. 为每个问题标记类型：**描述型**只描述当前数据；**比较型**要有可比总体/口径；**推断型**涉及推广、因果、风险规律或预测时要求额外证据。不能以“小样本”为理由阻断准确描述当前全体样本的简单问题。
3. Hard Gate 排除：数据不足、指标语义不清、关键字段不可信、无法验证、显著重复、重复计量无法约束、只能猜业务规则、依赖禁止表、为了覆盖 SQL 关键字。
4. 教学模式的比较维度：分析信息增量、教学增量、数据支持度、可验证性、思维递进、非重复性，扣除分析及认知复杂度。业务模式只有在明确业务目标时评价决策价值。
5. 通常选 **2–4** 个高价值问题。不强凑 2 个。执行完一个问题再重新考察剩余候选池；如新结果暴露真实新问题，可调整原计划。不能机械枚举每个字段。
6. 对入选问题明确它需要哪些数据、过滤总体、JOIN、粒度、单位与事实层，再决定最小 SQL。实际结果可能使该路线中断、转向或分叉。

## SQL 与教学增量

| 真实障碍 | 最小新增 SQL 能力（仅在需要时使用） |
|---|---|
| 观察有效交易/过滤 | `WHERE`, `GROUP BY`, `COUNT` |
| 对类别作可验证比较 | `GROUP BY`, `ORDER BY` |
| 借助其他表字段 | 显式 key 转换后 `JOIN` |
| 方向或业务条件不同 | `CASE` |
| 合并同构记录且保留重复 | `UNION ALL` |
| 保留完整业务对象总体 | `LEFT JOIN`, `COALESCE` |
| 排名、占比或累计 | Window Functions |
| 当前问题需要时间粒度 | `date_trunc` |

这些是**触发映射**，不是必须讲完的章节。每个问题都解释“已知什么、为什么要查、用了什么 SQL、查到什么、如何独立验收、接下来是否值得继续”。

## 已知决策边界

源 SOP V2.2 **没有**定义评分刻度、固定权重、同分裁决和 Probe SQL 预算。不要偷偷补一个数学公式并宣称“遵循 V2.2”。可用透明的定性比较并记录依据；若多个候选无法合理排序，明确写“当前 SOP 无法唯一决定优先级”，将其计入可执行性审计。详见 [已知限制](known-limitations.md)，但不要因为不确定性而编造证据。
