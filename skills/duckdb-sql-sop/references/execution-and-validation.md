# 执行、指标与验证规则（V2.2）

## 分析单元的输入输出

1. **观察事实**：只记录已执行 DuckDB SQL 可支持的字段、数值与关系；对未知保持未知。
2. **口径决定**：单独标注筛选总体、币种、有效交易标准、时间范围与 NULL 规则；这不是数据事实。
3. **指标定义**：列明对象、总体、时间、数据粒度、单位、分子/分母、正负、去重、NULL、可比性、可加性。
4. **最小 SQL**：能够回答问题即可；复用多次再考虑 TEMP TABLE/VIEW，仅一次使用可用 CTE。
5. **实际结果**：原样记录行数、字段、数值、查询错误或空结果；禁止用 Pandas/JS 计算业务数值代替。
6. **独立 Validation SQL**：根据问题选择原始/结果行数对账、KEY 唯一性、TRY_CAST 失败、JOIN 覆盖、NULL、分组回和、占比、时间窗口与反向验证。不能仅用“结果看起来合理”验收。
7. **解释与重新路由**：标明适用范围、未知、后续最值得回答的问题；根据已验证事实重新决定下一步。

## JOIN key 规范化

- 先识别是业务 ID 还是可数值运算的字段。标识符含前导零或字符编码时不得转整数。
- 显式指定统一类型（例如 VARCHAR），用 `CAST` / `TRY_CAST` 规范化；随后检查 `NULL`、转换失败、规范化后冲突及 JOIN 覆盖。
- 不假设 `users.uid` 与交易 `uid` 原始类型相同。不能用隐式类型转换悄悄绕过不一致。

## 跨域语义 Gate

相同 `USDT` 单位只说明**价值尺度可比较**，不能证明 fiat 和 crypto 是独立事件。检查经济含义、事件互斥/重复计量、粒度、时间口径和业务关系。不足以证明时分开报告或显式陈述假设，禁止报告未经验证的合并净流入。

区分活动与净额：`transaction_count`、`gross_inflow`、`gross_outflow`、`gross_activity`、`net_flow`、`has_activity` 按当前问题选择；`net_flow = 0` 不等于“没有交易”。

汇率 `rate_to_usdt` 要核查映射覆盖、正值和 `effective_date`。交易与汇率日期不一致时只能作为“USDT benchmark”且注明局限，不能冒充交易发生时估值。

## 异常处理

| 状态 | 用法 | 下一步 |
|---|---|---|
| PASS | 已满足当前问题的验证条件 | 生成新事实；重新路由 |
| BLOCK | 会破坏当前指标正确性，例如必要金额解析失败、重复计量无法排除 | 停止受影响路径，定位根因，验证后再继续 |
| SCOPE | 仅阻断依赖该缺陷的分析，例如 `completed_at` 不足以支持处理时长 | 限缩当前问题，其余独立路径可继续 |
| WARN | 限制不改变当前结果，但影响解释范围 | 披露限制，继续 |

状态需附可定位证据：查询、异常数、失败字段、影响问题；不得一处缺陷全局阻断。

## 停止判定

当前路径已经回答、剩余问题重复、数据不支持更深结论、需要不可获得的业务规则、复杂度超过学习/分析收益、仅为了覆盖语法，都可以停止。完成少量问题、主要结论验证、限制明确且无高优先级新增问题后结束本轮。
